# Equipment from Heavens: AI, Presentation, and Completion

## AI recipient equality

AI countries use the same uniform recipient pool, magnitude weights, family selection, technology pool, quantities, nuclear chance, and special-equipment chance as player countries.

AI cannot receive a smaller package because it is poor, weak, landlocked, low on fuel, out of manpower, or unable to understand the equipment. The event's identity depends on equal absurdity.

Technical validation can reroll an unusable token. It cannot reroll a strategically awkward but functional family.

## AI post-delivery assessment

After the one-time grant, an AI recipient performs one bounded military assessment. It does not need a new permanent AI system.

The assessment classifies each delivered family into:

- immediately usable
- usable after ordinary force reorganization
- useful for lend lease or strategic reserve
- unusable under current geography or infrastructure
- dangerous special payload requiring an owner-approved use path

The classification helps AI production, template, air, and deployment choices. It does not alter the package.

## AI conventional use

### Infantry and artillery

The AI can expand or reinforce ordinary templates when it has manpower and supply. It should not spawn free divisions or receive manpower to match the stockpile.

The AI may reduce production of an oversupplied family, but it should not delete all domestic production when replacement is impossible. It should retain a bounded replacement line when the delivered family supports existing divisions.

### Armor and mechanized forces

The AI should create or expand armored formations only when it has adequate fuel access, supply, and manpower. It may keep much of the stockpile unused if those conditions fail.

A large stockpile can justify a temporary shift toward armor. It should not force a landlocked or fuel-starved minor into an unsustainable all-armor army.

### Aircraft

The AI should use delivered aircraft only when it has airbases, fuel, and pilot manpower. It may prioritize airbase construction through ordinary AI plans if the package is large enough, but Event 42 does not build airbases for it.

The AI should not delete excess aircraft merely because it cannot deploy them immediately.

### Logistics

Trucks, trains, and convoys enter ordinary logistics and lend-lease evaluation. A landlocked AI can retain convoys or send them to allies. It does not need an Event 42-specific disposal action.

## AI nuclear use

Event 42 does not create separate reckless nuclear logic. The recipient uses the shared nuclear AI, target rules, delivery conditions, and strategic evaluation.

The launch-only compatibility contract, when needed, must expose the stockpile to the shared AI without giving production access. The AI should understand that the weapons are finite.

Actual use triggers the normal consequences. AI possession does not receive a hidden exemption from Condemnation or retaliation.

## AI special-equipment use

A special family is not eligible for Event 42 until its registry row includes an AI plan.

That plan must define:

- whether the AI can create the matching template or activate the payload action
- minimum usable stockpile
- manpower and support-equipment requirements
- fuel and supply requirements
- maximum share of fielded army or payload reserve
- valid enemy and target conditions
- use-policy restrictions
- cleanup when the source event later takes ownership

If no safe AI path exists, the family remains excluded even if a human could use it through console or manual template editing.

## Delivery report presentation

The event uses report-event art and ordinary popup surfaces. The physical scene should dominate each image.

Planned report families:

1. crate fields and blocked roads
2. vehicles descending under immense parachutes
3. intact aircraft scattered across an improvised landing ground
4. a village or depot overwhelmed by military cargo
5. a sealed nuclear storage discovery
6. unidentified high-chaos containers whose contents are not visually tied to an unverified equipment family

Images should look like period documentary photography. Final 210 by 176 report cards use black-and-white source treatment with sepia, a slight local tilt, transparent corner space, and a soft shadow according to the asset skill.

A report should not show a visible sender, modern cargo aircraft, readable generated labels, futuristic user interfaces, or a map as the main subject.

## Report allocation

The main popup can use a general crate-field image. Landing reports select an image based on manifest family and report theme.

Nuclear art appears only when the nuclear slot succeeded. The high-chaos sealed-container art appears only when Evolution III added a verified special family. A conventional package never uses those images merely because current Chaos is high.

## Event Log integration

Each completed main delivery creates one Event Log history row.

The row records:

- Event 42 identity
- date
- recipient actor
- magnitude
- broad package type
- firing count

The detail view explains the premise and reports the broad manifest. It should not expose hidden family weights, source-event internal tokens, or exact compatibility flags.

The event catalog row shows live weight and repeatable state through the normal event framework. When no valid recipient exists, its weight display is `N/A`.

## Evolution Log integration

Each evolution stage records one global actorless evolution entry after its paced activation.

The detail direction is:

- Evolution I: the sky no longer distinguishes ordinary from specialized conventional arsenals
- Evolution II: the deliveries contain technology from the far end of existing military development and may include atomic stockpiles
- Evolution III: equipment tied to other Chaos systems appears without its original cause

Evolution details describe the new behavior without listing exact hidden probability values or future surprise families.

## Event Details direction

Event Details should explain:

- a random ordinary country receives an enormous unexplained military delivery
- recipient size does not reduce the package
- equipment may be difficult or impossible for the recipient to reproduce
- later evolutions widen the pool and can introduce nuclear or special Chaos equipment
- the source remains unknown

It should not read as a reward list. It should not reveal exact achievement conditions, weighted pools, special-family tokens, or source-event isolation logic.

## Achievement routes

The event supports three difficult achievements. Names below are working labels.

### Working label: Tiny Arsenal State

Eligibility is recorded when a country with fewer than ten total factories receives Event 42.

Completion requires the same country to:

- field at least fifty more divisions than it had at receipt within one year
- retain control of its capital
- defeat or force peace against a major country within three years of receipt
- remain the same player-controlled country without tag-switch exploitation

The achievement represents converting an absurd stockpile into a real army. It does not require exact equipment provenance in every battalion because ordinary HOI4 stockpiles do not preserve origin at division level.

### Working label: Nuclear Lottery

Eligibility requires:

- zero nuclear weapons before the delivery
- no nuclear production technology before the delivery
- an Event 42 nuclear cache

Completion requires the recipient to conduct a normal nuclear strike before gaining ordinary nuclear production access. The strike must use the shared nuclear consequence pipeline.

### Working label: Borrowed Nightmare

Eligibility requires an Evolution III special-equipment delivery before the owner event has fired in the campaign.

Completion requires the recipient to field or use that exact special family in a valid combat or payload action while the owner event remains unfired. The action must consume, deploy, or materially use the equipment. Passive stockpile ownership is insufficient.

This achievement is available only for families whose compatibility registry can prove source-event isolation and actual field use.

## Achievement safeguards

Achievement state must be snapshotted at the qualifying delivery and protected from:

- tag switching
- duplicate report grants
- source event firing before the required action
- force-trigger modes when achievements normally disallow them
- save and reload loss
- puppet release or annexation identity confusion
- repeated Event 42 firings overwriting a stronger active challenge

A later qualifying delivery can open another route only after the previous route completed or failed cleanly.

## Event asset inventory

Required visible assets are:

The event reuses ordinary equipment icons and existing special-family icons. It does not need a unique portrait, flag, focus icon, decision icon, animated sprite, or 3D model because it creates no new character, country, unit family, or mechanic window.

## Cluster behavior acceptance

When the final Various Anomalies cluster registry is available:

- Event 42 appears as a Low member

- cluster unlock is checked separately
- a cluster transaction can create at most one Event 42 delivery
- invalid recipient state produces a member skip reason
- Event 42 applies its own repeatable weight and history behavior
- the cluster advances global pacing only once
- landing reports create no extra pacing

## Core acceptance scenarios

### Recipient fairness

Create a candidate pool containing a one-state minor, a subject, a player minor, a major, and a large AI power. Under identical eligibility every country must receive equal raw selection weight.

### Tiny recipient

Select a one-state minor and force an Impossible armor or air package. The full quantity must arrive. Reports may revisit the same state, and local landing modifiers must merge safely.

### Major recipient

Select a major using the same seed and active stage as a minor test. Package scale must not rise because the recipient is larger.

### Duplicate-grant prevention

Save after the main popup and before delayed reports. Reload and complete the chain. The stockpile must increase once, while every pending report continues with the saved manifest.

### Repeated recipient

Allow one country to receive Event 42 twice in separate completed firings. The second package must be independently generated, and the recipient must not be excluded by prior history.

### Evolved first firing

Activate each evolution before Event 42 first fires. The first package must use the active pool without creating baseline-only evolution history or retroactive equipment.

### Disabled evolution

Disable each stage before eligibility and after activation. Future manifests must respect the setting. Existing stockpiles remain.

### Nuclear cache

Test a recipient with no nuclear technology, a recipient with launch access but no stockpile, and an established nuclear power. Verify stockpile quantity, launch-only access, production denial, shared AI, and shared consequences.

### Special family

For every allowlisted special family:

- grant the physical token
- prove the matching use path
- prove production remains unavailable unless already earned normally
- prove the owner event's lifecycle is unchanged
- prove AI behavior
- prove save and reload
- prove source-event later firing merges safely

### Cluster root and member

Test Event 42 as selected cluster root and as optional member. Each transaction must grant one package and create one Event 42 history row.

### Chaos accounting

Verify the first skyfall adds its one-time anomaly source, the first sudden nuclear actor adds its guarded source, and the first fieldable owner-event escape adds its guarded source. Repeat ordinary deliveries and evolution activation must add zero direct Event 42 Chaos.

### Catalog and UI

Verify event name, type, Chaos level, cluster role, severity, status, details, evolution details, live event weight, actor, and history wording agree across localisation, Event Details, cluster details, docs, and the authoritative workbook.

## Exploit review

Implementation must check:

- report chains granting the package more than once
- force-trigger spam bypassing repeatable cap behavior
- manifest rerolls after save and reload
- player tag switching to retain multiple achievement routes
- special receipts granting production
- compatibility receipts starting source events
- AI creating unlimited zero-cost special divisions
- clone cohorts producing runaway weekly manpower
- nuclear launch-only access remaining after stockpile depletion
- package family rerolls shrinking value
- designer variants producing invalid empty chassis
- the same special family occupying several slots
- cluster firing Event 42 twice
- obsolete temporary targets remaining after closure
