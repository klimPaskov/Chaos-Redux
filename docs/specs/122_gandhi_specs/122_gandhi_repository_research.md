## Findings that materially constrain the Gandhi specification

1. A cooperative League can coordinate research and industry while arsenals remain nationally owned. The examined repository has native technology-sharing definitions, but no established cross-country nuclear pool or general safe nuclear transfer service was found in this bounded search. A shared fungible bomb total must not be presented as an existing implementation.
2. Event 023 has a real stockpile and allocation contract, but it is an event-owned Soviet-origin ledger with actor and provenance gates. Its opening and evolution device grants are Event 023-specific. Gandhi cannot call those grant helpers as a shortcut to an earned arsenal.
3. Native law permission is separate from capability. The nuclear law has no-use, retaliation and unrestricted routes. Retaliation requires an exact hostile offender receipt and is not inherited from a threatened ally or faction member. A League vote cannot silently authorize a country's native launch against its current law.
4. Event 023's native detonation route has an explicit callback and one-device stock-delta boundary. It is an accepted source route with acknowledged physical-delivery limitations. It does not start a raid, assign a wing or establish actual air superiority.
5. Event 032's nuclear custody extension is explicitly unresolved. Current code still has the defects described in its October handoff. The proposed `nuclear_payload_*` endpoints must not be cited as existing APIs.
6. Capturing a nuclear depot is physical custody. It does not instantly grant technical access, authorization, delivery or a native usable stockpile. A safe Gandhi capture or voluntary transfer branch requires the proper owner adapter and proof before it can satisfy credible arsenal eligibility.
7. Peaceful dismantlement and observed removal exist as source precedents, with explicit site, holder and ledger ownership. They do not justify deleting an arbitrary country's native bomb count from a League diplomatic popup.
8. Current Event 023 and Event 032 documentation explicitly separates nuclear escalation from terminal world-end ownership. A general exchange does not itself set `world_end`. This supports the supplied rules requiring a playable Gandhi opposition conflict before a terminal victory.
9. Current occupation sources show responsible-occupier state modifiers and separate local factory, resource and manpower surfaces. They do not establish that zero resistance plus zero compliance yields zero economic benefit. Exact zero-yield behavior remains an installed-engine verification item.

The accepted specification uses distributed national arsenals and owner consent. Research and industry assistance can be coordinated by the League. Special borrowing, custody and capture are conditional on verified owner APIs. The unresolved Event 032 extension is therefore a blocker to claiming that extension works, not a prerequisite for the core peaceful campaign.

## 1. Real nuclear capability and source ownership

### Event 023 runtime contract

Fully read: `common/scripted_effects/023_sov_nuclear_bombs_runtime_effects.md`.

Its source ledger has mutually exclusive operational, assigned, reserved and transferred intact buckets, and dismantled, missing and expended terminal buckets. Transit is a subset of assigned custody. Active dismantlement is a subset of reserved custody. Neither subset is an extra bomb. Native `num_of_nukes` is observed separately and the event ledger does not overwrite the native stockpile to repair disagreements.

The same contract says a pending native callback, missing device, negative bucket or native stock mismatch creates a disputed state. The system must not silently create a replacement weapon or grant a refund when source proof is missing.

The actual current source in `023_sov_nuclear_bombs_runtime_effects.txt` confirms:

- `sov_nuclear_bombs_register_production_devices`, beginning at line 438, requires a registered actor, valid Event 023 actor, exact valid assembly site, production capacity, `atomic_research`, `nukes` and a positive pending production amount. It grants that batch once, updates Event 023 allocation totals, clears the pending amount and notifies Event 032. The helper is not generic cooperative production.
- `sov_nuclear_bombs_execute_shared_action`, beginning at line 819, rejects an unresolved pending request rather than refunding or replacing it. It distinguishes non-yield action classes, records a before-stock observation and expected one-device decrease, sets the atomic delivery profile and exact pending state/nonce, then calls the native effect.
- `sov_nuclear_bombs_confirm_native_delivery`, beginning at line 1099, reads native stock again, requires its valid delta, commits the existing reserved device and only then marks confirmation. A failed delta goes to disputed delivery handling.

These are source-confirmed behavior claims, not runtime observations. The runtime Markdown still names native delivery, mixed stockpile attribution and save/reload conservation as evidence gaps.

### Existing progress and DLC boundaries

Fully read: `docs/specs/023_sov_nuclear_bombs_specs/023_sov_nuclear_bombs_technology_and_dlc_notes.md`.

That specification requires unioning minimum capability with an existing country's research and production, without resetting or replacing progress. It specifically prohibits granting free delivery aircraft, thermonuclear technology, missiles or unrelated research merely to make an atomic narrative work. It also makes the installed-game DLC matrix an explicit implementation task, with unverified branches labeled pending rather than promoted to working fallback paths.

The current Event 023 event document identifies an implemented atomic preflight using `atomic_research`, `nukes`, strategic bomber technology or the BBA airframe branch, at least ten deployed strategic bombers, fuel, a controlled airbase, crew certification, a state distance ceiling and war for combat use. The document explicitly says the preflight does not model actual assigned wings, true wing range or air superiority.

For Gandhi, the credible-arsenal gate must therefore refer to a member's real available native devices, actual capability and the accepted delivery surface. A contribution score, a completed political project, reactor ownership or a selected nuclear doctrine is insufficient by itself.

## 2. Cooperative research and national arsenals

Fully read: `common/technology_sharing/chaosx_tech_sharing.txt`.

The file contains `cure_sharing`, four generic `chaosx_research_group_*` definitions and `zombie_postwar_research_compact`. The last is a concrete example of category-limited sharing with live eligibility. None of the examined groups establishes a nuclear stockpile pool or multi-country weapon-custody mechanism.

The supplied technology skill already establishes the native technology-sharing surface. Current repository source confirms the mod uses that native surface. A League research group can be specified as a new scoped consumer, subject to current capability and DLC checks. It must not imply that one country's completed research creates a bomb in another member's stockpile.

The accepted distributed model avoids depending on the unresolved nuclear custody proposal. Each member remains the owner of its research, production facilities, delivery forces and devices. League support may change incentives and project funding through shared payment contracts. The member's actual completed production remains the evidence that the arsenal exists.

A policy mandate is distinct from an operational order. Consent to membership or a common research program must not be treated as consent to release every existing national bomb. Withdrawal must not create or destroy devices. A national asset pledged to League defense is still unavailable to a strike if its actual owner has lost the stock, revoked authorization or no longer has a valid delivery route.

No bounded search result establishes a ready safe cross-owner donation, loan or pooled custody API. That is a narrow research conclusion, not a proof that no differently named or constructed call exists anywhere in the repository.

## 3. Native national policy and retaliation rights

Fully read:

- `common/scripted_effects/national_policy_warfare_effects.md`
- `common/scripted_triggers/national_policy_warfare_triggers.txt`

The current trigger `national_policy_nuclear_allows_use_against_target_id` permits an unrestricted nuclear law, or retaliation law combined with the existing exact-target retaliation right. The no-use law is not an allowed branch. `national_policy_nuclear_allows_use_against_from` also requires an existing exact target and a current war.

The Event 023 adapter `national_policy_nuclear_event_action_policy_is_valid` applies that permission to combat strikes using the existing exact target. Tests, accidents, demonstrations and demolition retain their own separate validators. A peaceful demonstration must not be mislabeled as combat simply to generate retaliation authority, and a combat strike cannot be passed as a demonstration to avoid policy.

The documented confirmed-use evidence contract uses native launcher ROOT and hit-state FROM. The victim is the current hostile controller. It does not propagate automatically to the state's owner, other enemies or faction partners. Tests, demonstrations, accidents and unresolved matching Event 023 requests cannot fall through to ordinary combat evidence. Visual-only asteroid callbacks are excluded.

The retaliation window is 365 days under the current shared tuning. Exact duplicate confirmation does not renew the same action. A later independent use can renew it. Copied civil-war evidence with a different authority owner fails closed. Same-day first-use ties retain contested history while revoking live rights in both directions.

Policy changes retain confirmed-use history. Tightening a law asks the existing Event 023 owner to cancel an unauthorized uncommitted reservation, but does not refund an already pending native delivery. This is a useful exact precedent for a member revoking a League mandate, with the stock owner retaining its transaction authority.

The current policy documentation names all six native nuclear raid launch gates and the Event 023 combat validator. I also inspected relevant current Event 032 payload predicates. They use their own missile payload policy and custody markers, with no direct `national_policy` occurrence in the inspected operations-trigger file. The definition of every transitive missile policy helper was not reviewed, so this is not a completed bypass finding. Gandhi must explicitly require both the shared national law and delivery-owner permission in its acceptance criteria rather than assume one policy field covers both.

A new Gandhi wrapper must not add a second native bomb debit around this route.

The bomber raids have success calculations involving air superiority, interception, anti-air, radar, aircraft properties and intelligence. The Event 023 scripted `launch_nuke` route does not execute that native raid sequence. These delivery surfaces must be described accurately and not conflated.

Current Event 023 documentation says `launch_nuke` is a detonation effect and no installed documented effect starts a raid or assigns aircraft. Its accepted route waits for `on_nuke_drop`, exact state correlation, a stored nonce and native stock difference. Native callbacks do not echo Event 023's nonce or payload identity, so the current one-pending-request correlation remains a stated limitation.

All real detonation consequences must remain with the existing owner routes. Event 023 documents that it does not call Chaos, deaths, contamination, condemnation or Fallout again around native confirmation. A League strike must not add duplicate consequences simply to record diplomatic success or failure.

Native production and raid concepts distinguish atomic and thermonuclear weapons, but the inspected documented script surface does not expose independently measurable typed bomb stocks or exact-type refunds. Do not invent `num_of_nukes@thermonuclear_bomb` or an `add_nuclear_bombs` argument block.

The same sidecar says Event 076 currently has no identified nuclear inventory or custody provider. Its narrative ownership boundary must be respected, but the Gandhi spec cannot cite it as an already implemented exact stock API.

This evidence supports the accepted distributed-national-arsenal choice. Normal peaceful gameplay and earned nuclear diplomacy can proceed without depending on a pooled inventory. Borrowing, cross-owner dispatch and capture operationalization remain conditional on completing a verified owner service and its conservation evidence.

## 6. Capture, custody and peaceful disarmament

Current Event 023 documents and source distinguish physical custody, technical access, command formation and delivery integration. Native stock movement only follows completed exact-site capability stages and a proven prior native-custody removal.

The actual `sov_nuclear_bombs_operationalize_breakaway_site` source, beginning at line 1213, requires a registered site, transferred stock, no existing operationalization, no global custody dispute, a collapse-breakaway owner or controller, the native-custody-removed receipt, exact local command receipt, the holder's active delivery-stage mission for that same state, and actual delivery capability. It then moves the same cohort through the existing ledger. It does not grant Soviet technology or a new extra cohort.

This helper is explicitly tied to Soviet collapse and Event 023 provenance. Gandhi liberation cannot fabricate its `soviet_collapse_breakaway` authority or reuse Event 005 snapshot IDs merely to invoke it. New owner integration must be narrow and preserve exact current custody.

The current Event 023 document describes negotiated joint custody, return of devices, observed dismantlement and foreign removal assistance. Foreign assistance starts observed dismantlement in the physical holder's scope. It does not give the assisting major those devices. Losing the route can end the work. Joint custody blocks unilateral access stages.

The actual `sov_nuclear_bombs_mark_site_dismantled`, beginning at line 1656, moves existing intact site and actor allocation buckets into dismantled history and clears the site holder. Its body is not a general cross-country native-stock debit service. A caller still needs the owning transaction and physical/native proof. A Gandhi disarmament action must count only confirmed completed removal, never a promise, a renamed policy or an allocation-only reclassification.

For a member leaving the League, peaceful exit must preserve its real national stock unless it separately authorized a completed dismantlement contract. Withdrawal alone is not a reason to confiscate, duplicate or delete national devices.

## 7. Nuclear escalation and terminal ownership

Read current Event 023 sections covering native action, world threat, exchange and terminal behavior, and Event 032 sections covering payload consequences and shared ownership.

Event 023 contributes only `world_threat_source_sov_nuclear_bombs` to the shared aggregator. Terminal Fallout and Final Silence suppress its active source and invalidate new Event 023 actions. The first confirmed multi-major exchange has a nonterminal super-event distinct from Fallout. Its General Exchange stage never sets `world_end`.

Event 032 likewise states it never sets `world_end`. It submits confirmed physical consequences to existing owners and preserves the ownership of Event 023, Event 076, shared Fallout, Deaths, Air Cleanliness and Condemnation.

These current repository precedents align with the supplied current event skill. Gandhi's coercive ultimatum network, member split, defection and opposition war must remain playable before the terminal flag. A real nuclear exchange could independently activate the shared catastrophic terminal owner. Gandhi must not suppress that outcome to guarantee its own ending or set two terminal outcomes for the same world.

## 8. Zero resistance, zero compliance and zero useful occupation income

Fully read current primary mod sources:

- `common/occupation_laws/chaosx_occupation_laws.txt`
- `common/dynamic_modifiers/cbrn_occupation_dynamic_modifiers.txt`
- `common/scripted_effects/migration_presentation_effects.md`

The occupation-law file uses separate `state_modifier` and `suppressed_state_modifier` fields for resistance target, compliance gain, garrison requirements, local factories and local resources. The current dynamic modifier file documents that effects bind to the recorded responsible occupier and remove operational benefits immediately when control changes. It uses state lifecycle flags and separate state fields such as `local_factories`, `local_resources`, `resistance_target`, `resistance_growth` and `compliance_gain`.

The migration contract states that `local_non_core_manpower` is the percentage-style state field and that its flat `local_manpower` field is deliberately not used to represent a 0-to-1 population share. That distinction matters when designing zero recruitable benefit. Merely applying `local_manpower = -1` cannot be assumed to mean minus 100 percent.

These files prove relevant mod surfaces and owner-bound lifecycle precedents. They do not prove the requested complete invariant. No examined primary mod source establishes that:

- Setting resistance and compliance to zero removes all factories, resources and manpower yields.
- A single minus-100-percent modifier guarantees zero after all other native modifiers and occupation laws stack.
- An owner-bound state modifier affects only the intended current occupier in every owner/controller split.
- Zero compliance or resistance remains pinned while other shared systems and native growth update the state.

The Gandhi spec should retain the user's exact economic result, mark engine implementation as a required investigation, and define acceptance against actual useful yield. It should not weaken the demand to a large penalty or use population destruction, permanent factory removal or resource deletion as an unapproved substitute.

Required installed evidence includes the current occupation economy formula, modifier scopes and stacking, state holder/controller binding, resistance and compliance setting versus growth behavior, and final runtime checks with positive competing modifiers and a changed occupier. No such installed proof or live test was obtained here.
