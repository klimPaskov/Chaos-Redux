# 122 Gandhi, Part 13: Implementation and acceptance

The completed design is intended to become one coherent event with a worldwide opening and several earned political outcomes. Implementation should preserve its observable promises first: actual independence, exact noncooperation, voluntary membership, real national arsenals and a playable final conflict. A successful cinematic or an attractive category is not evidence that those promises work.

This part defines the implementation order, ownership boundaries and acceptance evidence. It does not claim that gameplay code, assets, MCP validation or live-game tests were produced during this planning task.

## Lifecycle model

The persistent model needs one global incident, a bounded holder registry, exact state cases, beneficiary generations, durable outcome receipts, member consent and obligations, one Gandhi identity and one route state. Those are bookkeeping records, not extra public currencies.

The opening follows these states: untriggered, preparing, active response, local refusal or settlement, finite campaign closing, and closed. The institution follows separate states: absent, founding, voluntary League, nuclear programme, Nuclear Pacifism, supreme congress, coercive campaign, stabilization, resolved or reformed.

These tracks can overlap only where the design allows. A League may exist before the initial noncooperation has faded. A supreme campaign cannot restart the original campaign. A terminal ending closes all unresolved Gandhi actions but preserves completed history.

Each scheduled action stores its incident, actor generation, target, due time and payment owner. When it executes, it revalidates those facts. A stale callback closes only its own record. It cannot clear a newer release plan or another country's current obligation.

## Performance and scheduling

Use one initial worldwide snapshot and scoped lifecycle hooks for later changes. After the snapshot, loops operate on Gandhi-owned actor, member, case, state, payment or treaty collections. Do not introduce a new daily, weekly or monthly scan of every world country.

Finite deadlines use scheduled events or existing scoped callbacks. Political reviews run only for registered institutions with outstanding work. A dormant peaceful legacy has no artificial crisis churn. The exact mechanism that pins active resistance and compliance must be supported by the installed engine and measured for cost.

The visible limits of eight strategic actions, three target cards and three concurrent missions are presentation limits. They never truncate the underlying global state list or omit countries. Target paging uses stable ordering and revalidation, with meaningful urgency first and the user's explicit selection retained where still valid.

The initial worldwide application must handle more than one thousand affected states without relying on a tool preview's default row limit. An implementation that processes only the first visible or returned batch is incomplete.

## Save, reload and repeated calls

Every irreversible result has an idempotent causal receipt. Reloading, acknowledging a report twice, receiving a duplicate native callback or reopening a decision category cannot repeat a release, device debit, reward or terminal transition.

Durability observation uses real elapsed intervals with invalidating hooks for war, lost sovereignty or broken commitments. A current peaceful snapshot cannot prove that an unobserved interval was peaceful. If a due checkpoint was missed, do not backfill evidence that the game never recorded.

Character custody, national stock, current owner/controller, native law and treaties are revalidated after reload. Temporary cached scopes are not treated as durable identity. A new country generation never inherits an old generation's pending payment or eligibility simply because the tag is reused.

## Evidence to collect

The future implementation record should distinguish parsed source, inspector output, probability analysis, rendered assets and actual runtime observations. Each check names the files or scenario, what passed, what remains uncertain and which owner must act.

For occupation denial, record useful yields before, during and after the effect under competing bonuses and changed control. For releases, record the exact frozen and committed footprint and failure recovery. For nuclear actions, record owner consent, law, before and after inventory, callback correlation and shared consequence receipts. For the ending, record the final all-country coverage and the shared terminal owner.

AI analysis begins with the actual source-derived candidate pool and legal gates. The future probability tool must compare named small-colony, large-empire, fascist, vulnerable-member, nuclear-owner and opposition scenarios. Do not present raw weights as already measured normalized probabilities. Simulation is useful only for a declared uncertainty. A sequence analysis requires a complete pool and real cadence.

Technology work requires the current technology inspect, render and compare workflow when its consumers change. Asset and focus renders require visual inspection of the actual consumers. No optional DLC route is marked supported because an unrelated older document once mentioned it.

## Completion boundary

Gameplay completion requires the core invariants and all reachable promised content. Optional pooled custody, custom 3D and frame animation are not required, because the accepted design does not depend on them. Real portraits, ordinary art, icons, flags where introduced, super-event assets and localisation are required for their visible consumers.

Unavailable HOI4 MCP or rendering tools are recorded as verification limits after bounded discovery and one useful retry where appropriate. Use relevant source inspection and local checks to complete unaffected work. Do not invent successful validation, wait indefinitely or ask the user to launch the game merely to finish ordinary implementation work.

Live game launch, debug-playtest and log review require their own explicit user invocation under the supplied workflow. This planning package does not request or claim them.

The final implementation report must state what changed, why, what was actually checked and which concrete limits remain. It must keep completed planning, completed implementation and observed runtime behavior distinct.
