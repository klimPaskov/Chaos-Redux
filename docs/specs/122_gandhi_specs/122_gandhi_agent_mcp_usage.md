## Common delegation contract

Every future project custom subagent receives a self-contained prompt with no inherited parent-thread context. In Codex, use `collaboration.spawn_agent` with `fork_turns="none"`; follow the runtime's documented mechanism in other environments. The prompt must contain the event identity and alias cautions, accepted package sections, exact allowed files, forbidden surfaces, the concrete question or change, source paths already established, previous attempts and findings, dependencies, required checks, and one named handoff destination. Do not ask the agent to reconstruct missing decisions from conversation history.

The exact file allowlist comes from the current repository audit before delegation. Surface classes named below describe ownership and do not claim that an uninspected file exists. An agent may patch only within its role and the explicit allowlist. Shared helpers with multiple consumers need a parent-reviewed caller and compatibility plan. Unclear ownership returns to the parent before a broad edit.

Each handoff belongs under docs/plans/122_gandhi_plans/subagent_handoffs and records the accepted basis, files inspected or changed, evidence with source revision or hash, findings resolved, remaining limits, previous failed tool attempts, and dependencies. A handoff must distinguish implemented behavior, source inference, measured behavior, and work still proposed. It must not treat unavailable optional tooling as a confirmed gameplay defect.

The parent reviews each handoff and the relevant actual source once, then rechecks real fixes. It does not commission repeated audits of unchanged findings. If delegation is unavailable, the parent may use the same checklist within its own authority and identify itself as the reviewer. It must not fabricate an independent specialist review when one is required.

## MCP execution policy and current route inventory

The current service is hoi4-agent-tools, exposed to coding agents through the mcp__hoi4_agent_tools__hoi4_* family. The dotted names below are documentation names. Confirm the connected tool list and live schemas before constructing arguments. Their appearance in source documentation does not prove that the service, optional task transport, or a standalone viewer is available in the next session.

All HOI4 routes below are **not invoked in this planning task**. They are future implementation or review routes. A successful ordinary read-only domain call is sufficient evidence that that route works. Reuse unchanged schema discovery rather than repeatedly probing health.

For any underlying failure or unsupported analysis, permit the initial read-only request and at most one corrected or narrower retry. Skip the retry when unavailable or when no useful correction exists. This limit follows the same cause across files, scenarios, tool names, agents, and resumed turns. A renamed request or status poll does not reset it. New information that fixes the cause can justify a new check. Record attempts and the condition for retry once in the existing handoff, then use available local references and source checks. A confirmed code defect still requires correction and a relevant recheck.

Before retrying an uncertain write, inspect actual source or transaction state. Successful MCP output covers its returned checks and scope. It does not establish live engine behavior. Missing optional MCP evidence does not prevent source implementation from being completed honestly.
