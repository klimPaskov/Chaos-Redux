# Acceptance and validation

## Status and test method

All 97 scenarios in this file are planned acceptance cases. No game source was implemented, no HOI4 MCP scenario ran, and no live game or save was tested in this planning turn or its continuation. The authored specification is reviewed design. The proposed numeric anchors are not measured balance results. The continuation added 14 bounded cases for concrete issues found during complete selected-source reading; these are requirements for later implementation validation, not claims of executed tests.

The implementation owner must create reproducible fixtures with real source identities, current country and state IDs, actual cohort records and exact owner contracts. Preserve starting and ending values, authority and charter versions, receipt identities, source paths, tool output and unresolved findings. Use bounded script or native-tool verification where possible. Live observations supplied later must be labeled with their actual run count and scope.

The following table defines what success means without inventing engine syntax. A scenario passes only if its authoritative owners agree. A plausible popup, an attractive render or a successful effect call does not prove population conservation, current military capability or correct settlement.

## Completion evidence and stop conditions

Implementation completion requires the accepted core, all six prompts, seven achievements, two super-event families, all five authored contexts, the shared civilian extension and every relevant scenario to be accounted for. A case can be not applicable only with a source-grounded reason that does not remove an accepted feature. A blocked case must name the missing owner, reference, capability or evidence.

Use ordinary repository validation for touched files, required MCP evidence from `mcp_usage_map.md`, specialist audits and final parent review. Run additional checks only to resolve a concrete risk or satisfy a required gate. Do not pad the report with repeated superficial checks. A clean static parse is useful evidence but does not establish native balance, civilian accounting or visual correctness.

Near completion, the improvement-loop planner must return a bounded addendum or closure. Record each proposal as incorporated, deferred with a material blocker, or rejected with a reason. Resolve all accepted work before claiming the full implementation complete. The event-completion auditor then compares actual implementation against this package, its accepted additions and the evidence ledger. The final report must distinguish implemented behavior, verified behavior, untested behavior and blocked work.
