## Findings and final dispositions

### C105-01: Define evolution-history frequency and first-entry behavior

The initial draft defined quantities and evolved openings but left the separate evolution-history frequency implicit.
It did not determine whether repeated Storm firings created repeated evolution rows or whether a first firing at Storm implied earlier unobserved stages.
Current events guidance requires explicit shared evolution context and distinguishes logged history from preview catalogs.

**Disposition: Promoted into an accepted spec.**
The parent accepted a first-actual-use record for each evolution stage, at most once per campaign.
S2's Evolution history now records only the stage actually dispatched, preserves later real lower-stage first use, and excludes previews, all-recipient empty pools, and failure before any dispatch begins.
The phrase before any dispatch begins replaces the ambiguous earlier phrase before all dispatches.
V1's e105_evolution_history now covers repeated Storm, no fabricated lower stages, a later real lower stage, later dispatch failure, and settings changes while retaining the frozen stage.

**Remaining implementation proof:** Establish the first-use record at the real dispatch boundary with the correct actorless shared context and once-only receipt.
A callback that changes settings must not erase or relabel a stage already used under the saved permissions.
This is a named implementation obligation, not an unresolved quantity design.

### C105-02: Complete the Subagent Usage Map contracts

The initial role table provided canonical names and useful summaries but omitted several fields explicitly required by Protocol section 12.
Those fields included the assigned inputs, owned surfaces, forbidden writes, dependency timing, and parent follow-up.

**Disposition: Promoted into an accepted spec.**
V1 now includes Role execution contracts with common accepted inputs, current source paths and revisions to provide in each assignment, the handoff directory, allowed and forbidden work by role, ordering, and parent review.
The original canonical-role table supplies the role identities and distinguishes actual planning work from later implementation assignments.
T1 supplies the planned exact event and shared integration surfaces.
The two maps together provide the delegation structure without pretending that unavailable implementation source has already been inspected.

**Remaining implementation proof:** Each new assignment must resolve its exact current allowed files and named handoff destination before the worker acts.
The architect and auditors may not acquire broader write authority from a generic role description.
The parent reviews actual source and required MCP evidence after each relevant handoff.

### C105-03: Complete MCP ordering and follow-up ownership

The initial MCP table named routes and useful outputs but left the per-route order, owner, and blocking follow-up implicit.
Protocol section 13 requires those execution details in an unavailable-tool planning handoff.

**Disposition: Promoted into an accepted spec.**
V1 now contains MCP ordering and follow-up ownership, paired with its detailed route table and named scenario matrices.
The additions identify preceding state, owning reviewer, required correction, source and scenario identity, coverage limits, and the distinction between an absent route and an unhealthy reachable service.
The map preserves mandatory matched source comparisons and refuses to use a cached analysis ID as a substitute for actual before-source evidence.

**Remaining implementation proof:** Discover real exposed routes and schemas in the coding environment, then obtain the prescribed evidence for the actual source and complete pool.
This reviewer observed zero exposed tool names or descriptions matching HOI4 or Hearts of Iron during the final audit.
No MCP inspection, probability analysis, render, comparison, or native engine execution was performed by this audit.

### C105-04: Choose the military achievement's war before freezing its target

The initial Improvised Victory table selected the largest enemy major from the enrolled war without specifying how the war was chosen when the player fought several qualifying wars.
That ambiguity could change the achievement target and disqualification context between implementations.

**Disposition: Promoted into an accepted spec.**
The parent accepted selection from enemy-major and war pairs across active wars that meet the no-other-major condition.
S3 now ranks the enemy's owned civilian plus military factory building levels, breaks equal enemy scores by verified stable country order, and uses verified stable war order only if a same-enemy and multiple-war tie is actually supported.
Both identities freeze for the attempt.
S3 explicitly permits a proven native invariant that makes the last tie impossible instead of inventing a war-order API.
The building measure excludes dockyards and off-map capacity and reuses the industrial achievement's documented measure.
V1 adds e105_victory_multiwar.

**Remaining implementation proof:** Verify war identity, pair membership, deterministic ordering, native participation, capitulation credit, war continuity, and authoritative major-ally transitions.
An approximate country predicate or periodic snapshot cannot replace those conditions without a separately accepted change.

### C105-05: Preserve captured-country identity through same-tag recreation

The written country lifecycle contract already prevents grants to newly created countries and forbids redirecting work to unrelated scopes.
The audit identified same-tag destruction and recreation as a concrete fixture needed to prove that contract.

**Disposition: Covered by the existing accepted design and promoted into its acceptance scenarios.**
V1 now includes e105_country_recreation.
Matching tag text alone cannot attach the destroyed country's pending work or historical receipts to an unrelated new country.
This addition introduces no new lifecycle mechanic or extra recipient filter.
