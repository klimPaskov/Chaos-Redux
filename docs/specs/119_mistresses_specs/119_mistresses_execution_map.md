# Mistresses: execution map and evidence handoff

## Build the crisis through shared, testable contracts

Implementation should first establish the saved identities, population accounting, country continuation and phase boundaries that make the crisis coherent. Screening, country packages, assets and presentation can then proceed on distinct owned surfaces. Shared integration remains with the parent implementation owner so that several workers do not independently edit the same registry, event log or world-end gate.

The output of this session is the multipart design specification and its handoff material. No production event code, final localisation, portrait collection, Meshy job, Blender export or live game session was performed. Proposed paths below are ownership boundaries for future work, not claims that those files already exist.

## Actual role use and future native roles

This design stage used separate screening, country and systems specialists alongside the parent coordinator. They adapted the supplied role contracts. The systems specialist followed `chaosx-scripted-system-architect.md` and its required sources. The configured native Claude profile was not instantiated here. A role definition in the uploaded configuration is evidence of its intended contract, not evidence of an available process, model, MCP connection or completed audit.

The implementation coordinator should create fresh, self-contained tasks. Each prompt names the precise design chapters, source revisions, owned paths, expected positive output, available tools, current blockers and the next recipient. It includes the current AGENTS and relevant skill obligations. Workers reread their own current role definition before acting. No worker is asked to infer requirements from another worker's private context. [E1] [E2]

The team completed the supplied 151-source reading gate before drafting. This systems specialist personally completed all assigned integration-related skills and references plus eight targeted repository files. The repository reading receipt records exact paths and SHA-256 hashes. The public repository was inspected at commit `41bc4e5045a7b5c131be69dda2f08079d478634c`, dated 18 October 2026. Newer user instructions and current supplied contracts take precedence where that source differs.

Preparation may be partitioned. An irreversible revolt cannot be spread over ordinary daily play in a way that gives early countries an advantage. Part 5's same-hour narrative and Part 10's logical transaction require a verified dispatch boundary. If the engine cannot deliver that result, report the specific blocking capability rather than rename sequential daily effects as simultaneous.

## Required checks, limited to concrete questions

### Reference and native capability gate

Before engine-facing edits, read the relevant offline wiki sections and installed documentation through the connected reference tools or directly from the pertinent local files. Keep source path, relevant line span and revision. Read the returned text. A reference list alone is not a completed read. Check exact vanilla definitions and overrides with `source_lookup`. Installed documentation resolves version-specific syntax. Do not substitute remembered commands or public wiki snippets for the project's installed reference workflow. [E1]

Prioritise these unresolved questions: exact civilian measurement and rounding, service-partner casualty removal, valid land/capital creation, unit manpower and equipment charging, weighted surviving-unit measurement, annexation inheritance, research exclusions and progress, character and focus reward preservation, multiplayer continuation, and the shared world-end suppression route. Helpers may organise supported native effects. They cannot create engine capabilities that do not exist.

### Static and visual checks

Inspect only the event graph, routes, categories, helper bodies and registries changed by the implementation. Use explicit scopes. Report `script_validate` coverage and checks performed without presenting them as a live-engine proof.

For the screening GUI, retain matching before and after scenarios at 1920×1080 scale 1, 1366×768 scale 1 and 2560×1440 scale 1. Add scale 1.25 only when the installed native setting supports it. Cover first admission, ordinary and selected cases, method selection, active investigation, depleted resources, no free slot, compromised source, stale authority, purge confirmation, empty/archive, crowded long names, disclosure, transaction lock, successor host and aftermath.

Inspect full window, relevant crops, hierarchy, text overflow and click regions. Use native scrolling rather than shrinking text. There is no assumed separate GUI comparison tool. Use preserved baseline artifacts and the render route's documented comparison capability. A visible defect in an available production render must be corrected and rechecked. Unavailable rendering permits a source review with an explicit gap, not a fabricated visual pass. [E2]

### Probability and balance checks

Begin with named scenarios and intended ordering. Examples include strong evidence versus uncorroborated accusation, low resources versus a staffed response, compromised versus independent reports, local survival versus foreign placement, and different adult force compositions in a merger. Use `probability_inspect` for the scenario matrix. Use sweeps for actual threshold or rank-reversal questions and compare after implementation.

Simulation requires declared uncertain inputs. Sequence analysis requires the complete custom pool, cadence and state transitions. Do not turn AI scores into exact selection probabilities when the candidate set is incomplete. The blinded screening evaluation specified in Part 3 is a substantive quality gate, not a substitute for deterministic replay and native action checks. [E3]

### Runtime, save and DLC checks

The debug-playtest skill is explicit-invocation-only. No live launch is authorised by this design request. Future autonomous live QA requires the user's explicit request and the correct supported process route. Windows tests use HOI4 Live Tools. Linux tests require the exact reviewed ELF build and lease, and only currently verified Clausewitz operations. A Windows result does not validate a Linux process. No raw desktop fallback or guessed memory operation is permitted. [E4]

For supplied text saves, use the read-only inspector's info, keys, get, find, flatten, diff and footprint operations narrowly. Capture before and after evidence for actual population, deaths, reserves, stockpile, units, research, rewards, ownership, transaction receipts and public values. A save remains evidence of one run. It does not prove a probability distribution. Binary saves are not silently rewritten or decoded with an invented token table. [E5]

The compatibility matrix includes no DLC, each DLC directly used by an implemented feature, and the full supported combination. Resolve the exact DLC names and feature gates from the installed reference audit. Core investigation, civilian accounting, uprising, playable war and continuation must work without optional DLC. Optional mechanics receive documented alternate routes where required. Do not report compatibility merely because a file parsed or a DLC-specific command was hidden.

### Proportional retry and completion policy

Use one initial attempt and at most one corrected, narrower attempt for the same underlying tool failure, shared across agents and resumed work. Do not reset the allowance by changing the caller. An absent tool is not an invitation to repeatedly probe guessed names. After the bounded attempt, use available direct source evidence and identify the specific unavailable check. Do not repair tooling or broaden into an unrelated environment project. [E1]

Broaden a check only to resolve a concrete uncertainty or required gate. Confirmed defects are corrected and rechecked. Once the named scenario is sufficiently evidenced, continue to the next dependency. Do not spend repeated runs reproducing a known limitation or claim optional analysis is mandatory for a small reversible edit.

## Completion package

The implementation handoff should include the changed path list, migration decisions, exact reserved identities, installed engine and DLC revision, asset manifests, transaction and case schemas, named scenario inputs, actual results and remaining blockers. Separate source review, render, static validation, live observation and save comparison in the evidence matrix.

Part 10 provides the conservation and lifecycle acceptance cases. Parts 3 and 9 provide screening and presentation cases. Parts 6 to 8 provide country, focus and Mother objectives. The completion auditor checks the assembled result against all of them. The spreadsheet worker records the resulting implementation status after that evidence exists.

Current completed work is the reviewed design and targeted source analysis. Current unexecuted gates are installed reference validation, namespace-content migration audit, production asset creation, native transaction and multiplayer feasibility, GUI rendering, runtime save/reload, and the DLC matrix. Those are concrete future dependencies. They do not prevent this design handoff from being complete.
