# Manual Role-Equivalent Subagent Reviews

## Process status

The custom Chaos Redux subagent runtime was not available in this environment. No project subagent was actually spawned. To avoid silently skipping the specialist perspectives required by the source skills, the planning package received the role-equivalent reviews below.

These reviews are planning evidence, not substitutes for the real implementation-time agents. The implementation prompt requires the actual subagents with `fork_context=false` when the runtime is available.

## Repo Explorer role

### Findings

- Current public Event 19 is a small fixed infantry spawn loop.
- The event has no current public decision, evolution, claimant, AI, derivative-country, or canonical event-doc layer.
- Parent zombie and Death systems use identity and progression triggers that make derivative isolation a primary risk.
- The final local repository must determine exact file paths, helper availability, unit identifiers, and safe dynamic-country precedent.

### Design response

- A full touched-surface map is included in `research/repository_context.md`.
- Local verification gates are carried into the coding prompt.
- The plan does not invent final script identifiers for unknown golem or helicopter definitions.

## Scripted System Architect role

### Findings

Repeated and dynamic logic clearly needs reusable systems.

### Proposed helper architecture

- generation and formation-lot creation helper
- diminishing state-coverage helper
- state-weighted formation-family selector
- equipment and manpower accounting helper
- event-owned audit lock and closeout helper
- random battalion and support generator
- claimant creation, demand, loyalty, and revolt helpers
- Chaos unit family registry
- derivative-country origin and parent-isolation helpers
- selected-lot GUI helper
- cleanup and migration helpers

### Constants

Central tuning categories are mapped in Part 7 and the spawn matrix.

### Event targets and cleanup

- short-lived generation, lot, claimant, and former-parent pointers should use the narrowest safe event-target scope
- global targets are used only where persistence truly exceeds one chain
- every global target requires explicit cleanup
- no-actor evolution records rely on the shared Event Log contract

### Implementation boundary

The planning package does not prescribe exact scripted-effect syntax. The local architect must verify existing helpers and avoid duplicate systems.

## Decision and Mission Auditor role

### Findings

The event would become an exploit-prone store if unit requests used only political power or if every weak lot could be instantly disbanded.

### Design response

- costs use equipment, trains, fuel, manpower, army experience, construction, supply, and political burdens that fit the action
- requests pay before the reveal
- repeated requests escalate cost and risk
- missions have objectives, dynamic duration, success, failure, and partial success where useful
- selected-lot management prevents category clutter
- delayed partial salvage prevents equipment farming
- GUI buttons call shared decision logic

### Remaining implementation audit needs

- exact cost balance
- mission duplication
- stale target cleanup
- AI target safety
- request and demobilization exploit tests

## Country Package Auditor role

### Findings

Zombie, ghost, and golem revolt states cannot be implemented as cosmetic tags with free armies.

### Design response

Every derivative package includes:

- origin and family identity
- coherent territory
- actual revolting starting units
- leader or council
- flags
- politics
- idea lifecycles
- supply and economy
- reinforcement
- focus-scale routes
- decisions
- AI
- expansion and integration
- defeat cleanup
- parent isolation
- shared special and nonhuman classification

### Blocking local checks

- safe dynamic-country pattern
- final golem identifiers
- state-transfer and existing civil-war safety
- portrait and name-pool helpers
- starting technology and equipment setup

## Focus Tree Auditor role

### Findings

A one-line fixed-purpose tree would be too shallow, while a separate bespoke tree for every regional derivative would be excessive.

### Design response

- one shared architecture with strongly adapted zombie, ghost, and golem modules
- roughly 25 to 35 focuses or equivalent route depth
- survival, hierarchy, sustainment, military method, former-parent war, expansion, integration, family transformation, and regional capstone
- route-specific AI, assets, leader state, and idea lifecycles
- no world-end capstone

### Audit need

The actual tree must receive a route coverage table and focus-level reward, icon, localisation, layout, and AI review.

## Localisation Auditor role

### Findings

Planning labels could be mistaken for pasteable localisation.

### Design response

- working labels are repeatedly marked as non-final
- the spec provides viewpoint, information, tone, and avoidance direction rather than final copy
- Event Details is separated from mechanical effect text
- cost and requirement text must be dynamic and clear
- claimant names use regional and gender-matched pools
- no unresearched quote, lyric, or cultural line is supplied

### Implementation audit need

Check missing keys, duplicate keys, BOM encoding, dynamic-value formatting, raw triggers, regional tone, and cross-surface wording after script exists.

## Generated Event Art role

### Findings

The event’s scenes, claimants, derivative leaders, flags, and GUI art are fictional or supernatural.

### Design response

- generated art is the default source mode
- report scenes use period-documentary direction and project card processing
- 20 static claimant portraits are fully slotted
- derivative flags and leaders are distinct from parent systems
- no generated real person is requested

## Icon Artist role

### Findings

The system needs a large coordinated icon family and three useful animations.

### Design response

- decision, idea, focus, and achievement icons remain separate asset types
- only state-communicating UI elements animate
- all three animations require real source frames and static fallbacks
- every derivative focus needs icon coverage after the final focus list is fixed

## Asset Source Researcher role

### Finding

No real leader portrait, historical flag, or real photographed event is required by the accepted design.

### Disposition

No sourced visual asset package is requested. This role becomes necessary only if implementation adds a real person or attested historical symbol.

## Super-Event Text and Audio Research roles

### Finding

The ordinary event, evolutions, and triggerable scenario do not meet the project threshold for a campaign-defining super-event.

### Disposition

No quote, remark, audio, or super-event image research package is requested. See `super_event_scope_decision.md`.

## Spreadsheet Worker role

### Finding

The catalog row cannot be updated accurately until final in-game Event Details, evolution, and scenario wording exists.

### Disposition

The planning package identifies required row changes but does not edit the workbook. After implementation, the spreadsheet worker must mirror exact final localisation and preserve workbook structure.

## Documentation Curator role

### Findings

Event 19 needs one source-of-truth spec pack, one canonical event doc after implementation, and explicit plan dispositions.

### Design response

- this folder is the source spec area
- there is no loose unresolved improvement addendum in this package
- future implementation handoffs belong under `docs/plans/019_infantry_spawn_plans/`
- accepted implementation changes should be reconciled back into the spec if they alter design

## Skill Maintainer role

### Finding

The proposed Chaos unit registry may become a reusable project convention.

### Disposition

Do not update a skill before implementation proves the registry shape. After implementation, use the skill maintainer to decide whether registry onboarding and parent-isolation checks belong in `chaos-redux-events`, a dynamic-unit skill, or documentation only.

## Event Completion Auditor role

### Findings

The specification covers the user’s requested baseline, four evolutions, generals, derivative countries, and scenario. Completion risk is concentrated in assets, AI, parent isolation, dynamic-country creation, and catalog alignment.

### Disposition

A planning completion audit appears in `spec_completion_audit.md`. A real implementation completion audit remains mandatory.
