# Event 021 ordinary-successor external-war relations addendum

Date: 2026-09-25

Status: accepted design; source path implemented, with focused engine and runtime verification still pending.

## Acceptance basis

The user explicitly approved a relation-only fallback with “Approve relation-only fallback,” then authorized replacement declarations with “Allow new declarations; I will choose goals case by case.” The user selected an in-game prompt for each missing relation with AI successors failing closed, and reaffirmed that “everything must still be dynamic.”

## Accepted behavior

The engine cannot establish that a successor continues the exact same named external war after its predecessor is annexed. Event 021 therefore preserves or restores only the successor-to-opponent war relation; a replacement declaration is a new war and must never be described as continuity of the old war identity or goal.

Before ordinary-successor annexation, Event 021 records the predecessor's live external enemy countries on the successor, excluding the successor itself and active same-crisis fronts. The list and number of records are derived from the current campaign state, not fixed country tags or a fixed enemy count.

After successor adoption, Event 021 rechecks each recorded opponent. Existing relations require no action. Missing, invalid, annexed, or undeclarable opponents fail closed. A human-controlled successor receives a standard event prompt for one still-valid opponent at a time. The event identifies that opponent from the live queue and exposes only war-goal choices valid under current state, plus a choice to decline. The player makes a separate choice for each opponent. AI successors make no automatic declarations.

Any chosen replacement declaration is revalidated immediately before use against the live successor, its current crisis receipt, its current queued opponent scope, current relation, current core or claim control, and declaration eligibility. The prompt's crisis ID and opponent scope are stored as successor-local variables rather than a regular event target, so an asynchronous choice is bound to a durable country-local receipt instead of an effect-chain pointer. Queue state is stored on the successor and cleared on completion, decline, invalidation, terminal cleanup, or annex cleanup; an already-open prompt keeps only its own quarantine receipt until its choice or default close resolves, and its effects fail closed after the queue or crisis receipt becomes invalid. An unrelated opening rollback preserves a still-valid pre-adoption snapshot or post-adoption queue and clears invalid receipts. While any snapshot, queue, or prompt receipt is live, that country is dynamically excluded from automatic target selection, recurrence windows, Critical launches through the shared target predicate, and manual-scenario candidate selection. The same bounded country-local target refresh runs when the snapshot hold begins and when the queue clears, so live target weight and the aggregate target count follow the current eligible pool without a fixed timeout. Save/load behavior and stale open prompts across crisis rollover remain runtime test cases and are not claimed as proven.

An unrelated opening rollback preserves a pre-adoption snapshot only while the live successor-roster and government-role adoption receipts are pending and the successor/crisis identity still matches. After adoption, preservation instead requires the full post-adoption queue receipt; stale receipts are cleared. A cluster reservation encountered during a live queue is released and logged as continuity-pending without entering target preparation. Scenario, transaction, and final-plan checks continue to use live queue state, and membership refresh follows the final receipt state.

Every opponent is collected from live enemy-country scopes into a dynamic array with no country-tag roster or fixed enemy limit. The prompt resolves the current opponent name from its country-local saved scope for valid declaration choices, and its core and claim choices appear only when the current opponent owns and controls a matching state. Invalid or recovered targets are skipped. Dispatch is the sole writer of the country-local prompt receipt and sets the in-flight flag before it fires the event; later dispatch attempts stop while that flag remains set, and queue cleanup preserves the open prompt's crisis and opponent receipt. This one-slot quarantine means a later same-opponent crisis cannot queue over an unresolved prompt through normal Event 021 paths; after the old prompt resolves or default-closes, a later crisis may be selected and receive a newly evaluated prompt. The event-level visibility gate permits an in-flight stale prompt to resolve safely. Choice visibility is evaluated when the event opens, so an option already visible before a later annexation may remain on the open card; its effect rechecks the live crisis, queue head, opponent, relation, and territory before declaring and otherwise advances without declaring. Annex teardown clears the queue and snapshot receipts, preserves both prompt fields only while a prompt is in flight, and clears the prompt opponent pointer when no prompt is active. Whether the engine retains and later delivers the popup across annexation and tag release remains a required runtime test, not a proven source-level guarantee. The shared opening transaction and final opening-plan validation both recheck the live queue receipt, so an earlier cluster or scenario reservation cannot bypass it. Rollback clears reservation and scenario receipts before its country-local pool refresh, keeping live weight and candidate count aligned with the final eligibility state.

The Event 006 adapter's package IDs remain an authored content crosswalk for complete packages, not a fixed live-country eligibility roster. Selection reads the initialized package array's current `^num`, normalizes a persistent cursor to that live count, and scans no more than the current number of registered package rows. Each candidate still passes the live host, anchor, ownership, control, reservation, conflict, and carrier-preflight checks before admission; a rotating cursor prevents registry order from permanently favoring the first valid package.

This fallback does not alter Event 006 fire history, repeatable weight, cap, evolution history, package identity, or league enrollment. It does not create a new Event 006 package or change Event 021 settlement and front identity rules.
