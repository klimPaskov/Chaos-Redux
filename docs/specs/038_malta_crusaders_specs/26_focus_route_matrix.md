# Focus route implementation matrix

## Purpose

This matrix converts the architecture in `06_focus_tree_architecture.md` into auditable route coverage. Working labels guide implementation and are not final localisation. Exact focus IDs, coordinates, and node counts belong to the implementation pass after local vanilla and MCP inspection.

The tree must open with a small readable group, then reveal the major branch families through control, route state, and campaign pressure. Every visible focus needs one primary branch home or a deliberate convergence role.

## Architecture and lane requirements

The normal visible tree should reserve clear lanes for:

1. opening survival and command
2. order politics and government
3. Holy Land and regional campaigns
4. Mediterranean logistics and naval development
5. custom military development
6. principality and settlement policy
7. Church and Crown
8. failure and comeback content when revealed
9. high-Chaos or hidden content only after its reveal proof

The Eleventh Crusade branch must appear as a crisis route without crossing ordinary connectors. Hidden Teutonic, Atlantis, and Holy World content must not leak through focus icons, navigation labels, requirements, search filters, or empty branch space before reveal.

## Focus Navigation plan

Use Focus Navigation for spatially separate branch families after local vanilla inspection. The initial navigation set should include:

- Command and Survival
- Military Orders
- Holy Land Campaigns
- Mediterranean Network
- Church and Crown
- Principalities
- Eleventh Crusade, only when revealed
- Holy World, only when revealed

Tiny order subbranches do not need separate navigation buttons. Their icons and lane position should make them readable inside the Military Orders region.

## Focus inlay contract

The Crusade Council is important enough for a focus inlay only if local vanilla and MCP evidence shows the panel can fit without obscuring nodes, connectors, navigation, filters, or continuous focuses. The inlay may show the three public values, the dominant order, one active demand, and one short route status. It must not reproduce the full mechanic window.

If the inlay cannot pass the supported-resolution layout review, retain the separate mechanic window and use focus tooltips plus one compact status element. This is a presentation choice, not a gameplay fallback.

## Route coverage acceptance

Implementation must produce a route coverage table that maps every row above to final focus IDs, decisions, country changes, AI plans, icons, and validation evidence. A merged route must preserve every mechanic and outcome in the affected rows. Renaming alone does not count as omission, but silent removal does.
