# Implementation, subagent and MCP usage maps

## 1. How this handoff is used

Parts 01 through 07 contain the imported design; Part 00 identifies which elements are grounded in the brief or expressly preserved and which additions still need parent disposition.
Part 08 defines the records and transaction boundaries needed to preserve it.
This file assigns future implementation work and evidence without claiming that those operations have already happened.
Part 12 distinguishes the repository sources inspected during planning from installed-engine and native validation still required.

The implementation parent owns integration, accepted scope, shared systems, actual source review and final completion claims.
Specialists work on bounded surfaces under the supplied canonical role definitions.
They receive explicit inputs and constraints with `fork_turns="none"`.
A specialist's report is evidence to inspect, not automatic permission to overwrite another worker's files or declare the feature complete.

Do not edit repository-backed source from this ZIP as if it were already implemented code.
Install this folder under `docs/specs/108_wrestling_tournament_specs/` and use `docs/plans/108_wrestling_tournament_plans/` for work plans, native evidence indexes, audits and accepted-change dispositions.
Fold accepted design changes into the numbered specs so the next worker does not inherit contradictory addenda.

## 8. Completion standard

The implementation is complete when currently accepted requirements, source, assets, final text, shared integration and documentation agree. Use native evidence when a relevant route is available and useful; otherwise use direct source review and meaningful local checks, and report material limits.
The completion report must distinguish implemented behavior, historical receipts, unresolved imported design proposals, provisional source placeholders and unavailable checks.
It must not call a static diagram a live bracket, a probability formula a native audit, a source URL a produced portrait, or a globally stored date an executing scheduler.

The current improvement-loop skill and the parent implementation plan govern the bounded depth review.
Resolve each proposed addendum within its acceptance scope or record it as queued, rejected, superseded or unresolved with the proper basis.
Keep iterating until the full currently accepted goal is satisfied.
No accepted requirement or hidden partial implementation can be reported as finished.
