# Event 056: Repeats and Evolutions

## Repeat design

The first firing is the world-changing naval shock. Later firings should still matter, but they cannot repeat the first grant at full scale forever.

Each country tracks its own receipt count. A country that was landlocked during two earlier global firings still receives a first-scale package when it finally qualifies. A country that already received three packages uses the fourth-receipt scale even if it changed government or lost its earlier ships.

This keeps repeat scaling tied to the recipient's history rather than the total number of global firings.

## Recipient scale by receipt count

The following values are planning targets for the package budget before global normalization:

| Package received by the country | Baseline local scale | Design role |
| --- | ---: | --- |
| First | 100 percent | Full manifestation and strongest local shock |
| Second | 75 percent | Major reinforcement or a second fleet identity |
| Third | 55 percent | Significant addition without repeating first-firing growth |
| Fourth and later | 40 percent | Bounded reserve or specialist addition |

Evolution I can raise the fourth-and-later floor to 50 percent because the evolved package pool is meant to become larger and stranger. This increase applies only while Evolution I is active. Global limits still take priority.

These values should be centralized and tuned after real package inspection. The relative shape is more important than the exact percentages.

## Repeat identity rules

Every repeat performs a fresh package roll.

A country may receive the same identity again. Duplicate identity is allowed because an oversized concentration can be part of the event's chaos. A soft local variety preference can slightly reduce an immediate exact repeat when several legal identities exist, but it must never guarantee a new identity or choose a strategically useful replacement.

The event remembers the package identities needed for history and achievements. It does not forbid the player from reorganizing all granted ships into one navy.

## Repeat support scaling

Convoys, aircraft, fuel, repair support, and emergency port assistance decline with the same broad receipt scale as combat hulls.

Minimum functional support remains protected:

- a carrier package still needs a credible air group and screen
- an invasion package still needs meaningful transport capacity
- a convoy package still needs a substantial convoy grant
- a no-port recipient still needs the minimum emergency facility

Support above that minimum is reduced first when a repeat is compressed.

## Cohort memory

Each firing creates a bounded grant cohort for every recipient. The cohort stores enough information to answer later questions:

- which firing created the package
- which package identity was rolled
- which defining ships were delivered
- which commissioning choice was used
- whether delivery was full, phased, converted, partial, or cancelled
- which ships still count for achievement conditions

Cohort memory must not grow into a permanent record for every individual escort. Where the engine permits, ships can carry a compact origin marker and the country can retain aggregated cohort facts. Destroyed or deleted ships should stop counting without leaving active processing work.

## Repeat anti-farming rules

### No conversion profit loop

Break Up the Package returns less practical value than using the ships. Repeatedly choosing breakup cannot become a source of superior fuel, convoys, or naval experience.

The conversion amount scales from actually removed package value. It is capped by receipt count and package identity. Support that was already part of the original package cannot be counted twice.

### No delayed duplication

A phased package reserves its second tranche once. The follow-up has a delivered or cancelled proof. Reopening the event, changing tags, losing a port, or saving and reloading cannot create a second copy.

### No identity reroll through player choice

The package identity is locked before the personal report. The player chooses how to commission the rolled fleet, not whether to reroll it.

### No intentional port invalidation reward

Losing or abandoning the commissioning port can trigger one safe re-selection for a delayed tranche. It does not create extra support or a new fleet.

### No repeat reset through cosmetic change

Cosmetic tags, ideology changes, and ordinary government changes do not reset receipt count or cohort history.

A true country replacement or annexation follows the owning event and country-history rules. It does not automatically transfer a fresh Event 56 entitlement.

## Evolution pacing

The three evolutions unlock from Chaos thresholds, but an active campaign does not need to transform at the exact instant the meter crosses a threshold.

For a campaign where Event 56 has already manifested, each evolution should activate through the normal evolution pacing system after its threshold becomes valid. The base pace should be substantial enough that the change feels like a new phase rather than an immediate hidden switch. Around ninety days is an appropriate starting scale before dynamic factors.

For a campaign where the threshold is already met before Event 56 first fires, the initial firing can use the corresponding evolved package pool. The evolution still needs its proper enabled state and Event Log treatment.

Evolution activation gives zero Chaos. Chaos changes occur only when an evolved package produces a concrete first delivery milestone defined in the Chaos impact map.

## Evolution I: Larger and Stranger Fleets

### Requirement

- Chaos: 200 or higher

### Design purpose

The ordinary fleet identities expand into stronger extremes. The world can receive larger destroyer masses, deeper convoy reserves, unusually dense submarine forces, carrier concentrations, or fleets centered on several major capital ships.

### Package changes

- unlock the Extreme size band
- increase the chance that one ship family dominates its package
- allow broader differences between defining ships and support ships
- raise the late-repeat floor from 40 percent to 50 percent while the evolution is active
- permit more severe port congestion and fuel burden, with clear reporting
- preserve the global entity budget

### Identity examples

- submarine package with very little surface support
- destroyer fleet split into several escort and patrol groups
- convoy package with enough transports to change a country's overseas capacity
- carrier package with several carriers and a complete screen
- capital package built around a small group of major ships

These are composition directions. They do not become fixed named variants that must appear once each.

### Active-event entry

When the evolution activates after an earlier firing, it changes future package rolls only. It does not add ships to existing fleets.

Existing recipients can see the evolution in Event Details and the evolution history. Their current granted ships remain unchanged.

### Pre-fire entry

When Event 56 first fires after Evolution I is already active, every eligible recipient rolls from the enlarged pool. First-receipt scale still applies.

### Disabled behavior

If Evolution I is disabled, the baseline event remains fully functional. Extreme bands and the raised repeat floor stay unavailable. Later evolutions must not depend on an Evolution I-only delivery to preserve baseline operation.

## Evolution II: Experimental Naval Forces

### Requirement

- Chaos: 400 or higher

### Design purpose

The package pool can draw from naval assets associated with special projects, unusual technology, or experimental development.

The evolution expands what can appear. It does not grant research and does not claim ownership of experimental content created by other systems.

### Owner permission rule

An experimental asset enters Event 56 only when its owning system explicitly registers it as safe for fleet-package delivery.

Registration should define:

- legal countries or content conditions
- required technology or compatible fallback rules
- package identities that may use the asset
- hull-equivalent value
- support needs
- DLC requirements
- cleanup and invalidation behavior
- whether the asset can appear in AI hands

An absent or incomplete registration fails closed.

### Package changes

- baseline identities can replace one defining or secondary component with an approved experimental asset
- rare experimental packages can be centered on one registered special ship or submarine
- supporting aircraft or equipment can enter only through the same owner permission rule
- experimental assets remain bounded by local and global budgets
- the package report identifies that the force contains unfamiliar equipment without revealing hidden owner-system lore

### Active-event entry

Activation changes the future pool. Existing packages receive no retroactive experimental ships.

### Pre-fire entry

If active before the first manifestation, experimental assets can appear during that firing wherever their owner rules and recipient compatibility permit.

### Disabled behavior

If Evolution II is disabled, all owner-registered experimental entries remain outside the Event 56 pool. Their original owning events and systems continue to work normally.

## Evolution III: Impossible Fleets

### Requirement

- Chaos: 600 or higher

### Design purpose

The package identities can combine rare naval capabilities in formations that no ordinary procurement system would produce. The result can mix carrier power, advanced submarines, heavy surface groups, experimental vessels, and deep support in one coherent but extraordinary fleet.

The evolution does not remove package identity. An impossible fleet still needs a primary role.

### Package changes

- unlock rare hybrid package structures
- allow multiple registered experimental asset families in one package when their owners permit it
- allow carrier-heavy, submarine-heavy, or capital-heavy formations with unusual supporting groups
- increase the chance of large packages while preserving global limits
- allow rare combinations that would be inefficient or doctrinally contradictory

### Impossible package principles

- one primary identity remains readable
- every defining asset is legal and registered
- screening and aircraft support remain functional
- the package cannot bypass the total world budget
- the package cannot grant technology
- the package cannot create a custom unit or ship that lacks an implemented runtime asset

### Active-event entry

The future package pool changes after the evolution activates. No retroactive fleet is delivered.

### Pre-fire entry

A first Event 56 firing at 600 or higher can include impossible packages from the beginning.

### Disabled behavior

Disabling Evolution III removes impossible hybrid structures from future rolls. Baseline and any enabled lower evolution content remain available.

## Evolution relationships

The evolutions are progressive in theme, but each availability toggle must fail safely.

A disabled lower evolution should not break a higher enabled evolution. The implementation can resolve the highest enabled package pool from the current campaign state while excluding content that belongs only to a disabled stage.

Examples:

- Evolution I disabled, Evolution II enabled: experimental assets can enter baseline-sized packages, but the Extreme band and larger late-repeat floor remain unavailable.
- Evolution II disabled, Evolution III enabled: impossible combinations can use baseline and independently registered Evolution III assets, but Evolution II-only experimental entries stay excluded.
- all evolutions disabled: baseline event and repeat behavior remain complete.

## Evolution logging

Each evolution records one milestone through the shared evolution history.

The record should identify:

- Event 56 as the source event
- evolution stage
- current Chaos tier
- activation date
- no actor, because the evolution belongs to the global event package rather than one country

The evolution catalog in Event Details describes the future package change. It must not show fake dates or history indexes before activation.

## Evolved delivery milestones

The first actual experimental delivery and the first actual impossible delivery are separate concrete milestones. These can add Chaos once through the event-owned impact map.

Evolution activation alone adds nothing. A stage can activate and wait through several firings before a legal package actually uses its new content.

## Package identity across stages

The same identity can change meaning across evolutions without requiring a new player-facing package name for every stage.

Example progression for a submarine package:

- baseline: ordinary submarines with limited surface support
- Evolution I: much larger and more skewed submarine force
- Evolution II: ordinary force with one approved experimental submarine family
- Evolution III: advanced deep-ocean force supported by unusual command and aviation assets

The personal report should communicate the actual composition and anomaly level. It should not make the player memorize a large taxonomy of variant names.

## Repeat interaction with world change

Later firings recalculate eligibility and legal package content from the current world.

This means:

- newly coastal countries can enter
- annexed countries disappear
- new civil-war tags can qualify
- Event 54 technologies can expand legal ship tiers
- Event 55 ports can improve commissioning capacity
- new experimental registrations can enter after their owner systems allow them
- lost or disabled content is removed safely

Historical cohorts remain tied to what was actually delivered at their own firing.
