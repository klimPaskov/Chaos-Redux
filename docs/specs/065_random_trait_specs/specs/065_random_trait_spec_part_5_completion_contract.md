# Event 065 Random Trait

## Part 5: Completion Contract

## Completion definition

Event 65 is complete only when the implemented game behavior matches the supplied idea and every pass or fail condition in this package.

A long trait list alone is not completion.

A finished implementation must prove all of the following:

- every final loaded vanilla and Chaos Redux country-leader trait appears once in the generated registry
- the runtime pool is generated or reproducibly derived from that registry
- the direct path and cluster path use one authoritative executor
- every eligible existing country-leader role receives the correct stage count
- existing and prior Event 65 source traits are excluded from later accepted grants
- source traits are not filtered for theme, ideology, country, usefulness, harm, or contradiction
- Baseline and Evolution I are uniform
- Evolution II and Evolution III use the accepted bounded featured weights
- all weighted scenarios pass the probability audit
- Evolution thresholds, enable settings, manifestation, persistence, and history are correct
- direct Chaos milestones are guarded and non-farmable
- multiplayer results are synchronized
- the report shows committed results without owning gameplay mutation
- event history, Event Details, cluster history, and workbook content agree
- the report asset is valid and correctly wired
- save and load preserve traits, ledgers, Evolution state, and milestone state
- the event remains disabled until implementation validation is complete
- user-led in-game testing is still required before `Available`

## Required implementation sequence

### 1. Repository inspection

Run the Event 65 repo explorer prompt.

Map the current event script, current list, localisation, GFX, event log, Event Details, Evolutions, repeatable registration, cluster framework, trait source roots, test helpers, and workbook scripts.

Record exact file paths and live consumers.

### 2. Scripted-system architecture

Run the Event 65 scripted-system architect prompt.

Resolve:

- final trait source roots
- final loaded-ID resolution
- generator output shape
- recipient identity and ledger scope
- exact weighted selection method
- report-safe result storage
- stale registry behavior
- cluster entry path
- failure behavior

Do not code around unresolved scope assumptions.

### 3. Registry generation

Implement the parser, manifest, stable index map, featured override data, generated runtime pool, generated localisation selector, and check mode.

Run it against each supported content profile that changes the loaded trait set.

Review all exclusions.

### 4. Event implementation

Replace the current mutation-on-report-option path.

Implement the hidden executor, Evolution resolution, global pass, per-leader rolls, ledgers, counters, report dispatch, history, Chaos milestones, and debug hooks.

Keep all tuning in Event 65 constants.

### 5. Cluster integration

Register the Randomizations cluster and Event 65 member after the final numeric ID collision check.

Use the same executor as the direct event.

Wire settings, logs, details, member status, and participation.

### 6. Asset implementation

Run the asset prompt through the event-asset workflow.

Validate the existing DDS before reuse.

Install one final report-event asset and preserve permanent provenance.

### 7. Probability audit

Run the Event 65 probability auditor after the generated pool and runtime logic exist.

Use every named scenario in `quality/065_random_trait_probability_scenario_matrix.md`.

Any unresolved or biased result blocks completion.

### 8. Localisation and documentation

Write final player-facing text from the direction in Part 3.

Run the localisation auditor.

Update permanent event documentation and the authoritative workbook.

Export the CSV snapshots from the workbook.

### 9. Improvement loop

Run the mandatory Event 65 improvement-loop prompt with `fork_context=false`.

The loop should test whether the event is still shallow, disconnected, bloated, or missing a meaningful consequence.

Its output must be accepted, integrated, rejected with evidence, or converted into a closure handoff.

### 10. Completion audit

Run the read-only completion auditor against the source specification, prompts, manifests, generated files, runtime files, docs, workbook, and test evidence.

Resolve every blocking mismatch.

### 11. User acceptance

Provide a test build and focused in-game steps.

The user performs the real campaign and multiplayer checks.

Status remains `Needs Testing` until that review succeeds.

## Blocking defects

Any of these conditions blocks completion:

- manually maintained incomplete pool
- new source traits not detected by check mode
- duplicate source IDs in runtime probability
- undocumented technical exclusions
- source traits filtered because they look wrong
- trait mutation still occurring in a player option
- AI countries receiving queued visible reports
- different clients rolling independently
- a stage adding fewer traits without saturation or target invalidation
- existing traits being replaced or removed by Event 65
- repeated Event 65 source IDs on the same recipient
- featured modifiers stacking from several reason tags
- a featured ratio above the accepted maximum
- probability evidence missing for a supported profile
- Evolution threshold off-by-one behavior
- disabled Evolutions still applying
- Evolution history recorded before a successful evolved firing
- direct Chaos granted more than once per milestone
- direct Chaos multiplied by the number of leaders or traits
- cluster and direct paths producing different mechanics
- cluster ID collision
- direct CSV editing
- report text showing raw keys or registry indexes
- invalid or placeholder runtime event art
- stale docs or workbook fields
- event set to `Available` without user acceptance

## Validation ownership

The main implementation agent owns fixes.

The probability auditor measures and reports weighted behavior.

The scripted-system architect resolves architecture before coding.

The localisation auditor can patch Event 65 text within scope.

The asset worker produces and validates the report image package.

The spreadsheet and documentation worker aligns permanent records.

The improvement-loop planner evaluates design depth and closure.

The completion auditor reports pass, fail, blocked, or needs user review.

No read-only auditor should edit gameplay source.

## Planned user test

The final handoff should ask the user to verify at least:

1. A baseline firing below raw Chaos `200`.
2. The exact boundary at `200`.
3. The exact boundary at `400`.
4. The exact boundary at `600`.
5. A repeated firing on a leader who already has several Event 65 traits.
6. A player country with an ordinary leader.
7. A subject or civil-war country.
8. A save and reload after a firing.
9. A multiplayer firing with two human countries.
10. The leader interface after contradictory traits are added.
11. The Event Log and Event Details entry.
12. The Randomizations cluster entry path.

The user should record screenshots and the error log for any mismatch.
