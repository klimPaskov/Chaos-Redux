# Event 19 Unit-Family Coverage

This matrix is the current source map for every Chaos Redux custom combat or support unit that can be encountered by Event 19 or by a parent package that Event 19 must not impersonate. The source census contains 97 land sub-units: 50 combat units and 47 support units. Nineteen provider IDs (`501-514`, `518`, `520-523`) cover all 50 combat units and four inseparable support attachments through 14 required owner surfaces per provider (registration plus thirteen Event 19 callbacks). The remaining 43 support units have an explicit parent-owned disposition because they cannot form a division without a combat regiment. The single Event 19 registry file remains `common/scripted_effects/019_infantry_spawn_unit_registry_effects.txt`; family-owned adapters register themselves from their existing owner surfaces and do not edit that file. The Event 19 MCP inspection is partial and the weighted provider pool is not normalized by the installed adapter, so this matrix is a source and callback-coverage map rather than live probability or lifecycle proof.

## Exact provider obligation contract

Providers 512, 513, 521, 504-507, 509-510, and 522 use the temporary provider manifest in `common/scripted_effects/019_infantry_spawn_ledger_effects.txt`. Each manifest row carries a stable profile, per-battalion need, component count, and manpower/equipment scale kind; the commit helper multiplies it by the current lot start factor before appending an ordinary Event 19 obligation row. Ordinary profiles 100-129 remain Event 19-owned. Custom profiles 130-148 are stable constants in the owning provider packages and resolve through `event19_get_equipment_token`, yielding 20 published custom equipment-token identifiers because providers 504 and 522 intentionally share profile 142. Future custom equipment does not require a central Event 19 mapping. Provider 508 deliberately publishes zero Event 019 obligation rows because the shared alien-infantry API performs the exact laser debit and landing transaction. Its provider callback still enters Event 019’s standard unit spawner, injects Event 019’s allocated engine deletion ID into the API-created cohort, and defers state history, Alien Presence, Pact Strain, cooldown, and pact callbacks until every active Event 019 transaction wrapper has accepted its ledger proof. Automatic generation and each scenario actor narrow provider 508 to one state and one cohort without changing global scenario intensity. Same-tag scenarios retain persistent outer, debit, deletion-ID, and target-state receipts until their final commit or proven-absence rollback, including delayed rollback retries. A rollback deletes the exact cohort and refunds exactly 2,000 laser weapons before the shared snapshot verifier compares equipment and ledgers. No generic proxy row replaces a bespoke need.

The selected-family spawn verifier is manifest-aware: it accepts a committed manifest row count of zero, two, seven, or sixteen (and any future zero-scaled omission), derives expected manpower liability and equipment debt from the committed manifest totals, and scans the appended obligation tail for sequential obligation UIDs, generation/lot/unit ownership, issued and outstanding amounts, zero paid/salvage amounts, outstanding status, and profile-appropriate debt before the transaction can commit.

The exact standing contracts are:

- Provider 512: one `chaosx_elephant` battalion, 1,600 manpower and 180 `chaosx_elephant_equipment_1`.
- Provider 513: five combat and three support components, 6,320 total manpower and eight bespoke equipment rows totaling 1,400 units (`gorilla_heavy_infantry`, `pan_sappers`, `stone_cohorts`, `riverborn`, `forest_giants`, `oracle_recon`, `disaster_wardens`, and `plague_carriers`).
- Providers 504-507 and 509-510: the exact unit-file needs, including generic infantry/support equipment, the provider-neutral autonomous robot and teleportation equipment rows, and the applicable profiles in the 142-148 range for clone and the remaining owner-specific project equipment. Provider 508 is excluded from this standing-obligation contract and instead calls the shared 2,000-laser landing API.
- Providers 504 and 522: ten combat battalions use 1,000 manpower, 90 `infantry_equipment`, and 1 `clone_equipment` per battalion; a full lot therefore records 10,000 manpower, 900 infantry equipment, and 10 clone equipment before start-factor scaling. Sustainment uses 1,000 manpower, 180 infantry equipment, and 2 clone equipment per provider contract. Provider 522 uses this same clone resource contract while retaining its five-gate Aryan-only eligibility boundary.
- Provider 521: 1,050 manpower, 170 infantry equipment, 70 support equipment, 100 gas masks, 60 decontamination equipment, 15 CBRN instruments, and 30 motorized equipment. The operation-level `chemical_agent_payload` is intentionally excluded from standing unit debt.
- Provider 523: all nine Event 014 combat bodies use owner-defined totals of 7,350 manpower, 990 infantry equipment, and 35 motorized equipment before Event 19 start-factor scaling. The provider publishes no new custom equipment token and remains spawn-only.

The provider manifest is temporary and is cleared before and after every callback. Its stable profile IDs are not an Event 19 family list: a future family still adds one owner-side registration and complete thirteen-callback contract without editing Event 19's dedicated registry file. `event19_get_equipment_token` resolves the current custom profile, `event19_publish_custom_equipment_tokens` exposes every custom stockpile touched by provider payment or refund to the exact snapshot verifier, and `event19_get_presentation` supplies the family-name, request-cost, and sustainment-cost localisation tokens used by the Muster decisions and frozen lifecycle evidence. These callbacks never perform a second debit or create another registry.

## Deliberate exclusions

`aryan_clone_infantry` is excluded from provider 504 because `mengele_aryan_clone_refinement_tech` is a Germany/Mengele parent refinement and Event 19 must not copy that parent identity into neutral family lots. Provider 522 is the separate owner-side, strictly gated Event 016 adapter for the actual German refinement, with its own template, manifest, management, and cleanup callbacks. The five cave support-free templates, six rat parent templates, and all CBRN support templates remain available through their owning events and are not re-created as a second Event 19 list. A future family or support-capable combat package adds one registry entry and its complete owner callback contract; no Event 19 list edit or new Event 19 registry file is required.

## Validation contract

Every registered token appears in an owner provider `build_template` callback and in its source `common/units` definition. Registration is idempotent from existing parent startup paths, all providers use the same source-local gate as their parent package, and missing provider or package proof fails closed without a generic infantry substitute.
