## Existing patterns
The prior Event 003 source in `HEAD` is the strongest recovery evidence. Its root event directly dispatched to TIB when TIB passed `can_host_holy_realm_refuge`, and otherwise used native `random_country` with that same trigger as the limit. Because the trigger itself admits BHU and NEP only when TIB is absent, the fallback was equal/native among admitted alternatives and did not encode a hidden TIB multiplier, country load score, or fixed-country bias.

The current owner helper preserves that contract while publishing the target expected by the new caller. The helper must remain a one-shot selection effect in the root event's immediate chain. The target is a regular event target because the next dispatch is part of the same chain; a global target would add unnecessary cleanup obligations.

The current crisis pattern for an actually weighted pool is to compute an owner-specific base score in the candidate country or state scope, apply any accepted shared pressure, add one temporary array entry per integer ticket, draw with `random_scope_in_array`, save the selected regular event target, and clear every temporary array and scratch variable. An empty pool must leave the selection result unset and must not silently choose a generic country or fixed host.

That pattern is useful if a future accepted Event 003 design introduces package-owned host scoring. It does not prove that Event 003 should use the shared load curve today, because the accepted Event 003 specs contain ordering and eligibility only, and the shared system document explicitly leaves fixed-target integration as a follow-up.

### Ordinary risks
- A broad `random_country` call without the existing `can_host_holy_realm_refuge` limit would admit unrelated countries and violate the source contract.
- Applying the shared load curve to TIB/BHU/NEP without an accepted fixed-target design would silently change prior behavior and make the `weighted` helper name misleading.
- A delayed event must stay inside the selected target scope and behind the target validity guard; a missing target must fail closed without queuing an event.
- Temporary pool or scratch variables introduced by any future weighted implementation must be cleared, and a global event target would create cleanup requirements that the regular target avoids.
