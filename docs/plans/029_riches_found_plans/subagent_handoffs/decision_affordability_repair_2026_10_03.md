## Changed files and behavior

- `common/scripted_triggers/029_riches_found_cost_triggers.txt` adds 24 concrete resource affordability components and 92 no-argument action composites. The components compare political power, command power, manpower, fuel, and equipment using the exact amount and concrete equipment token already debited by the corresponding decision. Manpower uses `manpower_k` with the existing people-valued debit amounts converted to thousands; equipment uses `num_equipment@<exact token>`; comparisons are inclusive. Fuel affordability negates the strict `<` check.
- `common/decisions/029_riches_found_decisions.txt` calls the matching composite from both `available` and `custom_cost_trigger` for all 92 paid decisions. Existing debit amounts, cost text, IDs, effects, durations, AI weights, route conditions, and mission eligibility helpers remain intact. Sixteen paid actions that require a free mission slot or mission eligibility retain those non-spendable requirements in both gate surfaces.
- The 90 paid decisions that previously declared `fire_only_once = yes` now declare `fire_only_once = no`. Their existing state-targeted availability/receipt conditions remain the repeat and lifecycle authority; audit and renegotiation retain their pre-existing repeatable status. This allows a second mine to use its own action state rather than being suppressed by the first mine's country-level completion. No new permanent state flags were added.
- `decision_riches_found_select_mine` retains its ID, selection receipt, target marker, hover text, and AI block, with `on_map_mode = map_only` so target rows remain on the map rather than filling the category list.
- Seventy-five bounded delayed `remove_effect` transactions validate `FROM` with `is_controlled_by = ROOT` and `riches_found_mine_is_registered = yes`. Their stale branch refunds every exact resource debit to the original actor. The invalid state-scoped `exists = yes` was removed from all 75 guards; the installed trigger documentation marks `exists` as COUNTRY-only (see references below).

## Cost audit and unresolved acceptance gaps

- Current recipe audit: 92 paid actions, zero actions over four distinct spendable cost types, and zero debit/gate amount or equipment-token mismatches. No semantic cost was removed. Four-value costs whose inline row shows three values retain the fourth in the full cost tooltip. Cost localisation uses texticons for every spendable resource family.
- The native cost display is not yet aligned to the new inclusive gates: `common/scripted_localisation/029_riches_found_scripted_localisation.txt` still uses strict `>` selectors for manpower, political power, command power, fuel, and equipment; manpower selectors also use deprecated `has_manpower`. Train and convoy display selectors use archetype tokens while these decisions debit `train_equipment_1` and `convoy_1`. At an exact affordability threshold, a decision can therefore be available while a displayed component remains red; train/convoy colours can also disagree with the exact-token gate. Localization was outside this handoff's write scope.
- Accepted physical commitment gap: the spec requires civilian-factory burden for `survey`, `claim_register`, `reserve_deposit`, `camp_administration`, `specialist_labor`, `sanitation`, `rail_spur`, `port_route`, `shaft_reinforcement`, `processing_works`, `housing`, `drive_deeper`, `nationalize_with_compensation`, `buyout`, `workforce_replacement`, `seal_depths`, `repair`, `evacuation`, and `permanent_seal`. The current decisions debit political power/manpower/stockpiles or alter mine values; they do not reserve or consume civilian factories. The universal-cost system documentation also classifies factory commitments as requiring an exact owner adapter rather than a generic native cost field. These costs remain a design/implementation issue, not a fifth cost to silently discard.
- Security commitment gaps: `army_cordon` and `pay_train` require `riches_found_state_has_supplied_force`, which checks route capacity and divisions-in-state above the configured floor, but neither transaction reserves those divisions from redeployment. `disarm_private_forces` requires private guards/enclave but does not require enough regular security or commit units. `quarantine` checks access control/security presence without reserving units. `temporary_closure` has no explicit force-presence or unit-commitment gate. The spec asks for unit/security commitment in these actions.
- Recipe/spec mismatch examples requiring owner decision: the spec lists support equipment and committed units for Army Cordon, while the source debits infantry equipment and does not reserve units; Escort the Pay Train's spec calls for support equipment plus unit commitment, while the source debits motorized equipment and only checks supplied-force presence. Adding support equipment without redesigning another component would push either current four-type recipe beyond the four-type cap. Do not remove a semantic cost to make the count fit.
- Accepted dynamic-cost gap: Part 3 says costs should respond to population, development, damage, distance, war, supply, local order, concession exposure, and previous failure. The implemented composites faithfully gate the existing flat constants. No scaling formula was invented in this bounded tranche; the parent can design/integrate it after reviewing the accepted cost profiles and the neutral universal-cost API.
- The neutral `universal_cost_framework` and `stockpile_debit_helpers` were inspected before adding the decision gates. The neutral framework quotes owner-supplied costs and records transactional payments/refunds for modifier-based costs; it does not supply these decisions' ordinary action-specific base costs or make an arbitrary resource token debitable. Existing decision payments already use fixed concrete `add_equipment_to_stockpile`/fuel effects. The new triggers therefore preflight those fixed recipes without creating a second scaling system or changing payment semantics. Revisit the shared quote adapter if Event 029 gains a universal-cost modifier or an accepted dynamic-price provider.
