# Skill Maintenance Note: Windows Mapped-File Write Recovery

**Disposition:** accepted and queued. The user authorized changes only to Event 042-owned files and minimal framework edits, so this proposal does not edit a skill, gameplay source, or spreadsheet. The parent owns any later skill update.

**Existing coverage:** `chaos-redux-shared-git-commit` documents OneDrive `.git/index.lock` reconciliation failures, but no inspected skill gives a generic recovery for an ordinary source file that cannot be truncated because a Windows process has it memory-mapped. The subagents and events skills do not cover that case. A narrowly scoped addition to `chaos-redux-shared-git-commit` is the closest current destination because it already covers OneDrive file-operation recovery; clarify that the method applies only to an owned regular file, never Git's index/lock files. For broader reuse beyond that skill, consider a small shared file-editing skill only if more instances establish the need.

**Proposed rule:** When repeated writes or truncation fail and a .NET `WriteAllText` attempt reports that the operation cannot be performed on a file with a user-mapped section open, preserve the exact intended bytes by writing them to a unique sibling temporary file on the same volume. Resolve and verify that both the original target and replacement remain inside the authorized workspace, then replace the exact original with `Move-Item -LiteralPath <sibling-temp> -Destination <original> -Force` and read the destination back to confirm the expected content. This is a targeted file-write recovery; it does not change runtime design or authorize unrelated fallback behavior.

**Evidence condition:** Apply this rule only after repeated direct write/truncate failure and an explicit mapped-section diagnostic. In this task, Python writes repeatedly failed with Windows `OSError` errno 22, and .NET `WriteAllText` clarified: "The requested operation cannot be performed on a file with a user-mapped section open." The same content was successfully installed through a unique sibling temporary file and exact-path `Move-Item`, then verified by readback.

**Safety checks:** Keep the replacement beside the target to avoid cross-volume moves; use literal paths; check the resolved absolute original and temporary paths are inside the workspace before replacing; write the intended encoding and BOM to the temporary file; replace only the exact owned target; read back and compare the result. Do not use this as a response to unrelated errors, for `.git/index` or lock files, or as a reason to launch/close applications, alter gameplay/runtime behavior, or request a restart. Clean up a leftover temporary file only after confirming its exact path and ownership.
