## Decision summary

The smallest complete architecture is a private Mengele provider layer with its own family-stage receipts and one active program receipt per family. It is deliberately separate from Kruger’s Event 016 board ledger, capacity, facilities, event targets, evolution state, terminal commitment, and achievements.

The layer has two entry routes, and the provider stage decisions remain available in both DLC states.

1. The native route exposes the existing native special-project objects for the mapped native step. Their native clock, breakthrough payment, resource payment, prototype reward selection, and completion callback remain authoritative. A completion adapter records a Mengele-owned receipt for that exact step and never calls `brilliant_scientist_complete_native_prototype_stage`.
2. The provider decision route exposes Theory and every post-prototype stage under the existing `mengele_clone_army_category` after the existing `MCL_directorate_project_registry` gate, regardless of DLC state. A Prototype decision is visible only when the mapped native project presentation is unavailable for that family; otherwise the native project owns only its actual mapped step. Private begin, cancel, and finish effects use the existing Event 016 family/stage duration and the existing stage cost table, with three direct provider payment axes (political power, support equipment, and fuel) plus a temporary civilian-factory reservation owned by the decision lifecycle. They never call the Kruger board effects.

Both routes converge on the same provider-owned stage outputs. Deployment grants the existing full operational package for the selected family, and Weaponization grants the existing upgrade or fourth stage output. The API flags and provenance arrays are durable entitlements and are not removed when the Mengele program closes, the provider dies, or the provider loses a project receipt.

Strategic Singularity is the only special adapter. Mengele owns a six-component registry and six component receipts, then enters the existing Fallout request/lock/world-end pipeline through a provider-aware branch. It does not set Kruger identity, Kruger stage 14, Kruger terminal commitment, Kruger terminal receipts, or Kruger achievement state. The provider Fallout adapter remains an implementation risk until the owner proves the shared lock and presentation callers in engine validation.

## Provider-owned state

Use `mengele_event016_` as the private namespace. The existing provider gate is the conjunction of the current Mengele validity/program state and the existing `mengele_clone_focus_directorate_project_registry` receipt. The implementation must preserve the existing program/faction/clone-model distinctions and must not turn a neutral API entitlement into Kruger state.

For each family short name in `computation`, `electronics`, `materials`, `rocketry`, `high_energy`, `biomedical`, `teleportation`, `cloning`, `robotics`, `paleogenetics`, `xenobiological_synthesis`, `biological_weapons`, `alien_arms`, `temporal`, and `singularity`, use four provider completion flags:

`mengele_event016_<family>_theory_completed`, `mengele_event016_<family>_prototype_completed`, `mengele_event016_<family>_deployment_completed`, and `mengele_event016_<family>_weaponization_completed`.

The active provider decision receipt is one entry per family in aligned arrays: `mengele_event016_active_project_stage_entries`, `mengele_event016_active_cost_political_power_entries`, `mengele_event016_active_cost_support_equipment_entries`, `mengele_event016_active_cost_fuel_entries`, and `mengele_event016_active_cost_civilian_factory_commitment_entries`, indexed by the existing family ID. A stage entry of `constant:brilliant_scientist_project_stage.none` means that family has no active provider decision. There is no global `mengele_event016_project_stage_in_progress` flag and no global active-family field.

Do not add a generation field to this contract. No source-proven mechanism was found for snapshotting a country variable into a native timed-decision callback; a token read dynamically by both the old and new callback would not isolate them.

Native prototype selection uses static per-project pending flags rather than an unproven persistent numeric special-project ID. Examples are `mengele_event016_native_computation_prototype_pending`, `mengele_event016_native_rocketry_flying_bomb_pending`, and `mengele_event016_native_rocketry_air_jet_engine_pending`. The pending flag is set only after the provider has passed the exact family/native-project gate and is cleared only by the matching callback, cancellation, provider cleanup, or terminal cleanup. For rocketry, the selected alternative must be retained so completion of the other alternative cannot settle the receipt.

Singularity uses `mengele_event016_singularity_component_entries`, `mengele_event016_singularity_component_count`, and one completion flag per existing component constant, such as `mengele_event016_singularity_command_core_completed`. Registration must de-duplicate the array before incrementing the count and must never call the Kruger component registry on a Mengele provider.

### Timed-decision receipt and stale-callback boundary

The bounded repository precedent is the existing Event 016 board: every decision wrapper writes literal family/stage selectors in `complete_effect`, `cancel_effect`, and `remove_effect`, while `brilliant_scientist_project_stage_in_progress` plus persistent active family/stage variables identify the one current receipt. The existing resources-found decision project similarly stores one active project family; neither pattern snapshots a generated token into a later callback.

Use that supported ownership model for Mengele, with one independent receipt per family rather than one global receipt. Each provider decision ID has a statically written family and requested stage in all three callbacks. `visible` and `available` require the provider gate, the exact predecessor, and that the family’s `mengele_event016_active_project_stage_entries` entry equals `constant:brilliant_scientist_project_stage.none`. The begin core sets that family’s active stage and cost entries before the decision timer starts. The cancel and finish cores require the family’s active entry to match the literal callback stage, snapshot family/stage/direct-cost values to temporaries, clear that family’s active stage and cost entries before any refund or output, and only then settle the callback. The civilian-factory quote is a native decision reservation, not a refundable balance.

This protects ordinary callbacks and cleanup callbacks: a callback for a different family or stage is rejected, and a callback after cancellation or finish sees no active receipt for that family. Cleanup must not start a new provider decision in the same effect chain. The owner must rely on the engine’s native timed-decision lifecycle, in which the canceled or removed decision instance is gone before that same decision can be selected again; a separate asynchronous event must never call a generic finish core without its literal family/stage wrapper.

Same-family re-entry after a canceled timer is the remaining engine-ordering point. Source review found no supported variable snapshot or callback-generation mechanism that would strengthen this. If live acceptance shows a removed decision callback can arrive after a new instance of the same decision has begun, the safe response is to keep the decision instance unavailable until its native removal is complete and add an engine-proven retirement or holdoff mechanism; do not reintroduce a dynamically compared generation token as if it were isolation.

## Native and provider stage routes

The native route should be unlocked by the existing Mengele program registry and use the existing special-project selectors. `make_all_directorate_special_projects_researchable` may set deterministic availability for the missing electronics, rocketry, high-energy, biological, and Singularity component candidates, but it must not change the 13-candidate weighted helper.

For each native project output, the existing callback should branch on `brilliant_scientist_mengele_project_provider_is_valid` before any Kruger completion call. The branch must verify the exact family and, for mapped alternatives, the exact native project receipt. It then sets the provider Prototype flag and clears only the matching provider availability/pending flag. It must not call `brilliant_scientist_complete_native_prototype_stage`, `brilliant_scientist_refresh_project_capacity_from_gross`, `brilliant_scientist_register_singularity_component`, or any effect that writes Kruger’s stage array.

The ten custom Event 016 projects already call `brilliant_scientist_record_new_project_prototype`. Extend that callback with the provider branch. The mapped native projects require an additive provider synchronization helper that tests `is_special_project_completed` for the same exact project IDs as the existing host gates. A native Prototype is not a provider Deployment receipt; later stages remain available through the provider route in both DLC states.

The existing custom-family bridge currently grants durable custom operational API knowledge at native Prototype for teleportation, robotics, paleogenetics, xenobiological synthesis, alien arms, and temporal. Preserve that knowledge and its existing API provenance. Do not revoke it, infer provider Deployment history from it, or re-award the same package at Deployment. A neutral/custom API flag may also have come from an external provider, so provider stage receipts and Mengele-owned native history must be written only by an exact matching project callback or an explicit provider decision.

The mapped later-stage exceptions are narrow.
