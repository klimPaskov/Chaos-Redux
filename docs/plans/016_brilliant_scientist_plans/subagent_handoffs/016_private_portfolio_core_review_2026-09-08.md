## Confirmed native-before-Theory dead end and reviewed repair boundary

Before the parent patch, the path was incomplete:

1. `on_project_completion` invokes the strict Mengele native reconciliation only at native completion.
2. Every ordinary family authenticity trigger requires its exact private Theory flag.
3. A project completed before Theory therefore records no private Prototype.
4. Later Theory completion called `brilliant_scientist_mengele_apply_family_stage_output`, whose tail only reconciled presentation availability; it did not retry native authentication.
5. The matching native research gate rejects an already-completed native project, so the player cannot complete the same native step again. The four reused native families could recover only incidentally if some later project completion retriggered their multi-family helper; the other native families had no guaranteed recovery.

The reviewed minimal repair is `brilliant_scientist_mengele_adopt_completed_native_after_theory`, called from `brilliant_scientist_mengele_finish_project_stage` after refund/output resolution and Computation incident dispatch, but before `stage_finished` and the final selector clear. Its gate requires the successful outer output, literal Theory stage, strict provider, and either an exact authentic ordinary native completion or the Singularity family. The Singularity branch then authenticates each component independently rather than treating family identity as completion evidence.

This location is non-recursive. The only direct callers of `brilliant_scientist_mengele_apply_family_stage_output` are paid finish, native sync, and Singularity component completion. The adoption helper is called only by paid finish. Its ordinary nested path is `adopt -> sync native Prototype -> apply Prototype -> reconcile availability -> restore early modifiers`. Its Singularity path is `adopt -> exact component record -> apply Prototype once all six exist -> reconcile availability -> restore early modifiers`. Neither apply nor reconcile calls adoption.

The helper snapshots and restores these eight outer temporary fields around native sync:

- `mengele_event016_project_family`
- `mengele_event016_requested_stage`
- `mengele_event016_project_index`
- `mengele_event016_project_output_applied`
- `mengele_event016_computation_output_applied`
- `mengele_event016_stage_output_gap`
- `mengele_event016_project_output_authorized`
- `mengele_event016_project_availability_reconciled`

Native sync does not write `stage_started`, `stage_finished`, `stage_cancelled`, the settlement snapshots, or the cleared receipt arrays, so those fields need no additional preservation. Calling adoption after incident dispatch also prevents the nested Prototype application from changing the already-decided Computation incident branch.

For Singularity, the helper additionally snapshots and restores `brilliant_scientist_singularity_component`. It loops a private index from zero to less than the constant component count, increments to selectors 1 through 6, restores private family `singularity` before every call because the component recorder clears it, and invokes the existing exact component authentication/record API. That API records only actually completed native components, de-duplicates the six private flags/count, and applies private Prototype once when the complete predicate first succeeds.

## New actionable findings

### Seven custom native families needed their operational entitlement on late adoption

The finish-time adoption helper initially called `brilliant_scientist_mengele_sync_native_project_prototypes` directly. That records the private Prototype, but the existing custom operational package dispatch lives in `brilliant_scientist_record_mengele_project_prototype` after a successful bridge result. When the original native completion predates Theory, that original bridge result is zero and the operational grant is skipped. A later direct sync therefore leaves Teleportation, Cloning, Robotics, Paleogenetics, Xenobiological Synthesis, Alien Arms, and Temporal with a private Prototype but without the custom operational entitlement required by the accepted native-Prototype scenario.

The parent implemented `brilliant_scientist_mengele_grant_native_custom_operational_package` in the bridge-effects file and calls it from both the original bridge success path and a successful late adoption. Final source review confirmed all seven family-to-custom-selector mappings, strict private owner, exact private Theory and Prototype, exact native completion, fixed Mengele provenance, idempotent public API dispatch, input/source cleanup, and no native output replay or Kruger history mutation. The stage helper calls it only when `mengele_event016_native_prototype_synced = 1` and supplies the saved outer family before restoring the eight outer fields. This finding is closed in source review.

The helper's companion contract now exists in `common/scripted_effects/016_mengele_project_bridge_effects.md`; the earlier dangling-document concern is closed.

### Biological bridge used six malformed project IDs

The bridge availability gate previously used `sp:sp_*` for all six Biological projects, while actual project definitions and the authentication trigger use bare IDs inside the `sp:` scope prefix. That mismatch could advertise an already-completed Biological route because the exclusion tests queried nonexistent IDs. The parent corrected the six gate tokens; the current bridge hash above includes the correction.

### Seven custom native-family Deployment baseline was restored, but full operational depth remains unresolved

The native Prototype bridge and post-Theory adoption helper grant the neutral custom operational package for Teleportation, Cloning, Robotics, Paleogenetics, Xenobiological Synthesis, Alien Arms, and Temporal. Their later private Deployment branches in `brilliant_scientist_mengele_grant_custom_stage_package` call that same operational API again. `chaosx_grant_custom_operational_technology_core` sets its applied result for every valid family even when the technology and durable grant flags already exist, so the finish transaction treats the replay as a successful new stage.

Before the parent correction, the only additional effect was the private `mengele_event016_<family>_deployment_completed` flag, whose only consumers were the family-stage predecessor/completion triggers that unlock Weaponization and prevent repeating Deployment. An exact-name search found no force, evolution, modifier, facility, or other operational consumer of those seven private Deployment flags. Reconciliation could repair a missing neutral runtime projection, but it did not grant a new entitlement in the ordinary already-reconciled path.

The matching Kruger Deployment outputs add a dedicated `brilliant_scientist_<family>_deployment` dynamic modifier for all seven families. Teleportation, Cloning, Robotics, Paleogenetics, Xenobiological Synthesis, and Alien Arms also establish their family-specific physical site/network state; Temporal receives the dedicated Deployment modifier. Kruger's personal Deployment flags additionally feed project-force and evolution consumers. Those Kruger facility, event-target, history, capacity, and evolution writes are deliberately forbidden to the private provider, but their absence does not turn the repeated Prototype API grant into a distinct private Deployment reward.

The parent restored numeric baseline parity by extending the seven existing Deployment modifiers with `current Kruger host OR (strict private owner AND exact private Deployment receipt)` enable conditions and the exact logical-complement removal conditions. `brilliant_scientist_mengele_restore_deployment_project_modifiers` maps each of the seven receipts to only its matching missing modifier and runs from reconciliation after early-modifier restoration. Source review confirmed all seven mappings, no Prototype flag in any Deployment authorization, no neutral API or history grant in restoration, removal on private-provider loss when the country is not the Kruger host, and preservation of the original current-host branch. Since successful stage output sets the Deployment receipt before its tail reconciliation, the first paid completion installs the modifier; subsequent reconciliation is idempotent.

This closes the paid-no-op defect at the existing numeric-modifier baseline. It does not establish a private physical or action package analogous to the matching Kruger Deployment sites/networks and their downstream project-force surfaces. The accepted plan says Deployment grants the full operational package while also forbidding private writes to Kruger facilities, event targets, history, capacity, and evolution. A private physical/action analogue therefore needs an accepted design rather than an auditor-invented fallback. Keep that depth gap open until the designer proposal is accepted and implemented or the accepted plan explicitly disposes it.
