# Parent-authored design review

Status: completed as a parent review of this planning package. This is not a custom-agent output, an independent audit, a game test or the mandatory `chaosx_improvement_loop_planner` pass.

## Preserved identity

The five-part design retains every substantive rule in the user brief: global current-map coverage, 1,000 added mines per eligible owner-region pair, separate ownership, preservation of existing fields, normal per-field cap, fire-once behavior, Sudden Abundance Medium, and genuine normal clearance.

The core files remain focused on the world change and player experience. Technical API gates, parser questions, lifecycle state, source conflicts, workbook instructions and detailed tests are placed in the companion plans. Prompt files are separate from the creative specification parts.

## Improvements incorporated during the parent review

| Finding | Disposition incorporated |
| --- | --- |
| “Stacking” can confuse stored ownership with combat multiplication | Part 2 explicitly separates these claims and leaves combat aggregation native |
| A fill-to-cap implementation would be wrong under a raised cap | Fixed +1,000 additive behavior and ordinary/raised/lowered cap examples |
| A later call can refill a swept field even if the initial amount was capped | A global consumed guard survives clearance, save/load, cluster selection and independent timers |
| Region coverage can be accidentally tied to coastal owners | Separate firing-time C and R sets, with full Cartesian coverage |
| A generated list can falsely imply arbitrary-map compatibility | Require effective-map fingerprint and an actual compatibility mechanism |
| Current report option owns irreversible mutation | Preflight/application/commit separated from acknowledgment |
| Generic dispatcher may consume or log before the body rejects | Explicit prefire integration and successful-history commit boundary |
| Legacy saves can receive an unintended second incident | Preserve proven legacy consumption without fabricated global provenance |
| A selection with all fields already full is not a new manifestation | No-change pass consumes once but adds zero proposed Chaos |
| Counts dropping do not prove active player sweeping | Achievement attribution excludes peace, decay, disappearance and allied-only removal |
| Coastal ownership does not prove a naval landing | Offensive achievement requires a native operation and actual attribution |
| A history snapshot can become a misleading live display | Separate historical event detail from current naval map information |
| Catalog description and membership are stale | Targeted XLSX/runtime handoff with unrelated cluster conflicts preserved |
| Provided agent profiles could be mistaken for executed reviews | NOT RUN on all briefs and explicit execution disclosure throughout |

## Expansion decisions

The accepted authored additions are the operational response profiles, explicit native recovery semantics, cross-event behavioral connections, once-only material Chaos proposal, two difficult achievements, and a coherent report/achievement visual family. They deepen the incident without replacing the native naval game.

Recurring saturation, permanent sweep resistance, a separate mine currency, click-to-delete clearance, automatic fleet grants, forced wars, scripted convoy-loss quotas, and a redundant mine-management panel were rejected because they would weaken the user's recovery rule or add unrelated administration. The review did not add new countries, focus trees or provider jobs simply to activate every supplied conditional skill.

## Unresolved findings

The current map provider, native ownership/cap behavior, eligibility, combat aggregation, material-increase observation, clearance and landing attribution, shared dispatcher details and legacy migration all require actual engine and repository verification. The complete external reading gate, current visual references, live XLSX inspection, HOI4 MCP calls and custom-agent execution are also incomplete.

The +20 Chaos amount is an authored starting proposal, not a tested balance value. The achievements are fully described, but their required observations have not been shown script-accessible. Neither issue is hidden behind a working-key registration or an icon plan.

## Near-completion disposition

The source-spec drafting and parent review are complete for this delivery. The project's complete mandatory workflow is not. The included custom improvement-planner brief must be executed in a runtime that actually exposes the profile. Its absence is a recorded requirement gap, not a clean closure certificate.
