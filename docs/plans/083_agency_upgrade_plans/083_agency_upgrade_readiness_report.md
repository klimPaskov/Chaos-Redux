## Full-pool adapter requirements

Inspect the installed `gain_random_agency_upgrade` helper, all effective agency upgrade definitions, and override order. Record identifiers, purchase-level behavior, prerequisites, country restrictions, feature gates, and ownership checks. Prefer a native complete selector only after its coverage and exhaustion behavior are proved.

If a generated registry is needed, its generator must consume the effective supported definitions rather than a hand-maintained list of favorite upgrades. It should emit coverage evidence and a source fingerprint. Runtime selection filters the complete generated registry after every grant. Changed installed definitions or unsupported third-party additions invalidate compatibility claims until the registry is regenerated and checked.

Build-time enumeration and runtime eligibility are different operations. Do not pretend Clausewitz reads arbitrary mod files at runtime. A generated catalog can satisfy broad dynamic ownership and availability selection for its verified installation, but cannot automatically promise coverage of an unseen later mod.

## Immediate recruitment adapter requirements

Prove the human interaction for five distinct Event 83 recruits from one firing, including a pre-existing cooldown and pre-existing normal recruitment choices. Each claimed Event 83 candidate must be available without successive ordinary waits, while leaving ordinary recruitment progress intact.

The documented direct-creation bypass may prove that automatic hiring is possible. That alone does not satisfy the design's retained recruitment choice. A custom decision that simply auto-hires five operatives also changes the user-facing behavior and is not an implicit fallback. Search the installed native recruitment surfaces before proposing any design change.

Capacity and candidate-choice count are separate fields. Inspect the capacity contribution through `operative_slot`, and do not substitute the similarly named recruitment-choice bonus. Event 83 capacity must coexist with native upgrades, advisors, and faction spy-master effects rather than resetting the country's total.

## Percentage adapter requirements

For counter-intelligence, a conceptual target is Event 83's active percentage sum multiplied by the appropriate native base excluding Event 83's own contribution. This is a mathematical statement of intent, not a verified engine recipe. A derived flat adapter must demonstrate access to that base, correct interaction with assigned home operatives and other owners, and correct updates when those sources change.

Reading a total that already includes yesterday's own derived modifier and multiplying it again can create feedback. A derived adapter must prove that this cannot occur, including the engine's modifier-update order. A one-time snapshot that stops reflecting later base changes is also not automatically equivalent to the specified percentage benefit.

Verify preparation speed against a controlled operation with unchanged prerequisites and costs. Verify encryption against the actual agency-era cipher protection measure. Keep speed, required work, strength, equipment cost, and operation outcome separate. Do not invent plausible-sounding modifier identifiers in finished game files.

## Country and save handling

A successful firing requires valid recipient context, a frozen package, committed per-country results, and one global completion contribution. This describes observable semantics, not a claim that the engine provides general database transactions or automatic rollback.

Preflight missing adapters and unsupported global capabilities before mutating rewards or consuming the event. If an unexpected error occurs after some real grants, preserve diagnostic phase evidence and prevent blind full replay. Do not convert the technical failure into exhaustion, mark the incident fully successful, or claim that the game rolled back changes it did not actually reverse.

Use stable country and firing ownership for claims and expirations. A cosmetic tag change is not a new recipient. Conquest is not a transfer of reward ownership. The current save migration and native handling of exiled or re-created countries must be inspected before selecting exact persistent identifiers.

## Cluster and shared-history reconciliation

The supplied CSVs are export-only snapshots. Their Intelligence ID and the inspected runtime enum are different identifier spaces in practice. Resolve the intended Intelligence cluster by identity and inspect existing runtime registration, pending queues, and saved history before allocating or migrating an ID. Do not repurpose persisted Diseases ID 8.

Low is the event's declared severity. Runtime required, optional, and randomized participation roles are separate and must be inherited from the actual cluster design. Respect the user's rule that a cluster incident counts once for timer and weight accounting, while each member retains its own once/repeatable eligibility. Event 39 must not become repeatable just because Event 83 joins the same semantic cluster.

Relevant inspection targets include `common/scripted_effects/chaosx_event_cluster_effects.txt`, `chaosx_logic_effects.txt`, `chaosx_events_log_effects.txt`, `chaosx_settings_effects.txt`, current category initialization, and the shared history localisation. These files are follow-up targets, not files claimed fully read in this planning session.

Choose the package before the existing history path commits its entry, or adapt that path so it records the frozen package correctly. Shared evolution-entry logging must not be mistaken for a new reward firing. An evolution flag or history callback never adds its own +5 Chaos.
