## Receipt contract and exploit closure

Each paid action now has an actor-targeted state receipt flag and controller-id variable, alongside an action-specific state lock. The shared pending flag is targeted by `@ROOT`. For example, security uses `asteroid_incoming_crater_action_pending_@ROOT`, `asteroid_incoming_crater_security_paid_@ROOT`, `asteroid_incoming_crater_security_action_in_progress`, and `asteroid_incoming_crater_security_controller_id_@ROOT`; the same pattern is repeated with distinct names for survey, fortification, reconnaissance, disruption, and offensive preparation.

Each `complete_effect` revalidates reserves and action requirements before debiting. Its single guarded start branch rejects an existing actor pending receipt, that actor's same-action paid receipt, or the state's same-action lock, and only then debits and records the actor/action/controller receipt. Each `*_action_can_resolve` requires the exact paid flag targeted to `ROOT`, the matching action lock, that actor's pending flag, and the matching actor-targeted controller capture still equal to the current site controller; it then rechecks site, control, war, and action-specific outcome conditions.

Each `cancel_effect` refund and each invalid `remove_effect` refund is nested under that decision's exact `*_paid_@ROOT` flag. A normal `remove_effect` dispatches only through its action-specific resolver, then clears only the matching action receipt. The six clear helpers independently guard on that same paid flag before clearing the actor pending flag, paid flag, action lock, and controller variable. An unpaid B row therefore cannot refund or clear A's receipt, and a second action from A cannot pass while A's first actor-targeted pending flag remains.

The source test extracts these guards and their shared start/refund branches from parsed current decisions, then exercises source-derived A/B and same-actor scenarios. In the A-paid/B-rejected case, B's same-action lock guard fails, B has no targeted paid flag, so the guarded debit, refund, and clear branches remain closed and A's receipt stays intact. In the A-first-action/A-second-action case, the second action is blocked by A's pending receipt, and its distinct paid flag is absent, so it cannot debit, resolve, refund, or clear the first receipt. These are source-model checks, not an HOI4 runtime simulation.
