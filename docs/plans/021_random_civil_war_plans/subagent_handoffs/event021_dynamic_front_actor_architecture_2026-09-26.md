# Event 021 dynamic front and actor architecture handoff

Disposition: `unresolved`. This is a proposal for parent review, not an implementation or acceptance record.

## Outcome and ownership boundary

No gameplay source was edited. The live front-plan arrays and row binder support a variable number of aligned rows, but the current planner and runtime still materialize named primary, ordinary secondary, ordinary secondary 2, and Event 006 secondary paths. A safe conversion would change the planning, scenario freeze, actor creation, Event 006 adapter, settlement, and cleanup contracts together, including consumers in `common/scripted_effects/021_random_civil_war_effects.txt` and `common/scripted_effects/021_random_civil_war_lifecycle_effects.txt`. Those files are outside this subagent's source ownership. A parent-effects-only loop would leave untracked actors or pending rows and would falsely claim dynamic participation.

This is a source ownership and integration blocker, not a proven Clausewitz loop limitation. Installed vanilla documentation explicitly supports `for_each_scope_loop`, indexed arrays, `while_loop_effect`, `states_filter` in `start_civil_war`, and child effects in the resulting actor scope. The offline wiki notes that one `start_civil_war` call creates only two sides, so additional sides require serial, validated calls with explicit relationships. The actual game behavior of a generalized serial loop remains unverified.

## Current contract and exact bottlenecks

- `event021_parent_append_front_plan_row` at parent-effects line 1708 appends aligned front ID, archetype, anchor, capital, goal, status, actor, type, generation, route, package, state span, force, stockpile, ratios, and relationship values. `event021_bind_front_plan_row` at `021_random_civil_war_effects.txt:973` finds and marks a row by front ID. These are useful dynamic foundations.
- `event021_parent_build_front_plan` at parent-effects line 1835 appends the remnant and primary, then uses separate blocks at lines 1909, 1938, and 1967 for precisely two ordinary secondary names and one Event 006 secondary name. The secondaries carry singleton anchor and actor targets. `event021_parent_validate_front_plan` at line 1785 still checks `maximum_planned_fronts`, a per-plan ceiling to remove only after the consumers are generalized.
- `event021_parent_prepare_crisis_identity` at line 2577 computes `random_civil_war_belligerent_cap` from live region, route, and remaining global front capacity. That calculation is dynamic, but lines 2606–2619 allocate IDs only for three named optional slots. `event021_parent_secondary_front_candidate` and `event021_parent_event6_secondary_front_candidate` in parent-triggers lines 308 and 341 use that cap, so raising the computed value alone cannot create more participants.
- `event021_parent_finish_ordinary_host` at parent-effects line 3330 attempts one Event 006 secondary and one ordinary secondary. `event021_parent_activate_second_secondary_opening` at line 3152 copies the second ordinary slot over the first. `event021_parent_try_secondary_front` at line 3522 and `event021_parent_start_secondary_civil_war` at line 3595 consume the singleton pending slot. This overwriting is incompatible with an arbitrary count of simultaneous planned rows.
- `event021_parent_try_event6_secondary_front` at line 4277 uses one named package, anchor, and actor transaction. Its complete-package admission at line 3960 is necessary and should be reused per row. The current code does not support a second concurrent Event 006 secondary transaction.
- `event021_parent_review_secondary_front` at line 5166 and `event021_parent_review_event6_secondary_front` at line 5138 review named country variables and flags. `event021_parent_update_front_resolution_receipts` at line 5238 also reads those flags. `event021_parent_rollback_transaction` at line 5723 and `event021_parent_cleanup_crisis` at line 7342 clear named pending slots. `021_random_civil_war_lifecycle_effects.txt:924` and `021_random_civil_war_effects.txt:2104` retain matching named cleanup. Settlement and rollback cannot safely consume a larger plan until all of these use row and actor identity.
- Scenario freeze and replay at parent-effects lines 6031 and 6326 preserve named ordinary and Event 006 secondary receipts. A dynamic runtime with this frozen representation would diverge under Maximum Fracture Cascade.

## Constants and tuning

Use the existing state and force severity formulas as tuning inputs and compute requested regions, participant count, and force packages from live country conditions. Remove `maximum_multifront_states`, `maximum_planned_fronts`, `maximum_major_belligerents`, and `maximum_minor_belligerents` only when their references and fixed runtime slots are gone. Preserve the explicitly shared global theater/front ceilings, bounded global registration/review/critical-queue budgets, maximum generation 2, and one-state route limit 1. Do not introduce a per-crisis row, actor, state, or division cap under another name. This handoff changes no constants or weights.

## Event targets, actor identity, and cleanup

Keep the aligned global arrays as the immutable precommit ledger and index by front ID. A plan row's actor entry initially identifies the viable source or dormant Event 006 carrier. On successful `start_civil_war` or package release, bind the created actor's country pointer and the row ID to the durable front registry. Use a single scratch event target only during one serial row transaction; it must be cleared before the next row. Existing global host and original-opposition targets may remain compatibility pointers, but they cannot be the sole participant registry. Per-actor host, immediate opponent, crisis ID, front ID, generation, origin, and route receipts must survive the effect chain so settlement can find them after the global planning arrays are cleared.

Reject an individual optional row only before any dependent war mutation. If a mandatory row fails, rollback reservations and staged values before the first irreversible civil-war call. After a successful call, handle later-row failure as a rejected optional row with precise cleanup; do not pretend that earlier created countries can be rolled back by clearing arrays. For an Event 006 row, reuse the existing complete-package validation and generation reset for failure. Do not annex a pre-existing carrier or duplicate a tag, character, focus package, or Event 006 history. Review all durable front rows before global crisis cleanup, and preserve still-active siblings after one front settles.

## Migration sequence for the parent

1. Define the row/actor identity contract across parent effects, registry effects, lifecycle effects, and scenario freeze. Clarify whether mutable actor entries are updated in place or a parallel durable actor pointer array is used. The before-commit row must remain auditable.
2. Replace named secondary freeze and ID allocation with a loop over viable actor sources and connected unreserved regions. Preserve host-remnant and capital safety, Event 006 complete-package admission, and all shared global capacity gates.
3. Replace named ordinary and Event 006 launch calls with serial per-row staging and activation. After every call, prove the new country, exact transferred states, forces, relationship, front registration, and row status before proceeding.
4. Convert settlement, review, achievements, decision selected-front access, rollback, lifecycle cleanup, and scenario frozen replay to durable front IDs and actor pointers. Remove obsolete named variables and flags only after every reader is migrated.
5. Remove the obsolete per-crisis constants and run scenario-specific read-only MCP and source checks. The separate probability owner must audit weighted surfaces if any weight is later touched; this proposal touches none.
