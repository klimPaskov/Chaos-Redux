# Event 021 ordinary successor continuity audit

Date: 2026-09-19.

Disposition: **blocked** for a source repair of surviving wars and full signatory/obligation continuity. The exact missing input is a verified HOI4 engine contract, or a parent-reviewed live fixture, for the fate of an `add_to_war` participant when `targeted_alliance` is annexed immediately afterward. The treaty owner's out-of-scope rebinding contract also needs a decision about successor-local obligation receipts. No gameplay source was changed, no fallback war was declared, and no commit was created.

## Accepted requirement and current implementation

The current user assignment explicitly treats ordinary successor promotion as needing to preserve and adopt unresolved Event 021 fronts and the host role, surviving actual wars, and signatory/obligation continuity. The source spec independently states that a victorious rebel inherits unresolved fronts, does not receive instant peace with all other fronts, and continues the war against unresolved fronts (`021_random_civil_war_spec_part_3_decisions_missions_and_outcomes.md`, multi-front selection and opposition military victory; `021_random_civil_war_spec_part_4_evolution_i.md`, separate front resolution). The Evolution III spec lists foreign obligations among successor inheritances.

Current source call order is explicit:

1. `event021_parent_promote_ordinary_successor` in `common/scripted_effects/021_random_civil_war_parent_effects.txt` binds the predecessor, marks the claimed successor, calls `event021_prepare_successor_roster_adoption`, white-peaces the predecessor against this successor, then calls `annex_country` with `transfer_troops = yes`.
2. Natural civil-war victory prepares the same claimed-successor receipt via `on_civil_war_end_before_annexation` and `event021_parent_prepare_annex_successor`.
3. `on_annex` calls `event021_parent_prepare_annex_successor`, then `FROM = { event021_treaty_rebind_successor = yes event021_handle_annexed_country = yes }`, then `event021_adopt_successor_roster = yes` in ROOT.
4. `event021_handle_annexed_country` has an exact claimed-successor, predecessor-pointer, and equal-crisis proof before rebinding host-linked front rows, actor host pointers, active-theater membership, and the global host pointer. `event021_adopt_successor_roster` requires that current lifecycle witness, takes the government/host role, and rebuilds the successor's local unresolved actor roster from bounded front rows. This is registry and role continuity, not evidence that an actual war survived.
5. `event021_treaty_rebind_successor` has a separate same-crisis proof and rebinds persistent signatory and front country pointers before the predecessor disappears. It copies the durable agreement id, hold date, settlement type, and selected history flags when it accepts the transfer. Conflict or duplicate detection invalidates the contract.

The existing `successor_roster_adoption_2026-09-02.md` and `lifecycle_helpers_2026-09-02.md` handoffs already distinguish registry rebinding from war continuity. Their proposed pre-annex war handoff was not subsequently wired in the inspected promotion path.

## Exact war blocker

The parent promotion path contains no `add_to_war`, `declare_war_on`, or complete enemy snapshot between the white peace and `annex_country`. The successor and lifecycle helper files contain no war mutation. `random_civil_war_external_war_at_opening` is a boolean historical receipt, and `random_civil_war_immediate_opponent_scope` identifies only one opponent. Neither can enumerate all surviving enemy countries or identify the old host's exact war side.

Installed vanilla `documentation/effects_documentation.md` documents `add_to_war` as joining a named `targeted_alliance` against a named `enemy`, `annex_country` as annexation with optional troop transfer, and `white_peace` as a separate country relation effect. It does not specify that `annex_country` transfers all wars or that a participant joined through `add_to_war` remains in the same war when the named ally is immediately annexed. Installed `documentation/triggers_documentation.md` defines `has_war_with` as a relation check. The offline wiki `Effects` page likewise describes these as separate effects, and its `On actions` page defines ROOT as the winner and FROM as the annexed country for `on_annex` and `on_civil_war_end_before_annexation`. `every_enemy_country` is documented and could enumerate the predecessor's enemies while it exists, but enumeration alone does not resolve war-side continuity after annexation.

Vanilla `common/decisions/SOV.txt` uses `add_to_war = { targeted_alliance = FROM enemy = PREV ... }` for a living civil-war ally. It is a syntax and join precedent, not a precedent for annexing that ally immediately afterward. Chaos Redux Event 006's `common/scripted_effects/006_independence_wave_scenario_effects.txt` declares a bounded war and checks `has_war_with` afterward; it does not show automatic war inheritance from an annexed host. Replacing each relation with `declare_war_on` would choose a new war goal and potentially change alliances and civil-war context, so it is not an accepted continuity repair.

Required missing contract: for each predecessor enemy in a surviving Event 021 front and each external war, determine whether the successor can join the predecessor's *existing* side after the successor/predecessor white peace, and whether that same war and every relevant `has_war_with` relation survive the predecessor's immediate `annex_country` callback. The proof must cover multiple concurrent fronts and unrelated external wars, not only one immediate-opponent pointer. Until this is demonstrated, source-only insertion of `add_to_war` is a guess about engine behavior.

## Treaty and obligation boundary

The persistent treaty registry stores exact signatory country, front, and obligation rows in `common/scripted_effects/021_random_civil_war_treaty_effects.txt`. Its current `event021_treaty_rebind_successor` replaces predecessor country pointers and copies selected successor-local agreement/history receipts. A targeted source inventory found no assignment in that rebinding effect for `event021_treaty_obligation_id`, `event021_treaty_signatory_front_id`, `event021_treaty_member_count`, or `event021_treaty_front_count`. Those local values are set during capture/review and are read by `event021_treaty_signatory_contract_valid` and `event021_treaty_nonempty_agreement` in the treaty triggers. The rebinder also does not transfer the predecessor's live `random_civil_war_settlement_obligation` and its front/active receipts. This is a source-visible continuity gap for a predecessor with an in-progress agreement. It does not prove every ordinary promotion carries such an agreement, because treaty capture has its own negotiated-settlement gate.

The treaty effect and trigger files are outside this assignment's write scope. Copying their local values inside the successor roster helper would duplicate treaty ownership, could conflict with an agreement already held by the successor, and could manufacture valid obligation proof after the treaty helper deliberately invalidated a duplicate or conflicting contract. A parent/owner repair should first specify which exact row and live obligation belong to ROOT, handle an existing ROOT agreement, and preserve the current fail-closed invalidation behavior. It should then make the local receipts agree with the persistent rows under the treaty owner's validation trigger. A historical agreement alone is not proof that an active obligation should move.
