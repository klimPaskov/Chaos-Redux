# Implement Per-Event Chaos Levels

Add a **Chaos level** requirement to normal Chaos Redux events. This is the minimum global Chaos tier at which an event becomes eligible for automatic selection.

Event clusters already have an unlock-tier system. Use that implementation as a structural reference, while keeping event Chaos levels and cluster Chaos levels as separate requirements.

## Required Behavior

Each registered event must have a minimum Chaos level.

Use the existing six Chaos tiers:

1. **Calm World**
2. **Gathering Storm**
3. **Rising Chaos**
4. **Chaos Tier**
5. **Totalen Chaos**
6. **World Collapse**

Do not create a second Chaos tier calculation system. Reuse the current global Chaos tier state and existing tier constants.

An event is eligible only when:

- the event is enabled
- its normal trigger and target requirements are valid
- its fire-once or repeatable state permits firing
- the current global Chaos tier is equal to or above the event's required Chaos level
- every other existing event-selection condition is satisfied

The Chaos level is a minimum tier. Reaching a higher tier must keep the event eligible.

## Registration Architecture

Add the Chaos level to the shared event registry.

Follow the existing event and cluster registration patterns. Keep the event ID and Chaos level data aligned and initialized in one central place.

Use a reusable lookup and eligibility structure. The final naming should follow nearby repository conventions, but the system needs the equivalent of:

- an event Chaos-level registry
- a helper that resolves the required Chaos level for an event ID
- a trigger that checks whether the current event's required Chaos level is met
- scripted localisation that resolves the numeric level and tier name

Do not scatter separate checks such as `event 9 requires tier 2` through selection, settings, GUI, and logging files. The event registry must be the source of truth.

Do not use a large duplicated conditional chain when aligned arrays or the established registry pattern can represent the data cleanly.

Every active event covered by the system must have an explicit registered value. Default to Chaos level 1 for every event when the Chaos level is not specified.

## Automatic Event Selection

Integrate the requirement into the normal candidate eligibility calculation before an event contributes weight to the random selection pool.

When the current Chaos level is below the event requirement:

- the event must contribute no selectable weight
- its stored weight must remain unchanged
- it must not be marked as fired
- its repeatable cap must remain unchanged
- it must not advance the event timer
- it must not add major-event weight
- it must become eligible immediately after the required tier is reached

Do not overwrite the event's stored weight with zero. Treat the event as temporarily unavailable.

If Chaos later falls below the required tier, the event must become unavailable again without losing its weight, fired history, recovery state, cap, or other persistent data.

## Event and Cluster Interaction

Event Chaos levels and cluster Chaos levels are independent gates.

For ordinary automatic firing:

1. The selected event must meet its own Chaos-level requirement.
2. If the event belongs to a cluster, the cluster must also meet its cluster unlock tier.
3. Cluster member-specific minimum tiers must continue to work.
4. All other cluster availability, cooldown, member, participation, and runtime-context checks must continue to work.

The effective automatic requirement can therefore be stricter than either value alone.

White Peace is Event 9 and must remain unavailable during Calm World even though the Peace cluster currently has Chaos level 1. The Peace cluster must not automatically enter through White Peace until the world reaches Gathering Storm.

Do not merge the event level with the cluster level or automatically rewrite one from the other.

## Manual Triggering

Normal manual event triggering from Settings must respect the event Chaos level.

When **Force Trigger Mode** is enabled, the existing force behavior may bypass the event Chaos-level requirement together with the other normal restrictions.

Keep manual cluster forcing consistent with its existing bypass behavior. Do not change cluster force-trigger semantics during this task.

Triggerable scenarios remain separate from normal event Chaos-level eligibility and must not gain this gate.

## Event Logs and Event Details UI

Expose the requirement to the player.

Add the event Chaos level to Event Details using the existing movable event-detail window. Show the numeric level and use the color appropriate for the value. Calm World level 1 should be green, for example.

Examples:

- `Chaos lvl: 1`
- `Chaos lvl: 2`

The Events tab should make the requirement visible without making rows overcrowded. Use either a compact Chaos-level field in each row or a clear requirement or status line in the selected event details, depending on the existing layout capacity.

When an event is unavailable because the current Chaos tier is too low:

- show `N/A` instead of a selectable weight
- provide a clear tooltip or status such as `Requires Gathering Storm`
- do not expose raw scripted trigger text
- do not describe the event as disabled, since the player's event toggle may still be enabled

Keep the enable and disable checkbox independent from Chaos-level availability.

Reuse the existing Chaos tier names and localisation where practical. Add dedicated localisation only where needed for event-specific labels, status text, and tooltips.

If the Events tab layout changes, verify row alignment, text bounds, click regions, tooltip regions, sorting controls, and event-row selection at the supported resolutions.
