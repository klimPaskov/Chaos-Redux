# Famine and migration presentation integration architecture

> **Superseded historical identifier banner (2026-08-25):** Any `fm_*` or `famine_migration_*` identifier quoted in this historical handoff is source-snapshot terminology only and is superseded; current authorities use separate `famine_*`, `migration_*`, or narrow neutral `civilian_transfer_*`/`humanitarian_*` names; see [source_of_truth_map.md](../source_of_truth_map.md).

Status: read-only integration audit completed on 2026-08-25. This handoff is the only file written by this owner. No gameplay, localisation, asset, workbook, or atomic-transfer file was edited, and no commit was created.

## Scope and current integration result

The presentation layer is the state-scoped dynamic-modifier API in `common/scripted_effects/famine_migration_presentation_effects.txt` and `common/dynamic_modifiers/famine_migration_state_modifiers.txt`. It is explicitly not a shared scripted GUI, mapmode, map scan, or population ledger.

The only existing external presentation consumer is `famine_migration_refresh_state_modifiers` in `common/scripted_effects/chaosx_famine_migration_effects.txt`, which calls `famine_migration_presentation_refresh_state`. Core cleanup calls `famine_migration_presentation_clear_state` but does not call `famine_migration_presentation_clear_all_projections`. The external call census is zero for all six `record_*_projection` effects, all six role-specific `clear_*_projection` effects, and `clear_all_projections`.

The ten presentation phases and their authoritative contracts are defined by `famine_migration_presentation_refresh_state`. A presentation receipt is evidence for presentation only; it must never debit, credit, kill, bind, rebind, or create population.

## Shared contract

All shares use `famine_migration_presentation_compute_share`: `clamp(actual_people / exact_population_denominator, 0, 1)`. For live state phases, the denominator is the rounded live state population in people, computed as `state_population_k * constant:famine_migration_presentation.people_per_k`. A receipt phase must pass exact positive people and denominator proof, and the persistent cohort phases must also pass `famine_migration_presentation_input_cohort_id > 0`, `..._input_generation > 0`, and `..._input_role > 0`. Preparing may omit or set the cohort id to zero because it is legitimately pre-cohort.

The generic receipt metadata is `famine_migration_presentation_input_generation`, `famine_migration_presentation_input_role`, and, for every persistent role except preparing, `famine_migration_presentation_input_cohort_id`. The phase-specific proof and people/denominator inputs are documented in `common/scripted_effects/famine_migration_presentation_effects.md`.

The exact transfer owner remains authoritative for `famine_migration_transfer_actual_origin_debit`, `famine_migration_transfer_origin_population_before`, `famine_migration_transfer_survivor_credit`, `famine_migration_transfer_route_deaths`, `famine_migration_cohort_id_request`, and the generation written by `famine_migration_record_transfer_projection`. Route deaths are a separate accounting channel and never enter any presentation people amount.

## Exact lifecycle callsite matrix

### Preparation, request, and cancellation

`fm_prepare_evacuation` in `common/decisions/famine_migration_decisions.txt` sets or removes `famine_migration_evacuation_prepared`; its remove effect does not stage an exact preparation people/denominator/generation/role bundle and does not clear the presentation receipt. The integration point is the proven preparation/mission/request branch, followed by `famine_migration_presentation_record_preparing_projection` and `famine_migration_presentation_refresh_state`; its remove/cancel and execution-start branches must clear preparing.

`famine_migration_request_internal_displacement` and `famine_migration_request_cross_border_flight` delegate to the spontaneous movement owner. `famine_migration_request_organized_evacuation` records the exact displaced cohort and updates flight pressure/flight population but does not record organized presentation state. `famine_migration_submit_survivor_flight_request` is the authoritative paired-flight writer; it must be followed by the state-scoped presentation refresh after both pair values are written.

`famine_migration_cleanup_route_request` clears action-local route inputs and the forced destination proof. It is not currently a presentation clear. The voluntary/forced return cancellation and expiry paths must clear return-readiness only after proving the matching readiness cohort/generation is terminal, and then refresh.

### Corridor lifecycle

`famine_migration_prepare_corridor_contract` stores the exact corridor amount, destination, cohort and route generation. `famine_migration_accept_corridor_offer` only accepts the offer and arms the route; it does not move people or record a presentation receipt. `famine_migration_execute_corridor_evacuation` sets organized role and calls `famine_migration_execute_exact_transfer_transaction`; the shared finalizer then persists the exact transfer receipt. After a proven preparation/accepted mission receipt it must record organized; after successful exact debit it must record depopulated from measured actual debit and clear organized.

`famine_migration_reject_corridor_offer`, `famine_migration_corridor_expire`, corridor unsafe/control-change invalidation, and `famine_migration_corridor_cleanup` are terminal/cancel seams. They currently clear route state but no presentation role. Each must clear preparing or organized only for the exact matching corridor operation and refresh, while preserving durable depopulated history unless the state history itself is retired.

The corridor mission `fm_mission_hold_humanitarian_corridor` completes through `famine_migration_corridor_finalize` and cancels/times out through `famine_migration_corridor_expire`. Neither path currently calls a presentation record or role-specific clear.

### Spontaneous and forced movement

`famine_migration_process_spontaneous_movement_owner` records a displaced cohort, stages role `spontaneous_exodus`, and calls `famine_migration_execute_exact_transfer_transaction` when a destination exists. If no destination exists it calls `famine_migration_spontaneous_movement_trap_request`, which registers the exact trapped obligation. It never calls presentation records directly; the finalizer refreshes live phases, and the centralized transfer receipt seam is the single depopulated integration point.

`famine_migration_execute_forced_transfer_exact` stages role `deportation`, exact route deaths, and the aligned cohort row before calling the exact transaction. Its condemnation/death branch is separate from survivor people. It must feed only measured actual debit into depopulated and only positive survivor credit into a destination/outcome receipt; it must not feed route deaths into any presentation phase.

### Shared atomic finalizer and all exact-transfer producers

`famine_migration_execute_exact_transfer_transaction` is the wrapper around exact preflight, population primitive, reception deltas, cohort bind/rebind, and `famine_migration_finalize_exact_transfer`. `famine_migration_finalize_exact_transfer` is the sole finalizer and calls `famine_migration_record_transfer_projection`, reconciles paired flight/trapped obligations, refreshes, and updates decision phase. The presentation depopulated record belongs once after `famine_migration_record_transfer_projection` has persisted the actual debit and generation; it must not be duplicated in every producer.

The current exact-transfer producers that converge on the finalizer are `famine_migration_process_spontaneous_movement_owner`, `famine_migration_execute_corridor_evacuation`, `famine_migration_execute_forced_transfer_exact`, `fm_famine_evacuation`, `fm_evacuate_vulnerable`, `fm_evacuate_workers`, `fm_distribute_arrivals`, `fm_transit_only`, `fm_enforce_closure`, `fm_third_country_resettlement`, `fm_voluntary_return`, `fm_forced_repatriation`, and the camp producer `camp_rework_germany_apply_prisoner_transfer` through the forced owner.

The three new-origin decisions are `fm_famine_evacuation`, `fm_evacuate_vulnerable`, and `fm_evacuate_workers`. Each selects an exact source/destination, sets organized evacuation role, and calls the exact transaction in its positive branch. Their preparation/cancel branches clear the generic prepared flag but currently do not record or clear presentation organized/preparing receipts.

The six hosted transfer decisions are `fm_distribute_arrivals`, `fm_transit_only`, `fm_enforce_closure`, `fm_third_country_resettlement`, `fm_voluntary_return`, and `fm_forced_repatriation`. Their exact roles are organized evacuation, transit, forced return, resettlement, voluntary return, and forced return respectively. `fm_local_integration` is intentionally listed separately because it is a terminal integration adapter, not a seventh hosted transfer lane; it resolves the exact hosted cohort, updates integrated population, and debits reception without creating population.

`fm_distribute_arrivals` currently sets organized role rather than transit role and calls the exact hosted transfer. `fm_transit_only` is the only exact transit role producer. `fm_enforce_closure` and `fm_forced_repatriation` are forced-return movement paths with separate route-death handling. The three resettlement/return outcome producers call the core durable projection effects after positive survivor credit but do not call the presentation resettlement/return record.

### Reception, local integration, return eligibility, and outcomes

`famine_migration_apply_reception_delta` is the single state/country reception load credit/debit seam, and `famine_migration_refresh_reception_context` derives reception and overcrowded context from exact load and capacity. `fm_open_reception` and `fm_controlled_medical_reception` set policy/services and register capacity; they do not fabricate presentation people. `fm_local_integration` consumes exact reception load through `famine_migration_integrate_displaced_cohort` and must clear a matching transit receipt when it terminates a transit-hosted cohort.

`famine_migration_evaluate_voluntary_return` proves persisted origin/route inputs and currently writes only `famine_migration_voluntary_return_eligible` plus route targets. `fm_voluntary_return` consumes that flag in its exact transfer branch, while `fm_enforce_closure` and `fm_forced_repatriation` use forced-return contracts. Return mission expiry/cancel clears mission subjects and route request state, but no presentation readiness clear is currently wired.

`famine_migration_record_state_resettlement_projection` and `famine_migration_record_state_return_projection` update exact durable counters and context flags without population creation. Their decision producers must supply a cohort-specific survivor-credit/outcome receipt to the presentation layer when available; the existing counters are a bounded fallback only while their context flags are active.

### Missions

The six mission families are `fm_mission_secure_relief_route`, `fm_mission_hold_humanitarian_corridor`, `fm_mission_protect_evacuation_transport`, `fm_mission_deliver_relief_before_reserves_fail`, `fm_mission_prevent_reception_collapse`, and `fm_mission_prepare_safe_return_route` in `common/decisions/famine_migration_decisions.txt`.

Their completion, cancellation, and timeout effects clear mission subject, success, deadline, cohort, and country control variables and recalculate mission state. The corridor mission additionally calls `famine_migration_corridor_finalize` on completion and `famine_migration_corridor_expire` on cancellation/timeout. No mission completion/failure path calls a presentation record or role-specific clear. The evacuation and return mission seams are therefore required inputs for organized/preparing/readiness receipts, while ordinary mission cleanup must not clear durable depopulated or resettlement/return history.

## Cohort visit-history eligibility gates

The decision owner effect `famine_migration_decision_preflight_destination_history` is the current exact ordinary-route preflight. It initializes the aligned visit-history registry, fails closed on missing or misaligned arrays, and rejects a candidate destination already visited by the exact cohort. It is called before the exact transfer by `fm_distribute_arrivals` and `fm_transit_only`.

The same no-repeat rule is not yet proven at every selector surface. `famine_migration_destination_selection_triggers.txt` and the core destination selector still need an exact cohort-history exclusion in candidate visibility, availability, target validity, both weighted selector passes, AI scoring, and the final transaction preflight. A post-transfer achievement disqualifier or after-the-fact history write is not an eligibility gate and must not be treated as one.

The explicit exceptions are persisted-origin voluntary return, forced return, terminal local integration, and third-country resettlement. Those paths may target a previously visited origin or terminal destination only after their exact return/resettlement proof, current control/capacity/policy proof, and exact transfer receipt pass. Ordinary distribution and transit must not use those exceptions. History gating affects route eligibility only; it never supplies presentation people, denominator, cohort role, or route-death amount.

The final exact-transfer preflight must repeat the ordinary history check after destination resolution and before population, reception, bind, history append, or reward effects. A repeat or misaligned history result must leave population, route deaths, reception, cohort arrays, presentation receipts, and history unchanged. Repeated A-to-B-to-A ordinary movement is therefore rejected; explicit return paths remain available and terminally clean the live row/history according to their own contract.

## Cleanup and invalidation audit

`famine_migration_presentation_clear_state` removes all ten presentation dynamic modifiers: `famine_migration_state_preparing_to_leave`, `famine_migration_state_exodus`, `famine_migration_state_organized_evacuation`, `famine_migration_state_depopulated_districts`, `famine_migration_state_reception`, `famine_migration_state_overcrowded`, `famine_migration_state_trapped_border`, `famine_migration_state_transit`, `famine_migration_state_return_readiness`, and `famine_migration_state_return`. It also clears all ten derived phase flags and share/modifier values.

`famine_migration_presentation_clear_state` intentionally preserves the six durable projection receipt families, their active flags, people, denominator, cohort, generation, role, and the depopulated last-generation key. Role-specific clears are therefore mandatory at exact phase terminals, and `famine_migration_presentation_clear_all_projections` is mandatory when state history is actually retired or reset.

The current core `famine_migration_clear_dynamic_modifiers` removes the original food modifiers and only these legacy flow identifiers: `famine_migration_state_exodus`, `famine_migration_state_reception`, `famine_migration_state_overcrowded`, `famine_migration_state_trapped_border`, and `famine_migration_state_return`. It is missing exactly five new presentation identifiers: `famine_migration_state_preparing_to_leave`, `famine_migration_state_organized_evacuation`, `famine_migration_state_depopulated_districts`, `famine_migration_state_transit`, and `famine_migration_state_return_readiness`.

`famine_migration_cleanup_state_registration` calls `famine_migration_clear_dynamic_modifiers` and `famine_migration_presentation_clear_state` when no core migration obligations remain, but it does not call `famine_migration_presentation_clear_all_projections`. The core predicates `famine_migration_state_has_migration_obligations`, `famine_migration_terminal_state_references_clear`, and their country variants omit all six presentation receipt-active flags. This allows a recovered, control-invalidated, annexed, or nuclear-invalidated state to clear live presentation modifiers while leaving stale durable presentation receipts behind.

The state cleanup path is reached from `famine_migration_retire_recovered_state`, invalid-state registration cleanup, `on_state_control_changed`, `on_annex` through bounded `every_owned_state`, and nuclear-state invalidation. Valid control/nuclear transitions refresh state; invalid transitions clean cohort rows and state registration. Each history-retiring path must clear all six receipts only after core ledgers and visit-history rows are no longer needed. Routine reception zero, flight settlement, or one role terminal must not clear another role's receipt.

## Old saves and no-world-scan proof

Old saves have no new presentation receipt variables or active flags. Refresh fails closed for preparing, organized, depopulated, transit, and return-readiness receipts rather than synthesizing values. Existing live flight-pair, reception-load, overcrowded-context, trapped-ledger, and active-context durable counter data can still rebuild their respective live/fallback phases. The old `famine_migration_evacuation_prepared` flag and old country return-eligibility flag are not amount proof and do not activate a receipt phase.

The presentation refresh operates on one resolved state and never invokes `every_state`, `every_country`, or a world-wide collection. Exact movement uses state-scoped targets and aligned cohort rows. Corridor invalidation and country cleanup iterate only registered sparse active-country arrays. `on_daily_CXT` is limited to the CXT test country, and `on_annex` uses `every_owned_state` only for the former country's bounded cleanup event rather than a recurring global scheduler. No mapmode, scripted GUI, flat modifier, placeholder asset, numeric weight, or world scan is part of this architecture.

## Proposed helper map and migration order

The existing presentation API is the reusable helper map; no additional helper or central router is proposed.

| Helper | Scope | Inputs | Outputs and side effects | Required integration seams |
| --- | --- | --- | --- | --- |
| `famine_migration_presentation_compute_share` | State | Exact positive people and denominator | Bounded share result only | Called by `refresh_state` for each phase. |
| Six `record_*_projection` effects | State | Phase proof, exact people/denominator, generic cohort/generation/role metadata | Phase receipt, active flag, share inputs; no population mutation; depopulated generation idempotency | Preparation/corridor, organized requests/decisions, centralized transfer receipt, hosted transit, return eligibility, survivor/durable outcome. |
| Six role-specific `clear_*_projection` effects | State | None, with caller-side terminal identity proof | Clears one receipt family and active flag only | Exact cancellation, execution, onward movement, expiry, failure, or state-history reset. |
| `famine_migration_presentation_clear_all_projections` | State | None | Clears all six receipts only | Complete state-history retirement/reset. |
| `famine_migration_presentation_refresh_state` | State | Live ledgers, persistent receipts, one-shot inputs | Rebuilds ten presentation modifiers/flags and consumes valid one-shot inputs | Must remain behind `famine_migration_refresh_state_modifiers` for every authoritative transition. |

The migration order is: first add the five missing modifier removals to `famine_migration_clear_dynamic_modifiers`; then wire `clear_all_projections` into complete state-history retirement and preserve role-specific clears for normal terminals; then wire preparation/organized/transit/readiness/outcome receipts at their exact owner seams; finally wire the centralized depopulated record once after `famine_migration_record_transfer_projection`. The transfer finalizer remains the single conservation owner, and route deaths remain separate.

The presentation layer uses no event targets. Core transfer event targets remain chain-local and must not be repurposed as durable presentation storage. No new global target is needed; if a future owner introduces one for a route, it must be explicitly cleared at route cleanup and must not replace aligned cohort/history receipts.

Constants remain in the existing `famine_migration_presentation` script-constant category and the existing transfer-role category. No new numeric weights or balance targets are proposed.

## Evidence, blockers, and validation
