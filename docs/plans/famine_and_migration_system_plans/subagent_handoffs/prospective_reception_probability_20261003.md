## Pre-edit source-only decision and pool findings

The official scenario IDs prob_destination_selection_internal and prob_destination_selection_persecution remain required. The internal fixture expects a safe internal host to outrank foreign options; the persecution fixture expects a safe foreign host to outrank a same-ideology persecutor. The source implements the first as sequential priority: migration_select_general_safe_evacuation_destination tries internal_safe_route and only runs foreign_safe_evacuation if no internal destination binds. This is a hard conditional preference, not a shared denominator; foreign candidates are starved while any valid positive internal candidate exists. Within each individual pool, the code performs probability-proportional sampling from candidate weights. This is source structure only; no numeric probability or ranking is certified.

At baseline, the foreign host safety gate required a valid current food proof, route/hazard safety, owner/controller validity, border policy, and valid reception capacity. The selector's adjacent-state prepass invoked the post-observer migration consumer before candidate validation, so the food proof was not limited to previously simulated/stored states. A same-ideology persecutor failed safety before weight calculation; ideology could not rescue an excluded candidate. Without all adjacent candidates and their external facts, the destination race was incomplete.

The requested same-case suite must include the official internal and persecution IDs plus these parent-named cases: dormant valid adjacent host with no services; existing paid capacity; hostile, persecuting, bombed, infected, and disaster host; missing food proof; zero/dead origin; ambiguous front row; exact capacity fit and one-person deficit; repeated offer; stale offer, counterpart capture, and expiry; and OpenReception cost equality/one-below cases for each of its three costs. No machine scenario inputs, target tags, neighbor rows, or typed bindings were invented or submitted.

At baseline, the OpenReception decision used state_target = any_controlled_state and required the selected FROM state to be owned and controlled by ROOT, stable food proof, positive population, route infrastructure, and all source-supported hazard exclusions. Its country visibility also required migration_decision_active and migration_displacement_country_active and explicitly hid while humanitarian_corridor_offer_pending. The migration category itself was visible when a pending offer flag existed, but that category threshold did not reveal OpenReception. This was the baseline host-service bootstrap gap.

OpenReception’s source costs are @MIGRATION_PP_STANDARD = 20, @MIGRATION_SUPPORT_HEAVY = 100, and @MIGRATION_FUEL_LIGHT = 500. Its custom_cost_trigger uses strict greater-than checks for all three; the complete effect deducts the corresponding amounts and installs positive shelter/medical service receipts in the exact selected state. These are frozen source values and expressions, not MCP availability results. Exact-equality and just-below behavior remains untested.

At baseline, corridor offer preparation and operational acceptance shared a strict capacity chain. humanitarian_corridor_front_destination_is_safe required valid positive spare reception capacity. humanitarian_corridor_offer_route_is_valid called the strict front-state validator, and humanitarian_corridor_offer_is_valid called acceptance validity, which also required the strict offer route. Thus an unserviced dormant host could not validate a preparable offer in that path. The repair must split the preparable offer gate from operational acceptance/evacuation gates; acceptance and actual movement should continue to require current capacity, food, route, border, safety, and exact transaction proofs.

At baseline, OpenReception was also hidden while the offer was pending, so merely relaxing preparation was not sufficient to let the host pay. The pending-offer category exception existed, but the action needed an exact pending-front state target and a receiver-side ROOT check before its paid service effect ran. Its existing any_controlled_state target could otherwise install services in a different state from the offered front.

The negotiation decision executes on ROOT with a FROM origin state. humanitarian_corridor_prepare_contract stores requester_country_id = ROOT.id while capturing the origin’s owner and controller separately; the response mirror later cross-checks the stored counterpart against PREV.id. This mapping is valid for the current decision scope. The spontaneous movement owner, however, may run under a global-host ROOT; it explicitly stores the actual origin owner as migration_destination_selection_actor. A new spontaneous corridor request must pass that captured actor explicitly rather than reusing ROOT as the requester.

At baseline, the spontaneous movement flow calculated a living amount from state_population_k minus its protected floor, saved the exact origin/owner, tried the internal-first/general destination selector, then recorded a cohort and ran the exact civilian transfer if successful. If no destination bound it trapped the request. Any new request path must preserve that exact amount and existing obligation proof and must follow the agreed point after internal-safe selection without accidentally bypassing or duplicating foreign fallback behavior.
