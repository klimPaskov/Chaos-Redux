## Primary findings

1. No existing camp, Gulag, genocide, internment, forced-labor, decision, event, or on-action path currently proves all three required owner inputs together: one persisted famine/migration cohort ID, that row's current host state, and the accepted living amount.
2. The exact receipt helper already present at `common/scripted_effects/famine_migration_adapter_effects.txt:14` is intentionally inert. It accepts only `famine_migration_cohort_custody_id_request`, the `internment` or `forced_labor` action enum, a positive whole-row `famine_migration_cohort_custody_amount_request`, `famine_migration_cohort_custody_transaction_proven`, `famine_migration_cohort_custody_actor_proven`, and `famine_migration_cohort_custody_site_proven`.
3. The helper's explicit-ID lookup is a bounded aligned-registry lookup and is allowed by the architecture; a world, country, or state scan that tries to discover a cohort is not allowed. The helper requires exactly one live row, current host equality, valid persisted owner, live status, exact amount equality, and owner proof before forwarding the idempotent receipt.
4. The current camp and genocide systems use `camp_selected_state_id`, `camp_rework_action_state_id`, `FROM.id`, state flags, building levels, site type, quotas, pressure, and death bursts. None of those values is a cohort ID or accepted living-person amount, so none is safe evidence of custody.
5. The closest existing cohort-bound pattern is in `common/decisions/famine_migration_decisions.txt`: `fm_close_border` around line 726, `fm_famine_evacuation` around line 1364, `fm_distribute_arrivals` around line 2193, `fm_local_integration` around line 2629, `fm_third_country_resettlement` around line 2726, and `fm_forced_repatriation` around line 3042 use `famine_migration_current_cohort_id`, explicit state targets, ambiguity guards, exact amount resolution, and owner-scoped transfer/reception effects. These are movement or reception owners, not custody owners.
6. The smallest safe owner change is to extend one existing direct intake or labor-assignment action so it owns one whole live row, carries the explicit ID and amount through the action, and calls the exact receipt immediately after successful acceptance. Site creation, quota changes, pressure, death recording, project completion, release, evidence destruction, or a generic state flag must remain non-producers.
7. If no existing action is approved to own the people, the smallest ordinary fallback is a new state-targeted decision in `common/decisions/famine_migration_decisions.txt` with an explicit selected cohort and explicit host state. Its complete effect must perform the actual internment or forced-labor acceptance and only then call the helper; merely copying `famine_migration_current_cohort_id` into request variables would be unsafe.

## Existing patterns

### Exact receipt contract

The architecture's one-shot request fields are `famine_migration_cohort_custody_id_request`, `famine_migration_cohort_custody_action_request`, `famine_migration_cohort_custody_amount_request`, `famine_migration_cohort_custody_transaction_proven`, `famine_migration_cohort_custody_actor_proven`, and `famine_migration_cohort_custody_site_proven`.

The action enum is `famine_migration_custody_action.internment` or `famine_migration_custody_action.forced_labor` from `common/script_constants/famine_migration_custody_constants.txt`.

The first implementation is whole-row only because the aligned live registry has no split operation. A partial amount must fail closed rather than mark an untracked subset as protected custody.

The receipt does not change population, deaths, the cohort row, or camp pressure. The owner transaction must perform the actual acceptance, retention, or labor assignment first, then call the receipt in the current host state.

### Closest state-targeted cohort pattern

The `fm_*` decisions resolve `famine_migration_current_cohort_id` from an explicit selected state, reject ambiguity, resolve exact live amount, and call a purpose-specific owner-scoped movement or reception effect. This is the correct carrier pattern for any new owner action.

The camp action system instead selects `camp_selected_state_id` or writes `camp_rework_action_state_id = FROM.id` and dispatches an action ID. That state pointer can identify a host but cannot identify a live cohort and cannot be promoted by inference.

### Common smallest transaction design

For every candidate below, the smallest valid design is the same bounded sequence.

1. Select exactly one live row by explicit persisted cohort ID in the action's state scope, with the same ambiguity and status checks already used by the `fm_*` decisions.
2. Require the current row host to equal the owner state, or perform one exact transfer/rebind operation before the owner accepts the row.
3. Make the owner effect actually retain, intern, or assign the entire live amount, and set the request amount to the resolved current living amount rather than a quota, death amount, manpower value, or building level.
4. Set the transaction, actor, and concrete-site proof tokens only after that owner operation succeeds.
5. Call `famine_migration_record_cohort_custody_action_exact` immediately in the current host state and clear only its one-shot request/proof values.

For a cross-state German or other transfer, the source movement and destination owner must use the existing exact transfer/rebind contract. A source-state death burst followed by destination site creation is not a custody transaction.
