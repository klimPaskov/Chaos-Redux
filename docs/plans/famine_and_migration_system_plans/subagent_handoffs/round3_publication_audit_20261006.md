## Source findings

- Food context lifetime: `famine_open_outbreak_food_context` and `famine_open_disaster_food_context` calculate a date offset in their caller frame and store the resulting date on the state. `famine_collect_surface_context` contributes the matching pressures only while the expiry is later than `global.date`. Accepted adapters call the setters only after the corresponding request returns success. Repeated accepted requests overwrite the stored deadline with a fresh deadline, so they extend the window without stacking another contribution. Retirement clears both dates. Relevant definitions are in `common/scripted_effects/famine_adapter_effects.txt` around lines 704-817, `common/scripted_effects/famine_core_effects.txt` around lines 1160-1325 and 3180-3220, and constants in `common/script_constants/famine_core_constants.txt` around lines 225-260.
- Temporary return lifetime: the changed local-war collector initializes `famine_local_war_evidence` in `famine_collect_surface_context` before calling `famine_resolve_local_war_evidence`. The selector does the same before its call. The profile mapper reinitializes occupation and war evidence before mapping. This follows the existing caller-owned temporary-output contract documented in `common/scripted_effects/famine_core_effects.md` around lines 28-35 and the shared date helper's caller-owned output pattern in `common/scripted_effects/chaosx_dynamic_effects.txt` around lines 827-842.
- Selector and mapper agreement: both paths call the same China, Ceara, and Congo cause triggers. The mapper initializes `famine_occupation_profile`, recomputes local-war evidence when a profile is selected, and then calls the matching cause trigger. The selector also initializes occupation and war evidence before evaluating candidates. Each trigger requires positive `famine_food_pressure` and a matching regional owner or controller. The three definitions are in `common/scripted_triggers/famine_core_triggers.txt` around lines 225-302, with calls in `common/scripted_effects/famine_core_effects.txt` around lines 244-420 and 1350-1545.
- Mortality disqualification: after `apply_exact_state_civilian_population_loss`, the mortality owner copies `state_civilian_population_loss_applied` into `famine_mortality_result`. The new disqualification dispatch requires a positive measured result, `famine_crisis_concealed`, and `humanitarian_achievement_blockade_state`. It records the owner and, only when distinct, the controller. The recorder again verifies the state flag, exact state ID, and current generation before setting the credited country's flag. The achievement trigger reads this same country flag as a disqualifier. Relevant code is in `common/scripted_effects/famine_core_effects.txt` around lines 2870-2900, `common/scripted_effects/humanitarian_achievement_effects.txt` around lines 560-585, and `common/scripted_triggers/humanitarian_achievement_triggers.txt` around lines 35-48.
- Nested `PREV` identity: the changed relief, wasteland, recovery, extraction suspension/recovery, and alternative-logistics recorders use `PREV` to read the credited country's tracked values while inside a nested source-state block. In the caller contract, each helper is entered as a country from the famine state, making the outer previous scope the source state. Within `PREV = { ... }`, the preceding scope is the credited country, which is the intended namespace for the recorded state ID and generation. The blockade start recorder also stores the starting state's identity and generation on the country and clears the new disqualifier on a new attempt. No ambient `ROOT` dependency remains in the audited recorder comparisons.
- Cleanup and conservation: context dates clear when the state retires, stage transitions clear both candidate and recovery clocks before the new stage interval begins, and mortality remains on the exact-loss helper's applied-output ledger. No new population transfer or reserve mutation is introduced by these drafts. The takeover test's existing reserve/conservation cases pass, though they do not validate the new mortality dispatch or achievement recorders.

2. For extraction suspension, extraction recovery, and alternative logistics, execute each country recorder from the tracked state with an unrelated `ROOT`; verify matching state ID and extraction generation records progress and either mismatch leaves it unchanged.

4. Repeat with a different controller that has a matching tracked attempt and verify that controller is independently disqualified. Give the controller a nonmatching attempt and verify it is not disqualified. Also verify an identical owner/controller is called only once.
5. Negative disqualification cases: zero applied loss, a requested loss with zero actual applied loss, unconcealed crisis, missing blockade-state flag, wrong tracked state ID, and stale generation must not set the disqualifier. Starting a new blockade generation must clear the previous disqualifier.
