## Core famine flight addendum

### Current gap and exact input contract

The first eligible upward transition is the only current sparse owner that has both a settled food-stage decision and live state scope. Use the existing stage enum (`stable`, `supply_strain`, `acute_shortage`, `famine`, `catastrophic_famine`) and call the new helper only for the stages accepted by the famine design. The existing specification calls for movement from acute shortage, famine, and catastrophic famine; whether `supply_strain` participates must be an explicit design choice rather than an inferred balance target.

Required inputs for a truthful request are the current `state_population_k`, `constant:famine_migration_population.people_per_k`, current committed stage and stage-start date, current `famine_migration_food_security_score` or `famine_migration_food_score_raw`, current need/vulnerability/transport/environment/governance/relief components, food exposure days, and the current state owner/controller actor proof. The current adapter stores only boolean actor proof, so a persistent actor scope is not presently available; use the existing famine owner convention or add an explicit actor target before claiming attribution. The request must use a separate temporary `flight_request_amount` input and leave any death amount in its food-only contract.

The source amount must never be `famine_migration_last_famine_deaths_applied`, `famine_migration_total_famine_deaths`, `camp_site_last_month_deaths`, `natural_disaster_last_deaths`, `state_civilian_population_loss_applied`, or a route-death amount. `state_population_k` already reflects all previous exact losses, so subtracting or reusing the death amount would either undercount the live base or duplicate dead civilians.

### Symbolic live-state formula

Use centralized stage/fear-share and severity mapping constants, with no new arbitrary numeric target in the owner code:

```text
live_people = round(state_population_k * constant:famine_migration_population.people_per_k)
protected_floor = round(live_people * constant:famine_migration_spontaneous_movement.protected_origin_share)
accepted_projection = max(famine_migration_flight_pressure,
                           famine_migration_state_flight_population,
                           famine_migration_trapped_population,
                           famine_migration_state_trapped_population)
active_host_cohort_reservation = sum aligned live cohort amounts whose current host is THIS
                                 and status is active, destination_bound, or destination_bound_unsafe,
                                 excluding rows already represented by accepted_projection
unsettled_origin_reservation = accepted_projection + active_host_cohort_reservation
movable_capacity = max(live_people - protected_floor - unsettled_origin_reservation, 0)
severity_evidence = clamp(central_stage_share(stage) * central_mapping(score, components, exposure), 0, 1)
desired_flight = round(live_people * central_stage_fear_share(stage) * severity_evidence)
flight_request_amount = clamp(desired_flight, 0, movable_capacity)
```

The projection and active-row terms must not be summed blindly. `famine_migration_state_flight_population` mirrors accepted flight requests, and trapped ledgers normally represent a failed subset of that same request. A safe implementation must either maintain a transaction/cohort token that identifies which active rows are already represented by the projection or conservatively reserve the maximum of the two ledgers and the active-row sum. The current arrays have aligned origins, hosts, destinations, owners, amounts, and statuses at `chaosx_famine_migration_effects.txt:19-27,90-98`, but no field linking an accepted pressure request to a provisional cohort. That missing linkage is a blocker for a non-under-reserving exact formula.

The central adapter should reject or clamp the flight sub-request before adding ledgers. It must return the accepted amount, add that accepted amount to both `famine_migration_flight_pressure` and `famine_migration_state_flight_population`, register the displacement state and owner country, and never call a Deaths effect. The existing food amount can continue to be converted through the population-scaled food formula documented at `common/scripted_effects/chaosx_dynamic_effects.md:648-676`.

### Once-per-stage/crisis guard

Persist a stage token composed from a crisis generation and committed stage, for example `famine_migration_flight_request_crisis_generation` plus `famine_migration_flight_request_last_stage`. Mark the token after the separate flight request is accepted, and do not submit again when the sparse evaluator revisits the same stage/date. On an upward stage upgrade, request only the positive delta between the stage's central desired total and the already accepted flight projection for the current crisis. Stable recovery may clear the stage token only when displacement pressure, trapped population, and active origin-host cohorts are all resolved; otherwise clearing it would allow the same crisis to re-add the same cohort. A new crisis generation begins only after the active crisis has fully retired.

The existing candidate-duration hysteresis in `famine_migration_evaluate_food_security` is the cadence/replay guard for the stage transition. The spontaneous movement cooldown at `famine_migration_spontaneous_movement_effects.txt:83-89` throttles route attempts, not pressure submission, so it must remain a separate guard.

### Ledger reconciliation and sparse processing

The exact reconciliation rule is `actual_origin_debit` from the transfer owner, not requested amount and not survivor credit. After a successful spontaneous transfer, subtract the actual debit from both flight ledgers and clamp at zero as already done at `famine_migration_spontaneous_movement_effects.txt:200-205`. After a failed route, add only the positive difference over existing trapped population; perform no population or Deaths mutation. After a successful decision or corridor transfer, the owner must subtract the actual debit from both ledgers; the current pressure-only call sites in `famine_migration_decisions.txt` are the exact cleanup patch surface.

Only the exact transfer owner may create a durable cohort row from measured positive survivor credit. The stage hook must not record a cohort, debit population, add destination population, or call reception. The sparse `global.famine_migration_active_food_states` and `global.famine_migration_active_displacement_states` jobs at `chaosx_famine_migration_effects.txt:4314-4344` are sufficient to process the state after registration. A bounded aligned-cohort reservation helper may walk the existing live arrays, but it must not scan every world state or country.

## Existing patterns

- Positive food adapter pattern: the owner applies the exact loss first, then calls a thin adapter. Air Winter, camp/Gulag/forced labor, chemical, Black Plague, and Event 013 all follow this shape in `famine_migration_adapter_effects.txt:217-327`.
- Positive exact movement pattern: spontaneous movement and forced transfer call `famine_migration_transfer_civilians_exact`; only actual origin debit and measured survivor credit are used, with route deaths separate. The state-ledger skill and `famine_migration_forced_movement_effects.md` require conservation and idempotent transaction identity.

## Risks and blockers

### Confirmed blockers

- Famine stages and famine mortality currently produce no survivor flight request, making spontaneous movement unreachable from famine alone.
- The shared adapter has no live-population flight clamp and defaults missing channels to food-only.
- The live projection and cohort arrays have no transaction key proving whether an active cohort is already represented by `state_flight_population`; blindly summing both can under-request, while ignoring the cohort can duplicate an active request.
- Several exact decision/corridor owners subtract only pressure and leave `state_flight_population` stale.
- Occupation-law, strategic-bombing, war/front, generic peace, generic outbreak, ordinary biological, generic event, cluster, and scenario owners lack one or more exact state, survivor/fear amount, actor, or replay fields.
- The required detailed probability auditor is not installed/callable. The Event MCP route timed out twice, and the map MCP route returned an internal error. These are tool blockers, not permission to claim engine evidence.

### Ordinary risks

- Using `state_population_k` after the exact death owner is the only truthful live base; using a recorded death amount as a flight request duplicates dead civilians.
- Clearing stage tokens while pressure or trapped cohorts remain can re-add the same crisis. Clearing displacement registration while active cohort rows remain can orphan reservations.
- `famine_migration_flight_pressure` and the state projection are currently not initialized together in the food initializer, so any new central clamp must handle missing values explicitly.
- The current mapmode and decision thresholds consume flight pressure, so ledger reconciliation must preserve those existing consumers without adding a GUI or map surface.
