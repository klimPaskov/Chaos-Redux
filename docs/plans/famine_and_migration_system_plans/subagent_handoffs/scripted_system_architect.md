## Event target and cleanup plan

The exact transfer contract requires a regular event target named `famine_migration_route_destination` pointing to the destination state.

The target is intentionally regular rather than global, so the engine clears it at the end of the originating effect chain and no manual global-target cleanup is needed.

The parent must enter the resolved destination state, save that destination as `famine_migration_route_destination` there, validate food safety and reception proof, return to the origin state, and then call `famine_migration_cleanup_route_request` on invalid route or failed action paths.

State cleanup is required after state-control change, annexation, destination invalidation, route cancellation, or pressure recovery.

Country cleanup is required after peace, annexation, country transformation, special/nonhuman classification, destination invalidation, and completed displacement flows.

No on-action or whole-world scan was added.

## Exact-transfer positive-credit evidence and conservation proof

The vanilla effects documentation states that `add_manpower` in state scope adds manpower locally on the state, while country scope adds manpower to the country.

The existing Chaos Redux helper `apply_state_population_loss_without_recruitable_manpower_gain` measures owner/controller `manpower_k` before and after a state debit and applies an observed negative correction, proving the repository's established reconciliation pattern.

The destination helper mirrors that pattern around a positive state add and records actual state population delta by multiplying `state_population_k` before/after values by `constant:chaos_meter_deaths.people_per_k` rather than trusting the requested amount.

For every accepted transfer, the origin debit is measured after the exact debit, route deaths are clamped to that debit, survivors are `actual_origin_debit - route_deaths`, and destination credit is the measured positive destination delta.

The conservation ledger is `actual_origin_debit - route_deaths - actual_destination_credit`.

The transfer result is valid only when the ledger is exactly zero, and global debit, credit, route-death, and residual counters preserve an audit trail.

Route deaths call the existing Deaths registrar with `chaos_deaths_apply_state_pop = 0` and `chaos_deaths_record_state_ledger = 1`, so physical population is not removed twice.

The caller supplies the death reason because the Deaths owner controls the final reason-ID additions and player-facing localisation.

The blockade predicate is conjunctive: it requires owner and controller war state, island, isolation, maritime dependence, either route or port disruption, either convoy or escort shortage, no humanitarian corridor, and insufficient local food.

## Migration plan and parent wiring

1. In each owner-local event, decision, mission, fallout, camp, genocide, condemnation, occupation, war, peace, or disaster path, replace local food/flight pressure arithmetic with the corresponding named pressure adapter after setting explicit amount, source proof, and actor proof.
2. For each movement path, save the destination state to `famine_migration_route_destination`, set all route and destination proof variables, and call `famine_migration_transfer_civilians_exact` once.
3. Consume only the returned actual debit, route deaths, and survivor credit when updating cohort records, event logs, clusters, scenarios, or localisation-facing state.
4. Call integration, resettlement, voluntary-return, forced-return, border, and reception adapters from the decision owner after their gameplay triggers pass; these adapters intentionally do not create population or alter AI weights.
5. Wire state and country cleanup helpers to existing control, annexation, peace, route, destination, recovery, and classifier-change hooks; do not add a whole-world periodic scan.
6. Verify the existing Deaths reason constant and player-facing localisation in the Deaths owner surfaces, then pass the selected reason through `famine_migration_transfer_route_death_reason` where route deaths are logged.

### Dynamic evaluator formula and thresholds

The state caller submits eight normalized components: production, transport, extraction, need, environment, vulnerability, governance, and relief. Missing values default to the centralized zero constant and values are clamped to the centralized 0-100 component range.

The evaluator reads the existing Air Cleanliness contamination flags (`air_contamination_threshold_25`, `_50`, `_75`, `_100`, and `fallout_air_contamination_permanent_99`), state Air values (`air_winter_pressure`, `air_winter_exposure`, `air_winter_strategic_bombing_pressure`, `nuclear_fallout_intensity`), fallout/chemical state modifiers, camp/genocide predicates and variables, gulag site/building surfaces (`gulag_labor_camp_network`, `genocide_gulag_site`, and the proven `camp_state_site_type`), the owner `forced_labor_quota` variable when positive, and only explicit local war/occupation/outbreak/disaster proof variables. Existing owner files remain authoritative and are not modified.

The score is `clamp(((1.15*production) + (1.10*transport) + (1.25*extraction) + (1.00*need) + (0.80*environment) + (0.90*vulnerability) + (0.95*governance) - (1.20*relief)) / 7.15, 0, 200)`. The eight coefficients and normalizer are `famine_migration_food_weight` constants; no tuning number is hidden in the effect.

`famine_migration_initialize_food_state` initializes score, all eight computed components, and state reception/flight/trapped projection amounts to centralized zero values. State retirement and displacement unregister clear those values and their projection flags, preventing stale mapmode or scripted-localisation values after invalidation. `famine_migration_apply_reception_delta` is the only shared state+country reception ledger mutator: it accepts one actual survivor credit/debit and fails closed on an uncovered debit, then refreshes reception and overcrowding flags.

The seven non-relief weights sum to 7.15, so equal pressure `p` in production, transport, extraction, need, environment, vulnerability, and governance with relief at zero normalizes to `p`: `p = 0` is stable, `p = 30` is supply strain, `p = 55` is acute shortage, `p = 80` is famine, and `p = 100` is catastrophic famine. The raw score is not clamped before division, which keeps every entry threshold reachable.

Relief and lower component pressure can cross the recovery hysteresis bands: catastrophic stress at equal `p = 100` is 100 without relief; after relief 100 and a five-point reduction in each component, it is `(7.15*95 - 1.20*100)/7.15 = 78.2`, below the catastrophic recovery threshold 80. Famine stress at `p = 80` can reach 58.2 with relief 100 and `p = 75`, below its recovery threshold 60; acute stress at `p = 55` reaches 38.2 with relief 100, below 40; and supply strain at `p = 30` reaches 8.2 with relief 100 and `p = 25`, below 20. The configured recovery durations still gate each transition.

Stage entry is stable below 25, supply strain at 25, acute shortage at 50, famine at 75, and catastrophic famine at 100. Upward candidate durations are 7/7/14/21/30 days for stable/supply/acute/famine/catastrophic. Recovery hysteresis thresholds are 20/40/60/80 and recovery durations are 14/21/30/45 days for supply/acute/famine/catastrophic. `famine_migration_food_incident_count` increments only when entering acute or worse. State stage flags, candidate date, recovery date, exposure days, and next pulse date are reset on transition.

### Mortality and conservation proof

`famine_migration_apply_famine_mortality` is called only by `famine_migration_evaluate_food_security` for acute shortage, famine, or catastrophic famine after the centralized minimum exposure and due-date gates. Population is read as `state_population_k` and multiplied by `constant:chaos_meter_deaths.people_per_k`; no `state_population` token or fixed historical death total is used.

The pulse reserves `max(round(population * protected_floor_share), protected_floor_people)` and clamps that reserve to current population. Requested mortality is population times the centralized stage rate, exposure multiplier, vulnerability factor, access factor from transport/need shares, extraction factor, environment factor, governance factor, and relief factor; it is clamped to the available population and rounded.

There is exactly one physical loss call site: `apply_exact_state_civilian_population_loss = yes` inside `famine_migration_apply_famine_mortality`. Its inputs are `state_civilian_population_loss_requested`, `state_civilian_population_loss_minimum_remaining`, `state_civilian_population_loss_reason = constant:chaos_meter_deaths_reason.famine`, `state_civilian_population_loss_log_deaths = one`, `state_civilian_population_loss_target_country = OWNER`, `state_civilian_population_loss_has_target_country = one`, and `state_civilian_population_loss_contract_supplied = one`. The returned `state_civilian_population_loss_applied` is stored in `famine_migration_last_famine_deaths_applied` and added to `famine_migration_total_famine_deaths`; no second debit or duplicate Deaths call is made.

After stage resolution, mortality, and dynamic-modifier refresh, `famine_migration_evaluate_food_security` calls `famine_migration_achievement_process_state = yes` before recovery retirement, so achievement consumers observe post-transaction population. The exact-transfer effect exposes `famine_migration_transfer_origin_country_id = OWNER.id` before the origin debit and preserves it through destination credit/cohort-host update for downstream achievement recording.

The existing parent-owned `chaos_meter_deaths_reason.famine` constant, Deaths registration path, scripted localisation, and English localisation key are present and consumed by this effect; no Deaths-surface edit was required here. Player-facing localisation remains outside this surface.

### Persisted cohort ledger and movement lifecycle

`famine_migration_record_displaced_cohort` accepts a state-local positive amount, owner proof, and non-unknown source and appends aligned global arrays `famine_migration_cohort_ids`, `..._origins`, `..._hosts`, `..._destinations`, `..._owners`, `..._amounts`, `..._sources`, and `..._statuses`. It returns `famine_migration_cohort_record_result` and `famine_migration_cohort_id_result`; defaults are invalid/zero. The origin is stored as the initial host and as a destination placeholder only under `active` status, so no missing destination is ever fabricated.

`famine_migration_bind_cohort_destination` is called inside the actual destination state and requires food/reception proof; `famine_migration_bind_cohort_destination_forced` is called inside the actual destination state with explicit forced actor/policy proof and records `destination_bound_unsafe`. Both return a valid/invalid temporary result and save the regular chain target. The forced bind never asserts food or reception safety and is the required deportation/coercive movement path.

`famine_migration_resolve_cohort_origin` accepts an explicit `famine_migration_cohort_id_request`, or derives one from an unambiguous host-state `famine_migration_current_cohort_id` and only then the bounded owner-country selection. It returns `famine_migration_cohort_origin`, `..._host`, and a destination target for safe or unsafe bound rows, plus resolved amount/source/status values. Every later decision transaction must call this resolver before testing event targets; regular event targets are not treated as durable cohort identity. Ambiguous, missing, invalid, or stale rows fail closed.

`famine_migration_evaluate_voluntary_return` requires the persisted origin plus food, route, housing, persecution, contamination, and host-safety proof. `famine_migration_force_return_cohort` resolves the same persisted origin but uses a separate unsafe-host/policy contract and intentionally does not invoke `famine_migration_destination_is_valid`. Neither effect chooses a random neighbor or creates population.

`famine_migration_rebind_cohort_destination_safe` is the safe voluntary third-country resettlement rebind. It must run inside the actual new destination state after the resolver has persisted `famine_migration_cohort_host` and `famine_migration_cohort_owner`; the caller supplies `famine_migration_cohort_resettlement_rebind_request_proven`, `..._food_safe_proven`, `..._reception_proven`, `..._route_proven`, and `..._actor_proven`. It accepts only a nonterminal `destination_bound` row, rejects the current host as the new destination, updates aligned destination/host entries, retains `famine_migration_transfer_survivor_credit` as the amount, and returns `famine_migration_cohort_resettlement_rebind_result`. It never calls a population effect or writes route deaths back to the cohort.

`famine_migration_update_cohort_host_after_transfer` runs in the actual resolved destination after exact movement. It updates only host and amount, preserving original state and owner; the amount is exactly `famine_migration_transfer_survivor_credit`, while `famine_migration_transfer_actual_origin_debit` remains debit evidence and includes route deaths. A zero survivor credit removes the row. `famine_migration_cleanup_cohort_record` removes an explicit row, and `famine_migration_cleanup_cohort_records_for_state` removes rows touching a state only on state invalidation/control/annexation cleanup. Recovery does not erase a live cohort's original identity.

The registered displacement-country processor now calls `famine_migration_reconcile_country_cohort_achievement`. It sums aligned rows with statuses `active`, `destination_bound`, or `destination_bound_unsafe` whose persisted owner tag equals the registered country, writes `famine_migration_achievement_cohort_people`, and calls `famine_migration_achievement_record_major_cohort_duration`. It sets `famine_migration_achievement_all_major_cohorts_resolved` only when a previously tracked major total reaches zero and `famine_migration_cohort_resolution_transaction_proven` was explicitly marked. Integration and safe resettlement mark their successful transactions; parent return and valid cleanup consumers must call `famine_migration_mark_cohort_resolution_transaction` after their transaction. No transfer-cycle detector is claimed because the aligned ledger stores only current host/destination and original origin, not a complete visit history.

### Request adapters and parent wiring

`famine_migration_request_internal_displacement` requires state validity, positive displacement amount, displacement proof, and actor proof; it registers the state for a later owner-controlled exact route. `famine_migration_request_cross_border_flight` additionally requires border-policy proof and submits flight pressure. `famine_migration_request_organized_evacuation` additionally requires transport proof and submits food plus flight pressure. `famine_migration_request_deportation_flow` additionally requires policy proof and submits flight pressure only; none of these effects directly removes population or fabricates a destination.

Occupation-law resolution and Air/fallout context reads are active when a state is already registered; the named camp, gulag, forced-labor, condemnation, bombing, nuclear, fallout, outbreak, disaster, war, peace, event, Air Cleanliness, chemical/biological, cluster, and scenario request wrappers remain API-only pending owner-local call sites. No owner-local file was changed to fabricate a hook or bypass its authoritative direct effects.

### Dynamic modifier consumer contract

`famine_migration_refresh_dynamic_modifiers` removes stale stage/flow modifiers and adds only the flags currently true. It is called after stage transitions, on every evaluator pass, after state-control and nuclear lifecycle refreshes, and before state unregister cleanup. `famine_migration_clear_dynamic_modifiers` removes all nine families for invalidation and retirement.

Stage consequences use the exact icons and centralized values in `famine_migration_modifier`: supply strain reduces local supplies, production, resources, and adds bounded controller attrition; acute shortage additionally reduces local supply impact and army speed; famine and catastrophic famine escalate those bounded fields. These modifiers supplement formula pressure and never write the food score or mortality ledger.

The flow contract maps exodus to `famine_migration_displacement_active` and trapped-border to `famine_migration_population_trapped`, with explicit state flight/trapped projection amounts. Reception and overcrowding use `famine_migration_reception_context_active` and `famine_migration_overcrowded_context_active`, rebuilt from exact state+owner-country reception ledgers. Safe resettlement and return use `famine_migration_state_resettlement_context_active` and `famine_migration_return_context_active` plus state projection amounts. The parent decision owner must call the exact delta/projection helpers only after accepted survivor credit/debit or return proof; shared cleanup clears all projection flags and amounts. No state modifier is inferred from a country-only capacity or return variable.
