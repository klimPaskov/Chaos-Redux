## Exact findings and recommended keys

### Source or wording defects requiring a patch

1. **Doctrine reform eligibility text contradicts the trigger.** `sov_nuclear_bombs_doctrine_reform_requirements_tt` at `localisation\english\023_soviet_nukes_l_english.yml:190` says an Event 23 incident, a major war-state change, **or Evolution I** qualifies. `common\scripted_triggers\023_sov_nuclear_bombs_event_triggers.txt:28-46` permits an investigated test failure, test accident, confirmed enemy nuclear use, capital threat, or Evolution I **together with war**. The current string also contains two semicolons and the player-facing phrase “Event 23.” `sov_nuclear_bombs_reform_custody_doctrine_desc` at line 189 repeats the misleading “evolution, or major war-state change” wording and buries the cost of disruption. Suggested requirement wording: “Requires an investigated test failure, test accident, confirmed enemy nuclear use, threat to the capital, or war after Evolution I. No moratorium or active operation. One reform only.” Keep the icon-first security cost in its existing cost key. Suggested description: “Reorganize nuclear custody over the scheduled reform period. The chosen authority takes control when the work ends, reducing Readiness and Command Integrity.” Verify the exact timing and magnitude against the final effect before applying. The new `.103` event options at `events\023_soviet_nukes.txt:152-188` call `sov_nuclear_bombs_apply_doctrine_reform` without event-owned custom effect tooltips, so the consequences may appear as raw variable/effect output. Add one clear effect tooltip per doctrine choice, or one shared tooltip with dynamic doctrine/value text, while preserving the existing option keys `chaosx.nr23.103.party`, `.military`, `.scientific_safety`, and `.dispersed_commands`.

2. **Phase-navigation strings do not explain their gates or show their selected context.** `chaosx.nr23.100.custody`, `.production`, `.test`, `.coercion`, and `.retaliation` at lines 16-20 are correctly referenced by `events\023_soviet_nukes.txt:97-149`, but their triggered options depend on Evolution I/II/III, atomic technologies, no active project, and no moratorium. No custom blocked-requirement text is attached to those options. `GetSovietNuclearBombsPhaseName`, `GetSovietNuclearBombsCategorySiteName`, `GetSovietNuclearBombsCategoryTargetName`, and `GetSovietNuclearBombsCategoryDeadlineName` are defined at `common\scripted_localisation\023_sov_nuclear_bombs_scripted_localisation.txt:70-291` but have no non-document consumer. The category description at YAML line 100 displays bombs, Readiness, Integrity, posture, and public knowledge only. The selected target/site and current response deadline required by Part 8 are absent from contextual text. Keep the four-item header budget; add phase-specific contextual tooltip or mission text using those functions only after verifying scope and remaining-time behavior. The current deadline keys display full duration constants, not time remaining, and should not be labelled as a live deadline without a timer source.

3. **The national spirits omit the two values the spec says they should show.** `sov_nuclear_bombs_hidden_arsenal_desc`, `sov_nuclear_bombs_demonstrative_deterrence_desc`, `sov_nuclear_bombs_coercive_posture_desc`, `sov_nuclear_bombs_retaliatory_posture_desc`, `sov_nuclear_bombs_unrestrained_posture_desc`, `sov_nuclear_bombs_atomic_moratorium_desc`, and `sov_nuclear_bombs_broken_chain_desc` at lines 138-148 are static. Part 2 requires the primary spirit to show the current posture, Readiness, and Integrity through dynamic localisation. Add current values or concise bands to the relevant spirit tooltips, reusing the existing numeric variables and posture function. Do not add another permanent meter to the decision header. This is a missing dynamic-text surface, not a missing YAML key.

4. **The test report describes an unresolved test after the test has completed.** `chaosx.nr23.101.d` at line 30 says instruments and plans “determine whether” the demonstration succeeds, fails, or becomes an accident. `events\023_soviet_nukes.txt:190-216` makes `.101` a triggered result report, while `.102` is a separate adverse report. Supply an outcome-specific `.101` description and, if needed, distinct success/failure/accident keys selected by the event owner. Do not imply that a completed outcome is still being decided. `chaosx.nr23.102.d` should name the actual material failure or affected test site if that outcome exists in source; the current “ended badly” and “exposed weaknesses” are too vague.

5. **Public news omits the people and places already selected by gameplay.** `chaosx.news.231.d` (line 73) says only “a selected government” and omits the specific demand and response deadline. `chaosx.news.232.d` (line 76) says “its target” with no affected state or defending country. `chaosx.news.234.d` (line 82) says “a successor authority” with no depot or holder. The opening/spec expects named governments, exact states, and concrete consequences. Bind the existing coercion actor/target, strike state, and custody state only where their event scope is valid. Add a safe fallback key for any missing target rather than displaying a raw namespace. Keep the language serious and avoid converting the news into a list of future unlock stages. `chaosx.news.234.d` currently spends its last sentence listing technical access, command formation, and delivery integration instead of describing the custody scene.

6. **The target response explains an implementation rule to the player.** `chaosx.nr23.120.d` (line 39) ends “without starting a war by itself.” That clause explains the event system rather than the government's decision. The passage should instead state the actual demand, named actor, and remaining response time if available. The existing `[ROOT.GetName]` and `[GetSovietNuclearBombsDemandName]` tokens must be preserved or replaced with equivalent dynamic references. Check that the demand function evaluates in the target country's scope for `.120`; source-only inspection cannot prove its rendered value.

7. **The Event Details premise lacks a knowledge gate and reads like mechanics documentation.** `sov_nuclear_bombs.event_details.description` (line 360) is selected unconditionally by `common\scripted_localisation\chaosx_scripted_localisation_events_log.txt:5718`. Part 1 requires foreign views to withhold exact internal information before public reveal. Although the text gives no number, it states the existence and operational structure of the secret arsenal. If foreign players can open this detail before reveal, it discloses the premise early; GUI visibility was not verified because the MCP route timed out. Provide a classified/uncertain public premise while knowledge is unknown, then a fuller description after demonstration. The current four sentences are repetitive: “governed through production, testing, coercion, and disputed custody,” “every weapon remains tied to...,” and “possession alone does not provide...” all explain the mechanics rather than the present situation. `sov_nuclear_bombs.event_details.status.active` (line 364) says “current phase is recorded in the event ledger,” an internal narration with no player value. `sov_nuclear_bombs.event_details.status.recorded` (line 366) similarly announces a record rather than an observable state. The shared GUI concatenates `[GetEventsLogDetailContextLine][GetSovietNuclearBombsEventDetailStatusLine]` in `localisation\english\chaosx_gui_l_english.yml:625`; render the normal, long-text, and missing-localisation states before closing this issue.

11. **The reform and nav text lack consequence detail even where values exist.** `chaosx.nr23.103.d` (line 23) says “long reorganization” and “disrupt the arsenal,” but does not tell the player the duration or expected Readiness/Integrity loss. The parent must reconcile the conflicting design: implement a real Suspected state with matching key and transition evidence, or record accepted omission of that state. Do not add an unreachable label alone.

## Prose-quality disposition by problem type

- **Vagueness:** `.101.d`, `.102.d`, news `.231.d`/`.232.d`/`.234.d`, and generic custody-status lines omit the outcome, actor, place, or action. Replace with verified dynamic names and concrete consequences.
- **Bloat:** `event_details.description`, `event_log.detail`, and `reform_custody_doctrine_desc` pile up systems and qualifiers. Cut to the premise or decision-relevant tradeoff.
- **Obvious explanation:** `operational_command_desc`, `device_assembly_mission_desc`, `dismantle_batch_desc`, and several button tooltips narrate the label or the ledger. State what changes for the player.
- **Repetition:** breakaway custody and operationalization text repeats the same four-stage caveat across news, reports, decisions, and missions. Keep the distinction where a choice could otherwise mislead, then use each remaining passage for its own scene or consequence.
- **Overcomplication:** doctrine reform eligibility and several target/authorization requirement strings use long noun stacks and semicolon-separated conditions. Split into short requirements while preserving every gate.
- **Style-rule repair:** `sov_nuclear_bombs_doctrine_reform_requirements_tt` contains semicolons and an out-of-world event number. No em dash or explicit update-history sentence was found in the English YAML. The sourced `.108.q` quotation is exempt from stylistic normalisation.
