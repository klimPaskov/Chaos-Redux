## Current defects and design gaps

1. **Human Evolution III major first use is denied in the specified no-prior-use case.** The accepted spec says a player can authorize first use against a nuclear major at Evolution III or IV (`docs/specs/023_sov_nuclear_bombs_specs/023_sov_nuclear_bombs_spec_part_5_evolutions_and_exchange.md:265-272`). The Evolution III world gate accepts two operational nuclear majors (`common/scripted_triggers/023_sov_nuclear_bombs_event_triggers.txt:364-373`), but the human branch of `sov_nuclear_bombs_action_major_first_use_gate_is_valid` also requires confirmed enemy use or an already active major exchange (`common/scripted_triggers/023_sov_nuclear_bombs_runtime_triggers.txt:62-94`). The alternative severe first-use gate requires Evolution IV (`common/scripted_triggers/023_sov_nuclear_bombs_event_triggers.txt:412-438`). Those receipt/active flags are established after a prior detonation (`common/scripted_effects/023_sov_nuclear_bombs_runtime_effects.txt:137-188`). Thus a human Soviet player at Evolution III, with the world gate open and no prior nuclear use, has no first-use branch. This contradicts the C2 closure claim in `docs/plans/023_sov_nuclear_bombs_plans/subagent_handoffs/023_near_completion_contract_closure_2026-09-19.md:16`.
2. **Breakaway operationalization can outpace native custody after SOV disappears.** `sov_nuclear_bombs_operationalize_breakaway_site` permits `SOV = { exists = no }` without the `sov_nuclear_bombs_native_custody_removed` marker, moves the site and actor to operational, and records reconciliation (`common/scripted_effects/023_sov_nuclear_bombs_runtime_effects.txt:942-1025`). It grants the holder native bombs only if that marker exists (`:1001-1015`). The marker is set by `sov_nuclear_bombs_mark_site_transferred` only on a successful preexisting-holder or living-SOV native deduction (`:1058-1103`). Consequently, if SOV is already absent when a transfer with no marker is processed, Event 23 can certify an operational breakaway arsenal without providing its native launch stockpile. The spec requires local custody tracks to survive Soviet disappearance (`docs/specs/023_sov_nuclear_bombs_specs/023_sov_nuclear_bombs_spec_part_6_soviet_collapse_integration.md:112-125,382-390`). Vanilla annex stockpile inheritance/order is not proven here; the source inconsistency is conditional and needs an explicit branch disposition and engine check.
3. **A native launch with no matching callback has no bounded terminal result while SOV survives.** The request sets a pending flag before `launch_nuke` (`common/scripted_effects/023_sov_nuclear_bombs_runtime_effects.txt:664-684`); later actions reject while it remains pending (`:617-622`), and reservation release refuses pending (`:408-415`). Exact callback/delta disagreement is handled (`:797-868`), and annex cleanup handles Soviet disappearance (`:1789-1796`), but `common/on_actions/023_sov_nuclear_bombs_on_actions.txt:13-35` contains no surviving-SOV timeout/recovery for no callback. This is not proof that the engine silently fails; it is an unclosed contract branch against the accepted/rejected result expected by `docs/specs/023_sov_nuclear_bombs_specs/023_sov_nuclear_bombs_spec_part_7_shared_systems_cross_event_and_cluster.md:60-70`. Parent should decide a safe fail-closed terminal policy after checking actual callback semantics.
4. **Documentation assigns native launch ownership inconsistently.** `docs/events/023_sov_nuclear_bombs.md:13` says shared nuclear systems own the native detonation call, while current `sov_nuclear_bombs_execute_shared_action` calls `launch_nuke` at `common/scripted_effects/023_sov_nuclear_bombs_runtime_effects.txt:680-684`. Shared systems own consequences. The ownership sentence should be reconciled; this audit did not edit it.
