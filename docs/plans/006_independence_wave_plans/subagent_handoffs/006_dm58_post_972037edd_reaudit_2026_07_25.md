# Event 006 DM-58 Post-Repair Read-Only Re-Audit

Date: 2026-07-25

Audited baseline: commit `972037edd` (`Repair Event 006 reclamation transaction and admission evidence`)

Scope: the DM-58 member loop, war-legality gate, pre-cost failure path, and rollback only.

## Verdict

**Partial / not verified complete.**

The repair puts the strategic and security payments after the staging loop and minimum-count test, and its failure branch invokes rollback without either payment effect.
The state and owner arrays are also intended to reserve distinct pairs.
However, the current source still has a high `ROOT`/current-scope risk inside the member loop, uses an undocumented `clear_event_target` effect, and cannot prove lossless rollback because it does not record whether a claim or same-type wargoal existed before staging.

## Remaining static risks

1. **High — loop member scope.** Official effects documentation says `for_each_scope_loop` changes scope to the current array element. The offline wiki example uses `ROOT` inside that loop for the original outer scope. DM-58 calls a scripted effect from the loop and then mixes unqualified current-member tests with `ROOT` member mutations. This can collapse staging and rollback onto the decision taker instead of each member unless an engine-specific scripted-effect root reset can be demonstrated.

2. **High — unsupported target clearing.** `clear_event_target` appears at `common/scripted_effects/006_independence_wave_decision_effects.txt:668-669,738`, but it is absent from current vanilla `effects_documentation.md`; that documentation exposes only `clear_global_event_target` and `clear_global_event_targets`. A search of vanilla script and documentation found zero `clear_event_target` uses. If ignored or rejected, a later loop iteration can retain the previous regular event target and pass `has_event_target` without selecting a new pair.

3. **High — claim provenance.** Rollback can delete a legitimate pre-existing member claim because the transaction does not record whether `add_claim_by` changed state.

4. **Medium — wargoal provenance.** Rollback can remove an unrelated pre-existing `take_state_focus` wargoal against the same owner because the removal effect accepts only type and target, not the generated state list or a transaction identifier.

## Validation and limits

- Traced the current trigger → member loop → resolver → count gate → payment/rollback paths directly at `972037edd`.
- Compared `for_each_scope_loop`, `can_declare_war_on`, `remove_claim_by`, and `remove_wargoal` against the offline wiki and current vanilla documentation.
- Searched vanilla script and documentation for `clear_event_target`; no precedent was found.
- Confirmed balanced braces in the three audited DM-58 source files and no `git show --check` defect in `972037edd`.
- An attempted HOI4 event-inspector lint was rejected because its selector supports event-chain nodes rather than these decision/scripted-effect identifiers. No runtime execution or in-game validation was performed.

## Accepted-plan disposition

The transaction-order portion of `006_dm58_pre_cost_atomic_repair_2026_07_25.md` is implemented: staging and the minimum-count check precede payment, and failure is pre-cost.
Its claims that the loop acts once per member and that rollback removes exactly the staged artifacts remain **reopened** by the scope and provenance findings above.

## Recommended next actions

1. Make the current loop member explicit throughout staging and rollback without relying on `ROOT` changing at scripted-effect invocation.
2. Replace or prove `clear_event_target` with a documented, vanilla-supported lifecycle that cannot leak a prior iteration's target.
3. Record claim and wargoal provenance before mutation so rollback removes only artifacts created by this transaction.
4. Re-run the same source trace, then test at least: two eligible members with different owners, two members competing for one owner, an eligible state with a pre-existing claim, a member with no eligible state after a prior successful iteration, and a pre-existing same-type wargoal.
