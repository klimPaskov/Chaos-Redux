### Medium: durable sovereignty is visible before its settlement gate

`independence_wave_rut_codify_durable_sovereignty` requires `independence_wave_founding_settlement_complete` in `available` (lines 471–479), but its `visible` block (lines 465–470) only requires project readiness, a route government, crisis resolution, and the absence of the completion flag. It can therefore display an unavailable project before the shared founding-settlement focus is complete, unlike the network corridor, whose visible and available blocks both include the settlement and crisis-resolution gates. Either add the settlement flag to the durable visible block or provide an intentional tooltip explaining why it is shown early. This is a clarity issue rather than a bypass because `available` remains fail-closed.

### Medium: paid-project timeout semantics need explicit plan acceptance

All ten paid projects use the sibling KOS/MNT `days_remove` plus `remove_effect` convention. Their timers are successful completion paths; only the founding mission has a separate `timeout_effect`. Cancellation invokes the bounded `independence_wave_rut_apply_project_failure` helper. This is consistent with the existing decision grammar and is acceptable if “timeout” in the plan means ordinary project completion after its timer. If the plan instead requires a distinct failure penalty when each paid timer expires, that requires a broader design change and must not be silently inferred.

### Medium: requirement feedback is mostly raw trigger output

The paid decisions expose `custom_cost_trigger` and cost text, but capital control, active-project serialization, route availability, host-war fallback, stable-ledger, network-member, league-route, and crisis-resolution requirements remain raw `available` triggers. Once localisation exists, add concise `custom_trigger_tooltip` or dynamic requirement text for the long blocks, especially former-host fallback and network/durable prerequisites. ## Costs and requirement clarity

The RUT administration-light and administration-standard gates require more than the shared RUT civilian-factory floor (floor zero, therefore one available project factory), command power, and manpower. The strategic gate adds stability, war support, and the shared diplomatic-standard convoy-or-train commitment. Security-standard and security-major use shared infantry equipment, support equipment, manpower, and Army XP. Diplomatic-standard uses command power and either convoys or trains; the shared payment effect selects the available transport. The one civilian-factory burden is exposed through the parser-safe file-scoped value `@CR_SC_INDEPENDENCE_WAVE_RUT_CIVILIAN_FACTORY_USE = 1`.

The cost gates and payment effects are real resource exchanges; none is a political-power store, passive checklist, free-unit loop, war-goal spam surface, or core-grant loop. Missing RUT cost localisation is still a hard player-facing gap.

## AI validity and route locks

Decision AI uses centralized shared scores: urgent for the founding mission and emergency command, high for depots, guards, communities, constitutional, socialist, and sovereignty projects, and standard for host settlement, agrarian route, and network. Guard and emergency priorities double during war; host settlement doubles when no severe host threat is detected. Visibility/availability gates select exactly one of the four researched RUT route flags and require no existing RUT route-government lock. Network participation is additionally gated by the founding-settlement flag, crisis resolution, league route, and stable ledgers.

The package AI strategy file supplies mountain survival, former-host restraint, settled compact, and emergency guard layers. These strategy declarations are useful context, but the probability adapter does not produce a normalized strategy-factor surface for this file; the weighted mission evidence above remains incomplete. Verify the named empty/unprepared, ready-peace, ready-war, host-threat, stable-route, and network-ready scenarios with the final compare receipt before attestation.

The paid `days_remove` convention remains a documented design choice rather than an unimplemented timeout branch.
