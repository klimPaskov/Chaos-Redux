## Executive disposition

The Event 006 core does not need another allocator, registry, evolution, ledger, retired-crisis compatibility layer, decision family, GUI layer, country package, focus route, formable, or super-event concept before the country-content phase.

The synchronized allocator, retired pre-wave crisis compatibility layer, Event 005 collision boundary, reusable `chaosx_country_*` registry projections, five evolution incident families, four scenario intensities, and country/former-host/Network/League/patron ledgers are connected deeply enough to remain closed at source except for one concrete SCN-008 post-commit type-application defect.

The current scenario contract says that Universal Belligerence opens at most one war per released country and reserves a target only once per launch.

The Neighboring Releases and Nearby Nonleague States rules implement that target reservation with `independence_wave_scenario_belligerence_targeted` and `global.independence_wave_scenario_belligerence_targets`.

The Former Hosts rule instead calls the ordinary `independence_wave_scenario_start_all_host_wars` path, and `independence_wave_scenario_start_host_war` neither checks nor writes the target-reservation marker.

Two selected countries with the same surviving former host can therefore both open a Universal Belligerence war against that host.

`IW-008` Rhineland and `IW-010` Saar provide a current, bounded witness because both packages are content-attested, their distinct anchors `51` and `42` are explicitly allowed to coexist, and both can derive the same German former host.

This is not a request for another scenario mode or a package change.

It is one missing connection between the accepted Universal Belligerence rule and the target-reservation helper already used by its other two variants.

## Concrete design problem: Universal Former Hosts bypasses target reservation

The current `independence_wave_scenario_start_universal_belligerence` effect clears the shared belligerence target marks before and after type application.

Its Neighboring Releases branch loops over `global.independence_wave_scenario_country_entries` and calls `independence_wave_scenario_start_neighbor_release_war`.

Its Nearby Nonleague States branch calls `independence_wave_scenario_start_nearby_nonleague_war`.

Both helpers reject a country already marked `independence_wave_scenario_belligerence_targeted`, mark the selected target before declaration, append it to `global.independence_wave_scenario_belligerence_targets`, and remove the mark immediately if the declaration fails.

The Former Hosts branch instead calls `independence_wave_scenario_start_all_host_wars`, which loops through the same released-country array and calls `independence_wave_scenario_start_host_war`.

The host-war helper validates the actor, former-host variable, target existence, war state, and `can_declare_war_on`, but it does not reject a marked host, mark a selected host, append it to the bounded cleanup array, or unmark it after failure.

That ordinary behavior is correct for **Wars of Separation**, whose accepted purpose is to place every released country into its own viable former-host war.

It is not correct for **Universal Belligerence: Former Hosts**, whose current system documentation promises the same at-most-one-target reservation rule as the other Universal variants.

The defect is observable without inventing a package: `IW-008` and `IW-010` can coexist through the accepted `RG-RHINE-SAAR` two-anchor exception and can both record Germany as their former host.

Under Universal Former Hosts, the current loop can therefore declare two separate scenario wars against Germany in the same launch.

## Bounded implementation specification

### Target policy

Universal Belligerence: Former Hosts must reserve a distinct former-host target per scenario launch.

Wars of Separation must remain unchanged and may continue to open one viable former-host war for every released country even when several countries share that host.

Within Universal Former Hosts, the first released country in the frozen scenario-country order that can lawfully declare against an unreserved former host receives that target.

Later releases with the same already-reserved host do not open a duplicate war and receive the existing `independence_wave_scenario_regional_threat_mission` result.

If the first actor selects a host but the declaration does not become an actual war, the reservation must be released immediately so a later eligible actor may attempt the same host.

Successful target reservations must persist only until `independence_wave_scenario_start_universal_belligerence` completes, then the existing bounded cleanup must clear every flag and array entry.

### Preferred helper design

Reuse `independence_wave_scenario_belligerence_targeted`, `global.independence_wave_scenario_belligerence_targets`, and `independence_wave_scenario_clear_belligerence_target_marks`.

Do not create a second persistent target registry.

Add a temporary policy input to the existing host-war helper or a very small wrapper around it; prefer the policy input because it keeps the declaration, witness, danger-count, and regional-threat behavior in one implementation.

The policy input must be active only while the Universal Former Hosts loop runs.

The ordinary `independence_wave_scenario_start_all_host_wars` call used by Wars of Separation must call the same helper with uniqueness disabled.

The Universal Former Hosts branch must call a bounded loop with uniqueness enabled.

When uniqueness is enabled, the host-war helper must perform this order:

1. resolve and validate the living former-host target;
2. reject the target if it already has `independence_wave_scenario_belligerence_targeted`;
3. mark and append the target before `declare_war_on`;
4. confirm the war with `has_war_with`;
5. retain the target mark on success;
6. clear the flag and remove the target from the array on failure;
7. apply the existing regional-threat mission result when no war starts.

Use existing script constants for policy and success values rather than adding literal boolean-number magic values.

Do not add a whole-world on action, global country scan, duplicate war helper body, alternate war target fallback, dummy war, second declaration attempt per actor, or post-launch persistent marker.
