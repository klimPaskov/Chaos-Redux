## D01. Retire the old Event 089 meaning without rewriting its history

Joining and refusal call `brilliant_scientist_record_tech_sharing_acceptance` or `brilliant_scientist_record_tech_sharing_refusal`. Those callbacks have their own once-only historical meaning.

**Selected draft resolution:** New campaigns use Doctor Wu as the sole ordinary Event 089 incident. Reserve the old `.2`, `.3`, and `.4` identities for legacy compatibility and do not reuse them for Wu popups. Allocate Wu's visible chain from a collision-checked new range. The canonical `.1` entry can dispatch the new design only after the campaign's content-origin version proves it is using the Wu contract.

Existing memberships, leader rewards already paid, and Kruger's recorded acceptance or refusal remain unchanged. A public Wu institute, medical treaty, independent archive, or joint laboratory must not call those old callbacks simply because it concerns scientific cooperation. A future integration that intentionally changes Kruger's attitude needs a separate reviewed consequence and receipt.

For a save that already consumed legacy Event 089, preserve that fire-once consumption. Do not reset it to manufacture an additional natural event. For a queued old invitation or leader notification, preserve its old meaning and exact reward guards until it settles or is explicitly retired by a compatibility transaction. Do not transform a pending old popup into a Wu appointment.

Historical rows require origin-qualified presentation so the old technology-sharing incident is not relabeled as a Doctor Wu arrival. A save without enough version or origin evidence remains a compatibility blocker for automatic reinterpretation. Absence of a Wu character is not proof that the old event never fired. This draft does not authorize a new manual migration scenario to circumvent that uncertainty.

Implementation must inspect actual dispatcher, queue, log, and save-origin consumers before replacing the entry. The migration cannot be declared complete from editing only the event file. No dispatcher, event, history, or save was changed in Stage 2.

**Disposition:** The requested rework identity is an explicit user decision. The conservative compatibility design above is a proposed resolution. Implementation and source-specific save compatibility remain unresolved.

## D03. Finite Wu replacement cohorts inside the shared clone owner

**User requirement:** Wu can discover cloning early through the shared system, without firing Army of Clones and without an unlimited free-manpower loop.

**Observed contract:** `clone_refresh_reserve_manpower` multiplies physical `clone_equipment` stock by `constant:clone_system.weekly_manpower_per_equipment`, currently ten. It does not consume that stock. Captured and transferred stock also provides the recurring benefit. The current Kruger final completion contract explicitly retains the legacy behavior. A fixed production price does not make the same item's recurring output a one-time personnel transaction.

**Selected draft resolution:** The shared clone owner needs a finite medical-replacement cohort mode for Wu-derived whole-person production. Use a distinct physical cohort archetype because capture, transfer, production, and manpower consequences are intentionally different from the legacy stock. This extension remains inside the shared clone system. It must not become an event-local duplicate of that system or an eighth family silently inserted into the existing seven-family Kruger selector.

A finite cohort has one original material identity, one current holder, a fixed remaining person entitlement, and one settlement history. Its material can be held, transferred, captured, admitted to a formation, or converted to a bounded replacement-person result. Consuming it for one result removes the corresponding entitlement before any alternative result can commit. Splitting or merging the physical lot conserves its remaining entitlement. No recurring manpower modifier reads this cohort class.

The next replication part must specify exact batch size, production, training, care, and admission accounting. It must decide whether a result is represented by native military manpower or new living civilian population at each stage, never both for the same person. Repairing an existing patient creates neither. Recorded dead people remain dead.

Do not call `clone_grant_infantry_access` as the completion of Wu's finite clinical route before this owner extension exists. That helper opens the legacy manufacturing and recruitment economy. The existing custom API's clone selector also grants the established clone family and cannot be treated as a finite clinical-person helper. Where a country already legitimately owns legacy clone technology from another source, retain it and its source history. Wu's new production must not mint its recurring-income stock as an unrecorded substitute.

Legacy Kruger and Mengele stock, refinements, and accepted recurring output remain unchanged by this planning stage. A proposal to rebalance that entire shared economy would be a separate owner decision. Compatibility work may let Wu care for an existing legacy formation, but cannot award the same formation a second manpower stream or change its refinement through an unrelated treatment.

This choice resolves the accounting direction for the Wu draft. It does not claim the shared owner has approved or implemented the new mode. The required extension is a dependency for implementation of finite Wu replacement people. Research access remains baseline and does not depend on Kruger, Chaos, an evolution, or a natural cloning event.

**Disposition:** The preservation and no-loop requirements are explicit user decisions. The finite shared-owner extension is proposed. The full Part 7 design, owner acceptance, concrete tokens, and transaction evidence remain unresolved.
