## Findings, sorted by severity

### Earlier source findings — corrected in the current snapshot

The former named-argument and `$PARAM$` helper paths have been removed. The six profile availability/setter pairs now use zero-argument profile-specific triggers/effects, the four preparation decisions call `missiles_activate_preparation_mission = yes`, and the helper dispatches by operation type to four literal native mission IDs with a locally declared `[DAYS]` expansion (`common/decisions/032_missiles_decisions.txt:464-505,567,602,640,690`; `common/scripted_effects/032_missiles_operations_effects.txt:1738-1760,2577-2629`). The timer arithmetic remains the one-day anchor plus calculated duration and one-day grace. I do not carry the former helper-argument finding forward.

The affordability wrappers are now zero-argument and populate five quote temporaries with `set_temp_variable` before calling the shared inclusive affordability predicate (`common/scripted_triggers/032_missiles_preparation_cost_triggers.txt:13-67`). `set_temp_variable` is explicitly documented as a trigger in installed `documentation/triggers_documentation.md:7482-7499`, and the installed vanilla precedent uses it in `common/scripted_triggers/GER_scripted_triggers.txt:152-153,190-191`; I therefore do not treat this as an effect illegally embedded in a trigger.

The operation-site receipt validator now requires each participant to have an allocation variable, be strictly positive, equal `ROOT.missiles_operation_site_allocation`, and remain within that site's capacity (`common/scripted_triggers/032_missiles_operations_triggers.txt:169-189`). The reservation writer copies the same root allocation onto each participant (`common/scripted_effects/032_missiles_operations_effects.txt:2436-2444`). Integer allocation/remainder behavior remains broader queued work; this validator now rejects missing, zero, or mismatched shares without changing the allocation formula.

## Decision category and operation lifecycle

The flow stays inside the existing Event32 decision category. Human target selection is paged; profile selection splits tactical and strategic families, and target-state selection uses the state target array. Each of the four preparation choices rechecks country eligibility, its accepted-preflight cooldown, and its operation-specific readiness/affordability conditions. Precision readiness is also rechecked at the operation-validity gate; common readiness/control and site constraints are source-backed in `common/scripted_triggers/032_missiles_operations_triggers.txt:153-199` and shared preparation gates in `common/scripted_triggers/032_missiles_triggers.txt:294-314`.

The source ordering is transactionally sensible: a prepare helper runs before fees; the decision debits command power, fuel, and support equipment and sets its cooldown only inside the `accepted` preflight branch (`common/decisions/032_missiles_decisions.txt:550-568,589-603,627-641,677-691`). Rejected preflight therefore does not debit these visible costs or start a cooldown, assuming the decision effect executes as written. The four accepted paths then call the zero-argument activation effect, which dispatches to a literal matching mission ID and locally declares its `[DAYS]` meta replacement (`common/decisions/032_missiles_decisions.txt:567,602,640,690`; `common/scripted_effects/032_missiles_operations_effects.txt:2577-2629`). This is source support, not runtime proof.

The latest escrow order is also source-backed: `missiles_reserve_operation_resources` first computes the per-site share, then requires `missiles_operation_projected_site_allocations_fit` (each selected site must be valid and have capacity at least that share) before calling the reserve-debit effect (`common/scripted_effects/032_missiles_operations_effects.txt:2448-2482`; trigger at `common/scripted_triggers/032_missiles_operations_triggers.txt:191-210`). If resource reservation is rejected after the operation receipt is created, `missiles_preflight_operation` calls `missiles_abort_operation` before `missiles_cleanup_operation`; abort refunds any active reserve receipt before cleanup clears it (`common/scripted_effects/032_missiles_operations_effects.txt:2484-2533,4884-4893`; refund at `common/scripted_effects/032_missiles_effects.txt:561-590`). This validates the current ordering without endorsing integer allocation/remainder semantics.

The mission lifecycle otherwise now has a coherent source graph. Each preparation mission requires the matching operation type and due trigger, cancels when the active preparation receipt is no longer valid, calls the ready-state setter on success, and routes cancel/timeout through `missiles_cancel_preparation` (`common/decisions/032_missiles_missions.txt:135-236`; `common/scripted_effects/032_missiles_operations_effects.txt:2564-2656`). The offline decision-modding reference confirms that an unselectable mission completes immediately once `available` becomes true; the current missions leave `selectable_mission` unset, so the due trigger can drive `complete_effect` and the setter. The source math is static one-day mission anchor plus a computed extension and one-day grace (`common/decisions/032_missiles_missions.txt:135-137`; `common/scripted_effects/032_missiles_operations_effects.txt:2577-2629`; constants at `common/script_constants/032_missiles_constants.txt:874-875`). Installed docs and vanilla CHI precedent support `add_days_mission_timeout` with a scoped `days` value; current dispatch uses literal mission IDs and a `[DAYS]` declaration local to each `meta_effect`. No runtime evidence is claimed.

`missiles_cancel_preparation` records the failure before abort and cleanup (`common/scripted_effects/032_missiles_operations_effects.txt:2633-2656`). Cleanup removes all four ordinary preparation missions and resets operation/pending selection state while keeping the selected enemy target (`common/scripted_effects/032_missiles_operations_effects.txt:4895-4978`). The final launch action is separated into the prepared phase and gates on the commit validator (`common/decisions/032_missiles_decisions.txt:734-755`; `common/scripted_triggers/032_missiles_operations_triggers.txt:231-248`).

The operation and target variables used by this flow have clear gates and consequences in source: precision readiness, common readiness/control, hostile state controller, profile/objective match, site validity, and counterforce proof are all represented in the predicates. ## AI, route locks, and target validity

Selector decisions are `ai_will_do = { base = 0 }`. Ordinary target selection excludes faction partners; the state trigger requires an enemy controller and disallows actor control while accepting a state still owned by the chosen target (`common/scripted_triggers/032_missiles_triggers.txt:270-292`). Human counterforce selection requires a counterforce profile and a proven target state; the AI branch searches valid hostile countries/states (`common/decisions/032_missiles_decisions.txt:652-675`; `common/scripted_triggers/032_missiles_operations_triggers.txt:83-97`). Rogue/retaliation faction exceptions remain scoped to their special operation context.

The delegated `chaosx_ai_probability_auditor` source review reports the four ordinary preparation-decision and four mission willingness blocks match the frozen baseline; these are willingness scores, not click probabilities. The counterforce operation type now selects and locks the counterforce target profile before considering a requested profile (`common/scripted_effects/032_missiles_operations_effects.txt:1901-1934`). The score formulas are source-visible: logistics adds `min(railway_level, 5) × 15`, industrial adds the sum of arms factory, industrial complex, dockyard, synthetic refinery, and fuel silo levels × 120, and counterforce adds the profile score plus site capacity × 20 minus site damage × 2 (`common/scripted_effects/032_missiles_operations_effects.txt:1953-2000`; constants at `common/script_constants/032_missiles_constants.txt:1084-1092`). These are implementation values, not balance recommendations.

The weighted auditor's suspected random-overwrite finding does not hold against the current source: a scored winner stores the state and sets the result to one (`common/scripted_effects/032_missiles_operations_effects.txt:2042-2048`); target selection initializes its result to zero and later profile-ladder branches/fallbacks recheck zero before acting (`common/scripted_effects/032_missiles_operations_effects.txt:2077-2199`). Thus random fallback is reached only if scoring did not select a state, and the scored winner is preserved. This source audit does not validate engine execution.

## Cleanup, cost parity, and exploit risk

The cross-cancel cleanup hazard is contained in the current source. Only the four ordinary preparation missions call `missiles_cancel_preparation`, which records and aborts their own precommit receipt (`common/decisions/032_missiles_missions.txt:150-235`; `common/scripted_effects/032_missiles_operations_effects.txt:2649-2656`). The six non-operation missions do not call `missiles_abort_operation` or `missiles_cleanup_operation`: survey and secondary-site cancellation/timeouts use their own helpers; repair, recovery, and warning verification clear their own flags/due dates; network restoration's cancellation/timeout effects have no state-mutating helper (`common/decisions/032_missiles_missions.txt:23-132,239-291`; `common/scripted_effects/032_missiles_operations_effects.txt:2660-2687`). Survey and secondary-site cancellation clear the shared `missiles_pending_site_state` only after checking the other project's in-progress flag. I found no operation-owned target, launch-site, active-operation, reserve-receipt, or mission fields cleared by those six non-operation cancellation/timeout handlers.

The exact non-operation cancellation write-set is project-owned: survey clears `missiles_survey_in_progress` and `missiles_survey_due_date`; secondary-site work clears `missiles_secondary_site_in_progress` and `missiles_secondary_site_due_date`; each clears shared `missiles_pending_site_state` only if the other project is not active. Repair clears `missiles_site_repair_active`, `missiles_site_repair_requested`, `missiles_site_repair_started`, and `missiles_site_repair_due_date`; recovery clears only `missiles_site_recovery_active` and its due date; warning verification clears only `missiles_warning_verification_active` and its due date (`common/scripted_effects/032_missiles_operations_effects.txt:2660-2687`). Network-restoration cancellation/timeout clears none of these and leaves the severed/restored network state to its native mission outcome.

The four ordinary operation timers are removed by `missiles_cleanup_operation`; participant site operation IDs/allocations are zeroed only when the site receipt ID matches the active operation ID. The cleanup then clears operation-owned fields, including the optional `missiles_requested_launch_site`, while leaving the selected enemy in place (`common/scripted_effects/032_missiles_operations_effects.txt:4895-4978`). The optional site request is accepted only when the stored scope exists, remains actor-controlled, can launch, and satisfies special-payload custody as applicable (`common/scripted_effects/032_missiles_operations_effects.txt:2213-2251`). When the variable is present but invalid, the automatic fallback branch requires it to be absent, so preflight remains rejected instead of silently choosing a different site (`common/scripted_effects/032_missiles_operations_effects.txt:2252-2271,2448-2475`). No non-operation cancellation helper clears this operation input.

This is a cancellation/timeout ownership check only; it does not certify that the broader survey, construction, repair, recovery, or warning success/timing paths are fully implemented. Cooldowns are assigned after accepted preflight, so failed attempts do not consume a cooldown. The ordinary preparation flow does not introduce a free retry loop in source: accepted attempts pay the same four cost types shown to the player, while the launch/abort lifecycle retains its pre-existing reserve receipt handling. Physical payload escrow/native numeric behavior and operation-site capacity integer allocation are explicitly outside this bounded audit and remain broader accepted work.
