## Findings

1. **No confirmed actor/state-scope defect explains the native rejection.** `chaosx_test_country_provision_facility_type` first checks whether an already owned and controlled CXT state can host the current type (`common/scripted_effects/chaosx_test_country_effects.txt:70-95`). The foreign-state selector prefilters candidates, saves their current owner and controller, then transfers ownership and sets controller to `ROOT` (`:97-135`). Its decisive `can_construct_building = [FACILITY]` check occurs after those transfers (`:137-157`), so a failure there is not merely the expected result of testing a still-foreign state. Rejected states restore their original owner and controller. Later placement candidates are iterated through `random_owned_controlled_state`, checked against the shared requirements, and tested with native `can_construct_building` before construction (`:182-220`).

   Installed trigger documentation says `can_construct_building` is supported in STATE scope and checks whether the country as `ROOT` and the state in scope can build that type. The offline Triggers snapshot says the same. Both CXT call sites have state scope and CXT as `ROOT`. The shared trigger also explicitly requires `is_owned_by = ROOT`, while its host trigger requires `is_controlled_by = ROOT` (`common/scripted_triggers/chaosx_test_country_triggers.txt:21-37`); installed documentation lists both ownership and control triggers as STATE-scope commands with ROOT as a supported target.

2. **No explicit facility DLC or technology gate is declared in the inspected building definitions.** Vanilla `land_facility` is defined at `C:/Program Files (x86)/Steam/steamapps/common/Hearts of Iron IV/common/buildings/00_buildings.txt:556-577`; the indexed definition is unoverridden. The mod's `biowarfare_facility` is defined at `common/buildings/chaosx_buildings.txt:38-72`. Both definitions declare special-project specialization, facility grouping, supply, and DMZ behavior, but neither declares `is_buildable = no`, `hide_if_missing_tech`, or an explicit DLC condition. The offline Building modding snapshot says `is_buildable` defaults to yes and `need_supply` means the building needs supply for operation (`paradox_wiki/Building modding - Hearts of Iron 4 Wiki.md:121-133`).

   CXT's technology helper enumerates the runtime `global.technology` database and grants each entry from index 1 onward (`common/scripted_effects/chaosx_test_country_technology_effects.txt:12-40`). Initial setup invokes it before the facility pass, and invokes it again after its initial special-project completion pass (`common/scripted_effects/chaosx_test_country_effects.txt:435-452`). This rules out an obvious source-order omission, but the loaded technology array does not prove DLC ownership or establish that a native facility gate passed.

   Installed `has_dlc` documentation defines the trigger as checking whether the player has a DLC. The files present in the installed game directory and the technology index are not an ownership signal. The current diagnostic helper already records `has_dlc = "Gotterdammerung"`, the current state owner/controller, shared placement, and the post-transfer native construction result when its existing trace flag is active (`common/scripted_effects/chaosx_test_country_facility_diagnostics.txt:6-45`). This review did not run the game, inspect logs, or add runtime diagnostics.

3. **The current candidate limit admits one more attempt than its name and value specify.** `chaosx_test_country_count.facility_search_max_candidates` is `24` (`common/script_constants/chaosx_test_country_constants.txt:35-36`). The loop starts its counter at zero, performs a candidate attempt, increments the counter, then exits only when `tries > 24` (`common/scripted_effects/chaosx_test_country_effects.txt:80-81, 86-95, 168-173`). That permits candidate 25. The reported 25-state result predates this current code, so this off-by-one cannot be assigned as its cause. Recommended bounded correction: after increment, stop at `greater_than_or_equals` 24, or check the limit before beginning the next attempt. Parent owns any implementation.

4. **One source comment overstates the supply construction rule.** The shared trigger comment says installed documentation requires a supply-connected province to start construction (`common/scripted_triggers/chaosx_test_country_triggers.txt:39-43`), while the retrieved offline Building modding section describes `need_supply` as an operational requirement and no installed building documentation for `need_supply` was found through the reference route. The current code uses the capital/supply-node/railway test as a preferred placement pass and falls back to any native-eligible owned and controlled state (`common/scripted_effects/chaosx_test_country_effects.txt:179-220`), so this wording discrepancy does not itself explain a missing facility. A later comment-only correction should call the first pass a supply heuristic/preference and retain the native trigger as the construction decider.
